Deployment Analyzer Agent

Cloud-orchestrated, local-analyzed, read-only deployment understanding -- IaC topology, service dependencies, env-overlay diffs, image audits, CI/CD pipelines -- with a live analysis surface. One of three standalone analyzers (alongside Code Analyzer and Data Analyzer).

1. Overview

The Deployment Analyzer is a read-only agent that produces a structured, cited Markdown report answering a user's question about how a codebase is deployed: the services it ships as, their inter-service dependencies, the environment-config overlays (dev / staging / prod), the container images and their vulnerability surface, the CI/CD pipelines that build and ship them, and the IaC files that wire them all together. It handles everything from focused questions ("what env-vars does auth-svc read in staging?") to broad audits ("walk the entire deploy topology and call out config drift"). It never modifies infra.

Internally the agent is two LLMs cooperating:

  • An Orchestrator on the active cloud provider decomposes the request into a task list, reviews each analyzer response, decides the next task, and finally assembles the full report.
  • An Analyzer on the local Ollama model answers one unit task at a time by parsing IaC files (docker-compose, k8s manifests, Helm charts, Terraform, CloudFormation), CI/CD pipeline definitions (GitHub Actions, GitLab CI, Azure Pipelines, CircleCI), and Dockerfiles in the repo + dependency closure.

The agent rides on the session-scoped TODO framework: the orchestrator's plan is a TodoList, each analyzer task is a TodoItem, and the existing todos editor pane + inline chat todos widget give the user live progress. A dedicated Analysis Report Pane renders the final synthesised Markdown and lets the user highlight a finding and send it back to the chat panel as a quoted follow-up.

The analyzer is standalone in every regard -- its plan, run loop, review loop, synthesise, present gate, findings store, artifacts dir (docs/deploy-analysis/<slug>.md), REPL entry (/deploy-analyze), prompt assets (~/.insrc/deployment-analyzer/), and tool registry are independent of the Code and Data analyzers. Removing one of the others does not affect this one. Cross-agent enrichment via registered tools is opt-in (see §13).

1.1 Two Entry Flows

The Deployment Analyzer accepts two entry shapes. Both share the same run-task / review / synthesise core; they differ only in whether the plan step is needed.

Decision: The synthesise step runs on the local LLM, not the cloud. The cloud is the heavy reasoner for plan + per-task review (where it sees minimal context per call); the local model writes the final Markdown report from accepted findings it already has in hand. Keeps cloud token cost focused on decisions, not prose generation.
Step Flow 1 -- direct user question Flow 2 -- tasks pre-decomposed (called from another agent)
Plan cloud LLM decomposes the user's request into DeployAnalysisTask[] Skipped -- the caller hands over DeployAnalysisTask[] directly
Run-task (per task) local LLM executes one task, calls read-only tools (deploy:* + fs.* + cross-agent code:* / data:*), emits a structured DeployAnalyzerResult
Review (per task) cloud LLM reviews the analyzer output; decides accept / retry-with-hint / add-follow-up / done
Synthesise local LLM composes the final Markdown report from accepted findings + citations
Output Final report rendered in the Analysis Report Pane; present gate fires for save / copy / send-to-chat Final report returned to the caller as a structured { report, findings, citations, confidence } object; no present gate (caller decides what to do with it)

Flow 1 is what the user reaches via /deploy-analyze or the classifier's deployment-analysis intent. Cloud LLM does the up-front decomposition because the user's prompt is unstructured.

Flow 2 is what another agent reaches when it wants this analyzer to handle a specific scope it has already framed. The caller dispatches via the cross-agent deploy:analyze tool (see §13.5) with a prepared task list. The analyzer skips plan, runs the tasks, reviews each, synthesises, and returns the result inline -- the caller's run-task LLM gets a tool result back, just like any other cross-agent call. Single-hop depth cap still applies. fs-access gates still fire on Flow 2's first read under any out-of-repo IaC root per session.

2. Goals & Non-Goals

Goals

  • Decomposed analysis. Break a broad request into focused sub-questions so the local model never has to carry the whole problem at once.
  • Cited answers. Every finding names a manifest file, a resource (kind + name), an env overlay, a CI job, or a Dockerfile + LOC range. No free-text speculation.
  • Multi-format topology. The analyzer composes a single deployment view from heterogeneous sources: docker-compose for local dev, k8s manifests for staging / prod, Terraform for cloud resources, GitHub Actions for the build chain. The user shouldn't have to mentally stitch them together.
  • Env-overlay aware. Findings flag values that vary across dev / staging / prod (or are missing in one of them). Helm values, Kustomize overlays, and Terraform tfvars are first-class sources, not afterthoughts.
  • Local-heavy, cloud-thin. Analyzer work (parsing IaC trees, walking Helm/Kustomize overlays, rendering manifests) runs locally. Cloud is used for planning and final synthesis only.
  • Progress-visible. User sees the plan, sees tasks complete one by one in the Analysis Pane, and can steer mid-flight.
  • Resumable. Crash / VS Code restart / model switch mid-analysis preserves completed analyzer results.

Non-Goals

  • Infra mutations. The analyzer never runs kubectl apply, helm install, terraform apply, docker push, or any cloud-API write. If a finding implies a fix (e.g. unset prod env-var), the user moves it to the coding agent separately.
  • Live cluster introspection. The analyzer reads the IaC tree at rest; it does not connect to a live cluster, list real running pods, or read live config-map values. Live cluster access is a future iteration with its own approval flow.
  • Cloud-API queries. No live AWS / GCP / Azure SDK calls in v1. The analyzer parses what's checked into the repo. Live cloud audit is a future iteration.
  • Unbounded autonomy. Capped iterations -- 16/24 soft/hard task caps, independent of the other analyzers (§6.3).
  • Vulnerability scanning at depth. Image audit ships a known-bad list for common base images; it doesn't talk to OSS Index, Snyk, or trivy. A separate "image-scan" tool can be wired in later via the cross-agent surface.

3. Family & Variant

Decision: The Deployment Analyzer is its own family (deployment-analyzer), not a variant of research and not a sub-mode of the Code Analyzer. The family owns its own registry row, slash command (/deploy-analyze), TODO ownership stamp (owner: 'deployment-analyzer'), prompt assets directory (~/.insrc/deployment-analyzer/), artifacts directory (docs/deploy-analysis/), and read-only tool surface. None of those depends on the Code or Data analyzer at runtime.

Why a sibling family rather than a variant of code analyzer or research:

  • Standalone in every regard. Removing the Code or Data analyzer leaves the Deployment Analyzer fully functional. The user can disable any of the three via insrc.analyzers.enabled without breaking the survivors.
  • Disjoint tool surfaces. Deployment wants deploy:topology / deploy:service-deps / deploy:env-diff / deploy:image-audit / deploy:cicd-pipelines backed by per-format parsers (compose, k8s, helm, kustomize, terraform, cloudformation, github-actions, gitlab-ci, azure-pipelines, circleci). Hosting these under another family forces a lowest-common-denominator tool registry; a separate family lets the Deployment Analyzer carry the right closed set for its domain.
  • Disjoint citation shapes. Deployment citations are (manifestFile, resourceKind, resourceName [, envOverlay]); rendering them inline with code or data citations would muddle the Analysis Report Pane.
  • Independent plan budget. The 16/24 soft/hard cap is owned per family, so cross-agent fan-out doesn't share a budget across analyzers (§6.3).

Prompt assets live in ~/.insrc/deployment-analyzer/: plan.md, review.md, analyzer.md, synthesise.md. Bundled defaults shipped; user copies override.

4.2 TODO Framework as Backbone

Same backbone story as the Code and Data analyzers (see code-analyzer.html §4.2). The framework owns plan persistence, item state machines, live event streams, the editor pane + inline chat widget. The Deployment Analyzer leans on deps.todos for everything except LLM task execution, IaC parsing, and final-report rendering.

4.3 Relation to Existing Artifact Kinds

The codebase already ships parsers for several IaC formats as artifact kinds (plans/artifact-tasks.md): deployment-sources.ts (docker-compose + k8s manifests), terraform-source.ts (Terraform plan + state). The Deployment Analyzer builds on these -- it doesn't re-implement format parsing.

Decision: The Deployment Analyzer is the agent layer on top of the existing artifact kinds. It calls into them as parser libraries (not as the artifact-rendering pipeline), composing their output into a unified topology + cross-format findings.
Concern Lives in

What we do NOT build: a second copy of docker-compose / k8s parsing. The shipped artifact kinds are the source of truth; the Deployment Analyzer imports their parsers as functions and composes their output.

             | 'free-form';

  };
  origin:      'plan' | 'follow-up';
  retryCount:  number;
  hint?:       string;

  answer?:     string;
  findings?:   DeployFinding[];
  citations?:  DeployCitation[];
  confidence?: 'high' | 'medium' | 'low';
  toolCalls?:  ToolCallSummary[];
  truncated?:  boolean;

5.2 Item Lifecycle

Same five-state lifecycle as the other analyzers. The Deployment-specific blocked reasons are fs-access-denied (the user refused the out-of-repo gate -- see §7.3) and parser-error (an IaC file failed to parse; the orchestrator records the file path + error and continues with siblings).

5.3 Feedback Channel: Batched Annotations → Chat

Decision: Same as the other analyzers. User feedback flows through the Analysis Report Pane's annotate-and-batch-send-to-chat path, not through framework per-item comments. list.meta.suppressComments: true applied.

5.4 Hierarchy & Follow-Ups

Two patterns:

  1. Flat follow-ups (default). A reviewer add-follow-up appends items to the same list with meta.origin = 'follow-up'.
  2. Scoped sub-list (when a follow-up explodes into ≥ 3 tasks). Common case: a topology task discovers 8 services and the user wants per-service drill-downs; the orchestrator spawns a child list seeded with service-deps tasks per service. The pane renders root + child as sibling flat cards with cross-references.

6.4.1 Decomposition prompt (cloud LLM)

The planner sees the user's request + a summary of detected IaC roots (compose files, k8s manifest dirs, helm charts, terraform modules, CI/CD definitions, Dockerfiles) and emits an ordered DeployAnalysisTask[]. 

You are the planner for the Deployment Analyzer agent. Your job is to
decompose a free-form user request about a codebase's deployment topology
(IaC, services, env overlays, images, CI/CD) into a sequence of focused
sub-tasks the local Analyzer can execute one at a time.

# Task kinds

  topology         Discover the IaC tree -- enumerate compose files,
                   k8s manifests, helm charts, terraform modules,
                   cloudformation templates -- and consolidate into a
                   { services, edges, envs, sources } shape. Almost
                   every plan starts with one of these unless the
                   user has named specific services already.

  service-deps     Per-service dependency tree: env-vars + secret refs
                   + ConfigMap refs + sibling services + DBs / queues
                   / caches it references. Comes after topology.

  env-diff         Resolve a single name (env-var / value-file key /
                   secret ref) across all configured env overlays
                   (dev / staging / prod). Highlights drift +
                   missing-in-overlay.

  image-audit      Inventory container images across Dockerfiles + k8s
                   + compose; flag known-bad bases against the bundled
                   list.

  cicd-pipelines   Parse CI/CD pipeline definitions (GitHub Actions,
                   GitLab CI, Azure Pipelines, CircleCI, Jenkins).
                   Surfaces jobs, secrets referenced, deploy targets.

  helm-values      Walk values.yaml across overlay files (chart-default
                   + per-env overlay + secrets-as-values), report
                   effective merged values per env.

  free-form        Fallback -- avoid when possible.

# Output shape (strict JSON)

{
  "tasks": [
    {
      "kind": "topology" | "service-deps" | "env-diff" | "image-audit"
            | "cicd-pipelines" | "helm-values" | "free-form",
      "title": "<6-10 word label>",
      "question": "<full question; complete sentence>",
      "scope": {
        "paths":    string[]?,    // IaC roots to consider
        "services": string[]?,    // service names from a prior topology
        "envs":     string[]?     // "dev" | "staging" | "prod" | custom
      }
    },
    ...
  ]
}

# Decomposition guidelines

- Order tasks: topology FIRST when the user's question requires
  discovering services. Subsequent service-deps / env-diff /
  image-audit tasks reuse the topology cache (built once per run).
- One env-diff task per name -- don't bundle "diff DB_HOST and
  REDIS_URL"; emit two tasks. The analyzer's per-name tool call is
  the natural granularity.
- helm-values is independent of topology; can run in parallel with
  the others.
- cicd-pipelines parsing is independent too.
- Cap at 16; never exceed 24.

6.4.2 Review prompt (cloud LLM)

Same shape as the Code / Data analyzers. Domain-specific signals the reviewer attends to:

  • Topology completeness. A topology result that lists 3 services when the repo's IaC tree clearly has 8 implies the analyzer missed some manifest dirs -- retry with a broader paths scope.
  • Env-overlay coverage. An env-diff task that reports values for dev/staging but says "prod overlay not found" should fire a follow-up env-diff with explicit paths to the prod manifest if one exists.
  • Image audit precision. Findings that flag an image as "potentially vulnerable" without naming the CVE or the specific deprecated tag are weak -- retry with a strictness hint.

7. Analyzer

7.1 Task Contract

interface DeployAnalysisTask {
  itemId: string;
  kind:
    | 'topology'
    | 'service-deps'
    | 'env-diff'
    | 'image-audit'
    | 'cicd-pipelines'
    | 'helm-values'
    | 'free-form';
  question: string;
  scope?: {
    paths?:    string[];
    services?: string[];
    envs?:     string[];
  };
  hint?: string;
  origin: 'plan' | 'follow-up';
  retryCount: number;
}

interface DeployAnalyzerResult {
  itemId:      string;
  answer:      string;
  findings:    DeployFinding[];
  citations:   DeployCitation[];
  confidence:  'high' | 'medium' | 'low';
  toolCalls:   ToolCallSummary[];
  truncated?:  boolean;
}

interface DeployCitation {
  agent:        'deploy';
  manifestFile: string;            // path within the repo
  resourceKind: string;            // "Deployment", "Service", "aws_lambda_function", ...
  resourceName?: string;           // resource's logical name in the manifest
  envOverlay?:  string;            // "dev" | "staging" | "prod" | a custom overlay name
  lineRange?:   [number, number];  // for citing the exact span in the manifest
  confidence:   'high' | 'medium' | 'low';
}

7.2 Read-Only Tools

Tool Purpose Notes
deploy:topology Discover the IaC tree: enumerate compose files, k8s manifests, helm charts, terraform modules, cloudformation templates; consolidate into a unified { services, edges, envs, sources } shape Backed by deployment-sources.ts + terraform-source.ts + new helm / kustomize / cloudformation parsers. Caches the topology for the duration of the analysis run.
deploy:service-deps Per-service dependency tree: env-vars + secret refs + ConfigMap refs + sibling services it talks to + DBs / queues / caches it references Combines the topology output with per-manifest deep parsing. Returns { envVars: EnvVarRef[]; secrets: SecretRef[]; sibling: ServiceRef[]; stores: StoreRef[] }.

Handles helm values.yaml hierarchies, kustomize overlays, terraform tfvars, CI/CD env blocks. Highlights inconsistencies (set in dev/staging, missing in prod).
deploy:image-audit Inventory container images across Dockerfiles + k8s + compose; flag known-bad bases (eol distros, deprecated tags) against a bundled list Returns { images: ImageRef[]; flagged: SecurityFinding[] }. Best-effort against a local list; deeper vulnerability scanning is a future iteration via cross-agent.
deploy:cicd-pipelines Parse CI/CD pipeline definitions across flavours (GitHub Actions, GitLab CI, Azure Pipelines, CircleCI, Jenkins, Drone) Returns PipelineDefinition[] with jobs, secrets referenced, deploy targets, container images used. Keeps the original-file-line references for citations.
deploy:helm-values Walk values.yaml across overlay files (chart-default + per-env overlay + secrets-as- values), report effective merged values per env Returns { env: string; values: object; sources: SourceTrace[] }. Handles --values / --set chains.
fs.read / fs.list / text.grep Manifest discovery + content reads Same shape as the Code Analyzer's. Out-of-repo paths trigger the access gate (see §7.3).

Explicitly excluded: any cluster-mutating call (kubectl apply, helm install, terraform apply), live cluster reads (kubectl get), cloud-API calls (AWS / GCP / Azure SDK), shell exec other than parser invocations, file writes, network fetch outside the repo's IaC files.

7.3 Scope & Out-of-Repo Access Gate

The Deployment Analyzer often needs to read files outside the active repo: a sibling infra/ repo, a shared Terraform module, a private Helm chart repo cloned alongside. Same gate as the Code Analyzer (code-analyzer.html §7.3):

  • The active repo root + every directory under it are implicitly approved.
  • Out-of-repo reads request approval at parent-directory granularity; once granted, every descendant is approved for the rest of the session.
  • Approvals are session-scoped and not persisted.
  • Default after 5-min timeout = deny.

IaC trees often span repos in well-defined ways (a service repo with a sibling infra repo); parent-directory granularity covers the common case in one gate.

7.4 Tool Loop

Per-task tool loop on the local model:

  1. System prompt is prepended with /no_think.
  2. User message contains the task JSON + the topology cache (if a deploy:topology call was made earlier in this run -- expensive to recompute and rarely changes between tasks).
  3. Model emits tool calls; daemon executes them; results fed back.
  4. Loop terminates on: model emits a final answer, hard cap of 8 tool calls, or 60 s wall clock.
  5. Final model turn produces the DeployAnalyzerResult JSON.

7.5 Citations

Invariant: every claim resolves to at least one DeployCitation. Missing-citation result auto-downgrades to confidence: 'low' after one retry.

Citation rendering: the Analysis Report Pane links each citation to the manifest file at the cited line range; resource-kind + name show as a structured tag pair (k8s/staging/auth.yaml :: Deployment/auth-svc :: env: DB_HOST). Env overlays are rendered as a small badge column to the right of the main citation text.

7.6 Local LLM System Prompt & Per-Kind Tool Guidance

Load-bearing rule (uniform across the three analyzers): the in-memory topology cache, the per-format parser summaries, and any cached IaC-tree-hash fingerprints are pointers / filters only. The analyzer must always call fs.read on the actual manifest / Dockerfile / pipeline-yaml / values.yaml file at the cited line range before producing a finding or citation. The topology cache tells you which file to look at; the actual file content is what gets cited. Findings backed only by topology summaries or parser-output rows without a corresponding fs.read are rejected by the reviewer.

Why this rule matters: parser output is lossy by design -- it normalises across formats so the orchestrator can reason about deployments without knowing the difference between a Helm template and a CloudFormation block. But citations need to point at the original text the user can open and edit. A finding that says "auth-svc reads DB_HOST" without a fs.read of the actual env block is a half-finding; the user can't click through to the source.

Bundled default in ~/.insrc/deployment-analyzer/analyzer.md: 

You are the Deployment Analyzer's local executor. You receive ONE task
at a time and produce a structured DeployAnalyzerResult.

# Hard rules

1. Topology cache + parser output are POINTERS, not answers. For any
   finding that names a manifest / resource / env-var, you MUST
   fs.read the actual file at the cited line range in the same task.
   The cache tells you where; fs.read is what you cite.

2. Every claim resolves to a DeployCitation. The citation must
   reference (manifestFile, resourceKind, resourceName?, envOverlay?,
   lineRange?) you actually read in this turn.

3. Closed tool list. Hallucinated tools error out.

4. Bounded loop. Hard cap of 8 tool calls per task; 60 s wall-clock.

5. Never mutate. No kubectl apply, helm install, terraform apply,
   docker push -- not even composing such tool calls. The deploy:*
   tools are parser-only by design.

# Per-kind playbook

## topology

  Goal: discover services + edges + envs across the IaC tree.

  Sequence:
    1. deploy:topology() -- builds the run-cache.
    2. For each service in the result, fs.read the primary manifest
       file at the resource block (line range) -- this is what gives
       you the citation snippet for the report. The topology output
       is a summary; the manifest body is the citation.

  Common pitfall: the topology summary lists "auth-svc -> postgres"
  but doesn't say which line declares the dependency. fs.read the
  manifest's env block or volume-claim block to find the actual line.

## service-deps

  Goal: env-vars / secrets / ConfigMap refs / sibling services /
  stores for ONE service.

  Sequence:
    1. deploy:service-deps(service) -- structured deps.
    2. For each env-var / secret / ConfigMap ref returned: fs.read
       the manifest at the cited line so the report can show the
       actual yaml block.
    3. (Optional cross-agent.) For env-vars whose names look like
       DB connection strings (DATABASE_URL, REDIS_URL, ...):
       data:list-connections to flag whether that connection is
       registered with the data-driver.
    4. (Optional cross-agent.) For env-vars whose names look like
       app config: code:trace to surface which code paths read them.

## env-diff

  Goal: per-overlay value table for ONE name.

  Sequence:
    1. deploy:env-diff(name).
    2. For each env that has the name set: fs.read the source line
       (helm values, kustomize overlay, k8s ConfigMap, terraform
       tfvars). The line text is the citation snippet.
    3. For each env that's MISSING the name: report it explicitly --
       missing-in-prod is a common drift finding worth surfacing.

## image-audit

  Goal: image inventory + known-bad flagging.

  Sequence:
    1. deploy:image-audit() -- builds the inventory.
    2. For each flagged image: fs.read the Dockerfile (FROM line) or
       k8s manifest (image: tag) at the cited line so the report can
       show the offending line verbatim.
    3. Don't speculate about CVEs the bundled list doesn't cover --
       say "image X uses base Y which is not in our flagged list" if
       a user asks.

## cicd-pipelines

  Goal: jobs, secrets, deploy targets per pipeline.

  Sequence:
    1. deploy:cicd-pipelines() -- enumerates parsed pipelines.
    2. For each pipeline: fs.read the pipeline yaml in full (they're
       small, < 5 KB typical). Cite specific job blocks for
       findings about a particular job.
    3. For secrets referenced: don't fabricate values; cite only the
       reference (e.g. ${{ secrets.PROD_DEPLOY_KEY }}).

## helm-values

  Goal: per-env effective merged values + source trace.

  Sequence:
    1. deploy:helm-values() -- runs the merge.
    2. For each env's values bundle: fs.read each contributing source
       file (chart-default, per-env overlay, secrets file). The
       merge result + source trace let you cite the WINNING source
       for any disputed value.
    3. Highlight values where two sources disagree and the override
       chain may surprise the user.

## free-form

  Use deploy:topology to ground; fs.list / fs.read to drill in. If
  after 4 tool calls you don't have a structured answer, return what
  you have with confidence "low".

# Cross-agent calls

  once-per-task to enrich a finding. Single-hop only.

# Failure modes

- IaC parser error on one file: include a finding noting the file +
  parser error; continue with siblings.
- fs-access denied on out-of-repo IaC root: stop further reads under
  that root; report partial finding noting the gap.
- Topology returned 0 services: the repo doesn't have IaC files in
  scope. Report "no IaC files found in <paths>" with confidence
  "high"; don't fabricate.
- Cross-agent tool returned TOOL_UNAVAILABLE: continue with topology-
  only finding + footer hint.

13. Cross-Agent Integration

The Deployment Analyzer is fully functional on its own. When the Code Analyzer and Data Analyzer are installed and enabled, this analyzer can call their read-only tools mid-task to enrich findings -- e.g. tie a service in the topology back to the source module that ships it (code:locate), or flag a connection string in a manifest as referencing a known DB connection (data:list-connections). When they're absent, the Deployment Analyzer falls back to topology-only findings and notes the missing enrichment.

Decision: Cross-agent enrichment uses the daemon's tool registry, not a new orchestration primitive. Single-hop only (cap depth at 1).

13.1 Available Cross-Agent Tools

Tool Owner When this analyzer would call it
code:locate Code Analyzer A topology task identifies auth-svc in the manifests; locate the source module that ships as that service (e.g. services/auth/main.go).
code:trace Code Analyzer A service-deps task finds an env-var JWT_SECRET; trace which code paths read it via process.env.JWT_SECRET.
data:list-connections Data Analyzer A service-deps task finds DATABASE_URL in a manifest; ask if that connection is registered with the data-driver and known to the Data Analyzer.
data:describe-table Data Analyzer An audit on a service that touches a DB; cross-link to the actual schema for the table it queries.

13.2 Single-Hop Depth Cap

Same contract as the other analyzers (§13.2): single-hop only. The crossAgentDepth counter prevents recursion.

13.3 Citation Propagation

Cross-agent results land in the report as a separate citation block tagged with the foreign agent. The synthesise step renders them in a Code findings (code-analyzer) or Schema findings (data-analyzer) subsection, never inline with deployment citations.

13.4 Graceful Fall-Through

If a cross-agent tool returns TOOL_UNAVAILABLE:

  • The analyzer continues with topology / manifest-only findings.
  • The orchestrator's review step categorises affected enrichment tasks as "external dependency missing".
  • The synthesise step emits a single line at the bottom of the report: "Consider running /code-analyze for richer service-to-source linkage" (or /data-analyze).

13.5 Flow 2 -- Plan-Level Delegation via deploy:analyze

Tool-call cross-agent (§13.1) is right when the calling agent needs a single targeted lookup -- "env-diff for DB_HOST", "topology for service X". When the calling agent has framed a multi-task investigation that's wholly inside this analyzer's domain, it dispatches via deploy:analyze: a single tool call that hands over a pre-built task list and gets back a synthesised report. 

// Tool surface registered by the Deployment Analyzer family
//
// Caller hands over an already-decomposed task list; the Deployment
// Analyzer skips its plan step (Flow 2 entry), runs the tasks (firing
// fs-access gates as needed), reviews each, synthesises a report on
// the local model, and returns the result inline.
{
  name: 'deploy:analyze',
  input: {
    tasks: DeployAnalysisTask[];   // pre-decomposed, no plan step
    callerContext?: {
      agent: 'code-analyzer' | 'data-analyzer' | string;
    };
  },
  output: {
    report:     string;            // Markdown, synthesised by the local LLM
    findings:   DeployFinding[];
    citations:  DeployCitation[];
    confidence: 'high' | 'medium' | 'low';
    truncated?: boolean;
    blockedTasks?: { itemId: string; reason: 'fs-access-denied'
                                          | 'parser-error' }[];
  },
}
Decision: Flow 2 is a single tool call from the caller's perspective. The Deployment Analyzer's run-task / review / synthesise loop runs to completion before the call returns. fs-access gates still fire -- the caller waits on them through the tool call, since the user is the right party to grant filesystem access in any case.

Why a separate tool from the per-capability ones (deploy:topology, deploy:env-diff, ...):

  • Different cost shape. A deploy:analyze call with a full-stack audit can take 60+ seconds across multiple parsers; deploy:env-diff is one name lookup.
  • Different return shape. Per-capability tools return raw topology / env / pipeline data; deploy:analyze returns a synthesised Markdown report with citations.
  • Topology cache amortises across tasks. A Flow 2 entry with multiple topology-dependent tasks builds the topology once; repeated per-capability calls would miss the cache across different invocations.
  • Single-hop cap still applies. Flow 2's tasks themselves can call cross-agent tools, but recursion is capped at depth 1 regardless of which entry flow opened the chain.

Caps inside Flow 2: 16/24 soft/hard cap as Flow 1. Lists > 16 trim silently. blockedTasks reports any tasks that hit fs-access-denied or parser-error paths so the caller can decide how to proceed.

Flow 2 has no present gate -- the caller folds the returned report into its own synthesise output as a "Deployment findings (deployment-analyzer)" subsection.

14. Caching & Resume

  • Topology cache (in-memory). Built once per analysis run by the first deploy:topology call; reused across subsequent tasks. Discarded at run completion.
  • Per-task cache (on-disk). Key = SHA256(task.question + normalized-scope + iac-tree-hash), where iac-tree-hash is a digest over the manifest files in scope. On a hit, the orchestrator skips the analyzer call and reuses the cached result. Cache lives under ~/.insrc/cache/deploy-analysis/, LRU at 200 entries.
  • Invalidation. iac-tree-hash recomputes lazily on next use; any modification under the IaC roots changes the hash and misses the cache. Manual deployAnalysis.clearCache command exposed.
  • Resume after daemon restart. Same as the other analyzers; topology cache is in-memory and rebuilds on resume.

  1. Phase 0 -- Family & orchestrator.
