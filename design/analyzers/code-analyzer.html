Code Analyzer Agent

Cloud-orchestrated, local-analyzed, read-only code understanding with a live analysis surface. One of three standalone analyzers (alongside Data Analyzer and Deployment Analyzer).

1. Overview

The Code Analyzer is a read-only agent that produces a structured, cited Markdown report answering a user's question about a codebase. It handles everything from focused questions ("where is UserService.refresh called from?") to broad audits ("summarise the auth flow and call out gaps"). It never writes code.

The analyzer is standalone in every regard -- its plan, run loop, review loop, synthesise, present gate, findings store, artifacts dir (docs/code-analysis/<slug>.md), REPL entry (/code-analyze), and tool registry are independent of the Data and Deployment analyzers. Removing one of the other analyzers does not affect this one. When all three are present, cross-agent enrichment via registered tools is opt-in (see §13); when not, the Code Analyzer produces best-effort findings with a "consider running the X analyzer" footer.

1.1 Two Entry Flows

The Code Analyzer accepts two entry shapes. Both share the same run-task / review / synthesise core; they differ only in whether the plan step is needed.

Decision: The synthesise step runs on the local LLM, not the cloud. The cloud is the heavy reasoner for plan + per-task review (where it sees minimal context per call); the local model writes the final Markdown report from accepted findings it already has in hand. Keeps cloud token cost focused on decisions, not prose generation.
Step Flow 1 -- direct user question Flow 2 -- tasks pre-decomposed (called from another agent)
Plan cloud LLM decomposes the user's request into AnalysisTask[] Skipped -- the caller hands over AnalysisTask[] directly
Run-task (per task) local LLM executes one task, calls read-only tools (graph / vector / fs / grep / cross-agent), emits a structured AnalyzerResult
Review (per task) cloud LLM reviews the analyzer output; decides accept / retry-with-hint / add-follow-up / done
Synthesise local LLM composes the final Markdown report from accepted findings + citations
Output Final report rendered in the Analysis Report Pane; present gate fires for save / copy / send-to-chat Final report returned to the caller as a structured { report, findings, citations, confidence } object; no present gate (caller decides what to do with it)

Flow 1 is what the user reaches via /code-analyze or the classifier's code-analysis intent. Cloud LLM does the up-front decomposition because the user's prompt is unstructured.

Flow 2 is what another agent reaches when it wants this analyzer to handle a specific scope it has already framed. The caller dispatches via the cross-agent code:analyze tool (see §13.5) with a prepared task list. The analyzer skips plan, runs the tasks, reviews each, synthesises, and returns the result inline -- the caller's run-task LLM gets a tool result back, just like any other cross-agent call. Single-hop depth cap still applies.

Internally the agent is two LLMs cooperating:

  • An Orchestrator on the active cloud provider decomposes the request into a task list, reviews each analyzer response, decides the next task, and finally assembles the full report.
  • An Analyzer on the local Ollama model answers one unit task at a time by querying Kuzu / LanceDB, reading relevant code, and returning a cited finding.

The agent rides on the session-scoped TODO framework (plans/todo-framework.md): the orchestrator's plan is a TodoList, each analyzer task is a TodoItem, and the existing todos editor pane + inline chat todos widget give the user live progress. A dedicated Analysis Report Pane renders the final synthesised Markdown and lets the user highlight a section and send it back to the chat panel as a quoted follow-up.

2. Goals & Non-Goals

Goals

  • Decomposed analysis. Break a broad request into focused sub-questions so the local model never has to carry the whole problem at once.
  • Cited answers. Every finding names a file / line range / entity id that came from the graph or vector store, not free-text speculation.
  • Local-heavy, cloud-thin. Analyzer work (which reads a lot of code and does most of the token consumption) runs locally. Cloud is used for planning and final synthesis only.
  • Progress-visible. User sees the plan, sees tasks complete one by one in the Analysis Pane, and can steer (add a task, edit the plan, ask a follow-up) mid-flight.
  • Resumable. Crash / VS Code restart / model switch mid-analysis preserves completed analyzer results.

Non-Goals

  • Code changes. The analyzer never emits diffs. If a finding implies a fix, the user moves it to the coding agent separately.
  • Unbounded autonomy. The orchestrator runs a capped number of iterations; we do not let a cloud LLM chase its own findings indefinitely.
  • Web / external research. That's the Research controller's job. Code analyzer scope is the active repo + its dependency closure.
  • Multi-repo federation. Only the active repo graph and its transitive DEPENDS_ON closure are in scope (architectural rule #3 in CLAUDE.md).

3. Family & Variant

Decision: The Code Analyzer is its own family (code-analyzer), not a variant of research. The Data Analyzer (data-analyzer) and Deployment Analyzer (deployment-analyzer) are sibling families. Each family owns its own registry row, slash command (/code-analyze), TODO ownership stamp, prompt assets, artifacts directory, and read-only tool surface. None depends on the others at runtime.

Why three sibling families instead of one umbrella with variants:

  • Standalone in every regard. Removing one analyzer is a code-tree change that doesn't touch the others. The user can disable any one of the three via insrc.analyzers.enabled without breaking the survivors.
  • Disjoint tool surfaces. Code wants graph / vector / fs / grep; Data wants DB drivers; Deployment wants IaC parsers. Hosting them under one family forces a lowest-common-denominator tool registry; three families let each carry the right closed set for its domain.
  • Disjoint citation shapes. Code citations are (path, lineRange, snippet); Data citations are (connection, table, column [, queryResult]); Deployment citations are (manifestFile, resourceKind, envOverlay). A shared family would muddle citation rendering in the Analysis Report Pane.
  • Independent plan budgets. Each family carries its own 16/24 soft/hard task cap independent of the others, so cross-agent fan-out doesn't share a token budget across analyzers (see §6.3).

The existing ResearchController (free-form web-capable investigation) stays as the research family it always was; the legacy CodeAnalysisController hosted under research is deprecated and removed alongside the cleanup tracked in §4.4. After cleanup, research covers free-form investigation only and the three analyzer families cover code / data / deployment cleanly.

Prompt assets live in ~/.insrc/code-analyzer/ for this agent (siblings: ~/.insrc/data-analyzer/, ~/.insrc/deployment-analyzer/). Each directory carries the family's plan.md, review.md, analyzer.md, synthesise.md prompts.

4.2 TODO Framework as Backbone

The TODO framework (plans/todo-framework.md) is load-bearing: it owns plan storage, item state machines, persistence (LanceDB tables), live event streams (listCreated, itemCreated, itemUpdated, ...), the comment channel for user feedback, and the editor pane + inline chat widget that render all of this. The analyzer controller leans on deps.todos for everything except LLM task execution and final-report rendering.

What we do NOT build: our own task state machine, our own plan persistence, our own live-progress pane, our own per-task comment storage. Every one of those already exists as framework infrastructure. Reinventing any of them duplicates code and drifts from the canonical UX agents share.

4.3 Relation to Brainstorm

The code analyzer adopts the brainstorm controller pattern end to end:

  • Controller shape. Implements the same TaskController interface (buildInitialTasks / next / finalize) used by BrainstormControllerBase.
  • Task kinds. Uses the same kind: 'llm' | 'rpc' | 'gate' envelope so the daemon's runControlledPipeline drives it without modification.
  • Pane pattern. Dedicated AnalysisPaneInput + AnalysisPane extending InsrcEditorPaneBase, rendered through a reusable AnalysisCardWidget modelled on BrainstormCardWidget.
  • Gate semantics. replyToGate(gateId, action, feedback) ferries plan edits and per-finding comments back to the controller, exactly like brainstorm's discuss / diverge / edit actions.

The one place the analyzer diverges from brainstorm: there is no "ideation round → convergence" loop. Analysis tasks are a flat queue and the orchestrator is free to append to it at any review step. This maps closer to brainstorm's per-theme spec queue (specThemeQueue / nextThemeSpec) than to its idea generation loop.

4.4 Relation to Existing Controller

Decision: The legacy CodeAnalysisController (src/insrc/daemon/controllers/code-analysis.ts) is deprecated and scheduled for removal. It ships as the default until the new orchestrator/analyzer pipeline is stable in phase 1, then is deleted in the phase-2 cleanup. No settings toggle, no "quick mode" kept around — we do not want two overlapping code-analysis pipelines long term.

Assets we port out of the legacy controller before deletion:

  • The Finding / FindingSeverity / CodeAnalysisConcern types in src/insrc/agent/tasks/code-analysis/types.ts — extended with an explicit citations: CodeCitation[] field and moved to the new module layout.
  • parseReport / formatReport in the existing controller — ported verbatim as the finding-formatting primitives the orchestrator calls during synthesis.
  • The existing draft / review prompts in src/insrc/agent/tasks/code-analysis/prompts.ts — cannibalised into the new planning / review / analyzer prompts; the originals are deleted alongside the controller.

Once the new pipeline is the default, the classifier's code-analysis intent routes straight to the orchestrator controller and the old file is removed in the same PR.

5. TODO Framework Integration

5.1 List & Item Shape

One TodoList is created per analysis run. The meta bag on each TodoItem carries the analyzer-specific payload without extending the framework schema: 

// The list created on Orchestrator.plan
const list: TodoList = {
  id:          ulid(),
  sessionId,
  owner:       'research',              // stamped by deps.todos
  source:      'research',
  status:      'active',
  title:       'Code Analysis: ',
  description: userRequest,             // full original ask
  body:        undefined,               // set by synthesise() to the final MD
  transfers:   [],
  items:       [ /* one per task */ ],
  // parentListId: only set for sub-analyses spawned via follow-up-as-sub-list
};

// Each item's meta keeps the per-task payload
interface AnalysisItemMeta {
  kind:        'locate' | 'describe' | 'trace'
             | 'compare' | 'inspect-schema' | 'free-form';
  scope?:      { entityIds?: string[]; paths?: string[]; packages?: string[] };
  origin:      'plan' | 'follow-up';
  retryCount:  number;
  hint?:       string;                // last retryHint, if any

  // populated on completion
  answer?:     string;
  findings?:   Finding[];
  citations?:  CodeCitation[];
  confidence?: 'high' | 'medium' | 'low';
  toolCalls?:  ToolCallSummary[];
  truncated?:  boolean;
}

TodoItem.title is the short task label shown on the todos pane row (e.g. "Trace callers of verifyToken()"); TodoItem.description is the full question the analyzer receives.

5.2 Item Lifecycle

Proposed framework addition: the existing TodosApi surfaces markInProgress / markComplete / markBlocked but no cancel or generic updateItem(meta). The analyzer needs both: updateItem to stash per-task payload on completion, and cancel for maxTasks-cap truncation. See §15 Q7 — this is a framework PR we bundle with phase 1.

5.3 Feedback Channel: Batched Annotations → Chat

Decision: User feedback on an analysis does not flow into the current run via framework comments. Instead, the user annotates sections on the Analysis Report Pane, accumulates multiple annotations, and sends the batch as a single chat message. That chat message kicks off whatever new turn the user wants (a follow-up analysis, a coding task, a question). The current analysis run never waits for user input.

Why not use the framework's per-item comment channel here:

  • One channel, not two. Splitting feedback between "comments on todo items" and "send section to chat" fragments the user's mental model. Keeping all feedback as chat messages means the user always knows where their words go.
  • Annotation across sections. Analysis feedback often needs to reference several findings at once ("points #2 and #5 contradict each other"). Framework comments are per-item; a single chat message can quote multiple annotations.
  • Keeps the analyzer run linear. The orchestrator doesn't need to poll for comments, the reviewer prompt doesn't need an "unacked comments" section, and retries don't fork on mid-flight user input.

What the framework's comment infrastructure IS still used for: nothing on code-analysis lists. The todos pane renders code-analysis lists read-only without the + Add comment affordance — the pane suppresses the comment row for lists with meta.suppressComments: true (a small extension to the pane's list widget). All feedback lives on the Analysis Report Pane.

Annotation + batch semantics are specified in §10.3 (Feedback Paths).

5.4 Hierarchy & Follow-Ups

Two hierarchy patterns the analyzer uses:

  1. Flat follow-ups (default). add-follow-up reviewer decisions call deps.todos.addItem on the same list, with meta.origin = 'follow-up' so the pane can badge them. This keeps scroll-back linear.
  2. Scoped sub-list (when a follow-up explodes into ≥ 3 tasks). The orchestrator creates a child list via deps.todos.createList({ parentListId: rootListId, ... }) and seeds it with the batch. The pane renders root + child as sibling flat cards with ↑ parent: / ↓ children: cross-reference links, same as brainstorm's per-theme spec breakout.

Sub-list spawning is the mechanism for a user's "drill into finding #3" ask: a comment on finding #3 triggers the reviewer to spawn a child list focused on that area.

6. Orchestrator

6.1 Step Flow

plan (cloud LLM, no tools) | -> deps.todos.createList(...) + addItem() per task | -> todos pane + inline chat widget auto-open showing the plan v plan-size check | +-- |plan| <= 16 --> auto-proceed (read-only, no gate) +-- |plan| > 16 --> [plan-size-approval] gate | approve -> proceed with full plan | trim-to-16 -> drop tail, keep first 16 | cancel -> abort run v run-task (one task at a time) | -> markInProgress(itemId) before analyzer.run() v review-finding (cloud LLM, no tools) | +-- accept --> updateItem(meta); markComplete(itemId); advance +-- retry --> updateItem(meta.retryCount++, meta.hint); keep in_progress +-- add-follow-up --> addItem(..., meta.origin = 'follow-up'); advance +-- done --> cancel remaining pending items; jump to synthesise v (loop until list has no pending items OR caps hit; user may click "Stop analysis" on the pane to fire mid-flight-cancel gate) v synthesise (cloud LLM, no tools -- composes report) | -> updateList(body = markdown) v AnalysisReportPane opens with the rendered markdown v present gate (save / copy / send-to-chat / discard) | -> on save: artifact-save to docs/analysis/<slug>.md | -> on discard: list.transfer('system') for audit retention
Decision: Plans with ≤ 16 tasks auto-approve. Read-only work doesn't warrant blocking on approval. Plans > 16 tasks raise a plan-size-approval gate — a plan that big usually means the decomposition went wider than the user expected, and we want a chance to trim before paying the cloud-token cost of that many review steps. The user sees the plan appear live in the todos pane and inline chat widget either way, and can steer via the Stop analysis button mid-flight.
Step Kind Description
plan llm Produces AnalysisTask[] from the user request + active-repo context summary (repo name, top-level packages, search hint). No tool calls. On success, creates the TodoList and seeds one TodoItem per task. Token budget ~1500.
plan-size-approval gate Conditional. Fires only when the plan has > 16 tasks. Actions: approve (run all), trim-to-16 (drop the tail and run the first 16 — remaining items are marked cancelled), cancel (abort the run, list → system).
run-task[i] rpc Invokes the Analyzer sub-pipeline (§7). Marks the current item in_progress first, then stores the AnalyzerResult on item.meta.
review-finding[i] llm Cloud LLM reads the analyzer output + accumulated cumulative context and decides one of: accept, retry-with-hint, add-follow-up, done. Structured JSON output. Does not consult user comments (feedback flows through chat, §5.3).
mid-flight-cancel gate Optional. Emitted only when the user clicks "Stop analysis" on the todos pane or the Analysis Report Pane. Actions: cancel (drop remaining pending items and jump to synthesise with what we have), abort (discard entirely — list.transfer('system')).
synthesise llm Composes the final Markdown on the local model: merges accepted findings, groups by concern, preserves all citations, writes the top-level summary. Token budget ~4000. Writes to list.body on Flow 1; returns the structured result to the caller on Flow 2 (see §13.5). Local-only synthesis keeps cloud cost focused on the per-task review decisions.
present gate Final gate. Actions: save (to docs/analysis/<slug>.md via artifact-save.ts), copy, send-to-chat, discard.

6.2 Decision Loop

After each analyzer task completes, review-finding returns a decision record: 

{
  "decision": "accept" | "retry-with-hint" | "add-follow-up" | "done",
  "rationale": "one-line reason",
  "retryHint"?: "string (only if retry-with-hint)",
  "followUps"?: [ { "question": "...", "scope": "..." } ]   // 0..2 items
}

Interpretation:

  • accept — updateItem(meta = <AnalyzerResult>) then markComplete(itemId). Advance to next pending item.
  • retry-with-hint — re-queue the same item with updateItem(meta.retryCount++, meta.hint = retryHint) (e.g. "focus on the callers in payments/, not tests"). Item stays in_progress. Per-task retry counter caps at 2; if exceeded, accept-with-confidence: 'low'.
  • add-follow-up — addItem() on the current list with meta.origin = 'follow-up' for each of 1–2 follow-up questions. The todos pane auto-renders the new rows via the framework's itemCreated event.
  • done — cancel remaining pending items via cancel(itemId, 'reviewer marked analysis complete'); jump to synthesise.

6.3 Termination

Termination conditions, whichever fires first:

  1. Plan queue is empty and no pending follow-ups.
  2. Reviewer decides done.
  3. Soft cap at 16 tasks. Initial plans > 16 trigger the plan-size-approval gate (§9); follow-ups that push total planned tasks past 16 are silently capped — further add-follow-up decisions are dropped with a follow-ups-skipped note on the offending item.
  4. Hard caps: maxTasks = 24 (absolute ceiling even after plan-size-approval) and maxFollowUps = 8. When either is hit, remaining tasks are cancelled and a truncated: true marker is set on the final report.
The caps exist because cloud-provider token costs scale with the review step running on every analyzer result. An analyzer result is typically 200–800 tokens plus evidence; 16 reviews at 2k input tokens each is already ~32k tokens for a single analysis. The soft cap + approval gate gives the user a chance to trim before paying for a wider-than-expected decomposition; the hard cap is a backstop against runaway follow-ups.

6.4 Prompts

Three prompts, all in src/insrc/agent/tasks/code-analysis/prompts.ts:

  • buildOrchestratorPlanPrompt(request, repoSummary, concerns) — produces AnalysisTask[] as strict JSON.
  • buildOrchestratorReviewPrompt(task, result, accumulatedFindings) — produces the decision record above.
  • buildOrchestratorSynthesisPrompt(request, findings, plan) — produces the final Markdown report.

7. Analyzer

7.1 Task Contract

The analyzer is invoked by the orchestrator per TodoItem. The orchestrator reconstructs an AnalysisTask from item.title + item.description + item.meta and calls analyzer.run(task, state). One task, one structured result. 

interface AnalysisTask {
  itemId: string;                    // TodoItem.id -- analyzer never invents ids
  kind:                              // from item.meta.kind
    | 'locate'                       // find entities matching a description
    | 'describe'                     // summarise an entity / file / package
    | 'trace'                        // trace callers / callees / data flow
    | 'compare'                      // two entities, two versions, two impls
    | 'free-form';                   // fallback (cross-agent calls -- see §13 -- happen as
                                     //  tool calls inside any kind, not as a distinct task kind)
  question: string;                  // from item.description
  scope?: {
    entityIds?: string[];
    paths?: string[];
    packages?: string[];
  };
  hint?: string;                     // from item.meta.hint on retries
  origin: 'plan' | 'follow-up';      // from item.meta.origin
  retryCount: number;                // from item.meta.retryCount
}

interface AnalyzerResult {
  itemId: string;                    // matches task.itemId
  answer: string;                    // concise prose, 1-3 paragraphs
  findings: Finding[];               // 0..N structured items
  citations: CodeCitation[];         // every claim must tie back here
  confidence: 'high' | 'medium' | 'low';
  toolCalls: ToolCallSummary[];      // for trace logs / debugging
  truncated?: boolean;               // analyzer hit its own budget
}

interface CodeCitation {
  entityId?: string;                 // if graph-resolved
  path: string;
  lineStart?: number;
  lineEnd?: number;
  snippet?: string;                  // ≤ 200 chars
}

7.2 Read-Only Tools

The analyzer is given a closed tool set. The tool registry rejects anything outside this list even if the local model hallucinates a name.

Tool Purpose Notes
graph.search Kuzu lookup by name / kind / relation Already exposed via daemon RPC. Results capped at 50 entities.
graph.neighbours Given entityId, return CALLS / IMPORTS / EXTENDS neighbours Bounded traversal depth (default 2).
vector.search LanceDB ANN lookup for semantic matches Returns entityId + cosine score.
text.grep ripgrep over target paths Result cap 200 lines. Out-of-repo paths trigger the access gate (see below).
fs.read Read a file or byte range Max 512 KB per call, max 2 MB cumulative per task. Out-of-repo paths trigger the access gate.
fs.list List directory children Out-of-repo paths trigger the access gate.
entity.summary Canonical entity summary from the daemon context builder Prefer over raw fs.read when the entity id is known.
data:* / deploy:* Cross-agent read-only enrichment (see §13) Available only when the Data / Deployment analyzers are installed and enabled. Single-hop depth cap; missing target returns the TOOL_UNAVAILABLE sentinel.

Explicitly excluded: shell exec, file writes, network fetch, git mutation, any tool that mutates state in any of the three analyzer domains.

7.3 Scope & Out-of-Repo Access Gate

Decision: Scope is not pre-constrained to the dependency closure. The analyzer may traverse to any path it decides is relevant, including paths outside the active repo. Approval is requested per parent directory: the analyzer names the directory under which it expects to read, and once granted, every file under that directory (recursively) is approved for the rest of the session.

Gate mechanics:

  • The daemon tracks an approved-directory set per session. The active repo root and every directory under it are implicitly approved.
  • Analyzer requests at directory granularity, not file granularity. When the analyzer wants to read /home/user/other-repo/src/foo.ts, the tool call carries { grant_path: '/home/user/other-repo', reason: '...' }. The prompt contract teaches the model to pick the narrowest parent that plausibly covers the reads it intends to do — usually a repo root, sometimes a sub-package.
  • If grant_path or any of its ancestors is already in the approved set, the call proceeds without a gate.
  • Otherwise the daemon suspends the tool call and fires a fs-access gate on the chat panel / todos pane naming the requesting item, the directory, and the analyzer's reason.
  • Actions:
    • approve — adds grant_path (and recursively all descendants) to the approved set for this session.
    • approve-broader (with a prompted parent path) — user escalates the grant to a higher ancestor, useful when they can tell the analyzer will need several sub-directories of a larger tree.
    • deny — analyzer gets PermissionDenied and continues with what it has.
  • Because approvals cascade to descendants, the expected case is one gate per out-of-repo root, not one per file or per sub-dir. The open question about batching co-temporal gates is moot — parent-grant semantics replace the batching need.
  • Approvals are session-scoped and not persisted across sessions. A new chat session re-asks.

Why session-scoped and not persistent: an approval persisted to disk is an easy path to accidental exfiltration a user wouldn't notice (e.g. an agent in a later session silently reading ~/work/other-client-repo/ because an earlier session approved it). Asking again per session is a small tax for a meaningful audit property.

The gate blocks the tool call synchronously. While waiting for the user, the todo item stays in_progress and the todos pane shows a ⏸ waiting for directory approval sub-row. If the user dismisses VS Code without answering, the gate times out after 5 minutes and defaults to deny; the analyzer continues with what it has.

7.4 Tool Loop

Each analyzer task runs a bounded tool-calling loop on the local model:

  1. System prompt is prepended with /no_think (required for qwen3-coder structured tool calls — CLAUDE.md note).
  2. User message contains the task JSON + any hint + the first-pass entity candidates retrieved from vector.search on task.question.
  3. Model emits tool calls; daemon executes them; results fed back.
  4. Loop terminates on: model emits a final answer, hard cap of 8 tool calls, or 60 s wall clock.
  5. Final model turn produces the AnalyzerResult JSON.

Implementation reuses the existing investigate-style tool loop (the daemon's tool registry + executor + validator) — we add an AnalyzerToolContext wrapper that enforces the closed tool list and token caps.

7.5 Citations

Invariant: every claim in answer or every Finding must resolve to at least one CodeCitation. The analyzer's output JSON is rejected and retried (once) if any finding has citations.length === 0. After the retry, a missing-citation result is accepted but auto-downgraded to confidence: 'low'.

Citations feed back into the orchestrator's synthesis step, which preserves every unique (path, lineStart, lineEnd) tuple as a clickable link in the Markdown output.

8. Controller State

With the TODO framework owning the plan, item lifecycles, persistence, and comments, the controller's own state shrinks to the pieces the framework doesn't model: 

interface CodeAnalysisState {
  request:     string;                 // original user message, for prompt rehydration
  repoSummary: RepoSummary;            // cached repo context the planner used

  listId:      string;                 // primary TodoList id -- source of truth for plan/progress
  childListIds: string[];              // any sub-lists spawned for large follow-up batches

  currentItemId?: string;              // the item in_progress right now
  truncated:    boolean;               // set when maxTasks / maxFollowUps cap hit
  cancelled:    boolean;               // set when user issued mid-flight cancel

  // Access-gate state (§7.3). Session-scoped, not persisted across sessions.
  approvedDirs: string[];              // absolute paths approved for this session

  // Final report -- also mirrored to `list.body` for the framework's view.
  finalReport?: string;
  reportUri?:   string;                // URI of the ephemeral AnalysisReportPane tab
  presentedAt?: number;
}

Items, comments, follow-ups, transfer history, and inline chat rendering all live in the framework. The controller never keeps a parallel copy.

Persistence: the shrunken state goes through the same TaskStateStore the brainstorm controllers use. Resume on daemon restart rehydrates listId + loads the list from the framework's LanceDB tables; any in-flight item is reset from in_progress to pending and re-executed.

9. Gates

Gate id Phase Actions Trigger
plan-size-approval planning approve (run all), trim-to-16 (keep first 16, cancel rest), cancel (abort) Fires only when |plan| > 16 after plan completes. Default after 5-min timeout = cancel.
fs-access execution approve (grant the requested parent dir, recursive), approve-broader (user picks a higher ancestor), deny Fires on first read under any out-of-repo directory not yet covered by an existing grant. Cascades recursively, so usually one gate per out-of-repo root. Default after 5-min timeout = deny.
mid-flight-cancel (optional) execution cancel (jump to synthesise with current findings), abort (discard run entirely) Emitted only when the user clicks Stop analysis.
present finalize save (path), copy, send-to-chat (with optional selection), discard Always, once synthesise completes.
Plans ≤ 16 tasks auto-proceed. Read-only work with a modestly sized plan doesn't need an approval click. The plan-size gate only fires when decomposition produces a plan big enough to be worth paying attention to.

Comments on tasks do not fire a gate — they flow through the framework's comment channel (§5.3) and are consumed by the reviewer at the top of its next turn.

10. UI Surfaces

Two surfaces cooperate — one reused, one new:

  1. Todos editor pane + inline chat todos widget (reused) — render the live plan and per-task progress as the orchestrator runs.
  2. Analysis Report Pane (new, ephemeral) — renders the final synthesised Markdown and hosts the annotate-and-batch-send-to-chat feedback flow.
Only one analysis at a time. A session may have only one active code-analysis run. Starting a new analysis while one is already running is rejected with a user-visible notification "an analysis is in progress — cancel it first". Consequences: the Analysis Report Pane is a single editor tab (not one-per-analysis), and the controller tracks a session-level activeAnalysisListId.

10.1 Todos Pane & Inline Chat Widget

These are the existing framework surfaces (plans/todo-framework.md Phase 5a/5b). No new code beyond registering code-analysis lists as consumers. From the user's perspective:

  • When plan completes, a listCreated event fires with suggestOpenUI: true. The todos pane auto-opens (if not already open) focused on the new list; the inline chat widget renders a card in the current chat session.
  • As tasks flip pending → in_progress → completed, both surfaces update in place via itemUpdated events. No polling.
  • Each item row shows: status icon, short title, origin badge (plan vs follow-up), confidence badge (once completed), and a compact citation count. Expanding an item reveals the full question, the analyzer's prose answer, and the citation list with clickable file links.
  • Lists are read-only in the pane — no add-comment affordance (suppressed for code-analysis lists, §5.3), no edit, no reorder. The kebab menu still offers copy-as-markdown and view-transfer-history.

Inline widget suppression rules: once synthesise completes, the inline card auto- collapses to a one-line header with a Open report action that focuses the Analysis Report Pane.

10.2 Analysis Report Pane

Ephemeral per session. The Analysis Report Pane does not persist across workbench reloads. Closing or reloading the window discards the pane; the report content is still preserved on TodoList.body and can be re-rendered by reopening the pane from the todos-pane Open report action. Save-to-file (via present gate) is the persistence path users take if they want the report durable.

10.3 Feedback Paths

One affordance: select a region, annotate, keep annotating, batch-send. Implementation:

  1. User selects any prose span (heading, paragraph, bullet, finding row) on the report pane. A floating Annotate button appears anchored to the selection, plus Quote to chat now for one-shot sends.
  2. Clicking Annotate opens a small composer (same widget pattern as brainstorm's input panel) with the selected text pre-quoted above the textbox. User writes a comment; Save adds the annotation to the pane's pending-annotations list. The selection receives a 🔖 marker inline.
  3. The status bar at the bottom of the pane shows Pending annotations: N and the actions Send all to chat and Clear annotations. Send all to chat becomes active when N >= 1.
  4. Clicking Send all to chat composes a single chat message and posts it via chatService.submit(message, { from: 'code-analysis-pane' }): 
    > From Code Analysis: <request slug>
>
> [1] auth entry points:
>   > src/http/auth.ts:42 -- ...
>   is this still used?
>
> [2] auth entry points:
>   > src/http/legacyAuth.ts:18 -- ...
>   bypass must go
>
> [3] SessionStore interface:
>   > (selected span quoted here)
>   look at cache layer too
    The pane then clears its pending-annotations list (kept annotations persist until the next Send, not across window reloads).
  5. The chat message enters the chat panel as a normal user turn. The classifier treats it like any message and routes appropriately — usually a follow-up analysis, sometimes a coding task, sometimes a question. The in-flight analysis run (if any) is not interrupted; if the user wants to stop the current analysis first they use the Stop analysis control on the todos pane.

Quote to chat now is the shortcut path: one-click send of the selected span as a quoted chat message, no annotation composer. Useful when the user doesn't want to wait-and-batch.

Annotations are stored on the pane instance's DOM state, not on the framework or on disk. A window reload loses any unsent annotations — by design, because we don't want stale annotations from a prior session coming back to haunt a later Send to chat.

11. Intent Routing

Two orthogonal entry points, both resolving to this controller:

  • Explicit slash command: /code-analyze <prompt>. Bypasses the classifier; the request goes directly to the Code Analyzer family. This is the primary surface, mirroring /data-analyze and /deploy-analyze for the sibling analyzers.
  • Classifier intent: the code-analysis intent in the classifier remains for free-form chat ("trace the auth flow"); it routes to the same controller. The classifier never disambiguates between code / data / deployment intents on a free-form prompt -- it picks the most likely fit by content, and the user reaches for the explicit slash command when they want a specific analyzer.

Once phase 2 stabilises and the deprecated controller is deleted (§4.4), nothing in intent routing mentions the legacy pipeline.

13. Cross-Agent Integration

The Code Analyzer is fully functional on its own. When the Data Analyzer (data-analyzer family) and Deployment Analyzer (deployment-analyzer family) are installed and enabled, this analyzer can call their read-only tools mid-task to enrich findings -- e.g. confirm that a db.query("SELECT * FROM users") call references a real users table, or that a process.env.DB_HOST reference resolves to a known deployment env-var. When they're absent, the Code Analyzer reports best-effort findings with a "Consider running /data-analyze for richer schema findings" footer line.

Decision: Cross-agent enrichment uses the daemon's tool registry, not a new orchestration primitive. Each sibling analyzer registers its read-only capabilities as tools (data:describe-table, deploy:topology, ...); this analyzer's run-task LLM sees them in the tool list and decides when to call them. No sub-pipeline, no recursive plan-decomposition, no shared in-memory state.

13.1 Available Cross-Agent Tools

When the sibling analyzers are present, these tools become callable from the Code Analyzer's run-task loop alongside its native graph.* / fs.* / vector.* / text.grep tools:

Tool Owner When this analyzer would call it
data:list-connections Data Analyzer Discover what DB connections are registered before deciding whether to ask schema questions.
data:describe-table Data Analyzer A trace task finds db.query("...users..."); calls data:describe-table to confirm the columns the code accesses exist + match types.
data:lineage Data Analyzer A describe task on a function that emits queries; lineage adds "reads from orders, users" + which other code paths share the same table.
data:schema-drift Data Analyzer A compare task between code's expected shape and live DB state -- surfaces columns the code uses that no longer exist in the DB.
deploy:env-diff Deployment Analyzer A trace task finds process.env.DB_HOST; env-diff shows how that var is set across dev / staging / prod overlays.
deploy:service-deps Deployment Analyzer A broad audit task asks "what depends on this module"; service-deps adds the deployment- level dependents (other services that pull this one as a peer).

13.2 Single-Hop Depth Cap

Decision: Cross-agent calls are single-hop. When the Code Analyzer calls data:describe-table, the Data Analyzer's tool can in turn call Code Analyzer tools internally for its own work, but it cannot call deploy:* from within the Code-initiated call. Depth is enforced by a crossAgentDepth counter in the run-task tool context; tools detect depth >= 1 and return the TOOL_UNAVAILABLE sentinel.

Why cap at 1: keeps the latency budget bounded (each cross-agent call adds a tool round-trip + a domain-specific lookup), keeps citation density manageable, and prevents accidental recursion when two analyzers register overlapping tool patterns. The cap can be raised later with explicit token + latency budgets if real-world usage shows benefit from chains.

13.3 Citation Propagation

Cross-agent results land in this analyzer's report as a separate citation block tagged with the foreign agent. The synthesise step renders them in a "Schema findings" or "Deployment findings" subsection, never inline with code citations. The reader can tell at a glance which findings came from which analyzer. 

// Excerpt from a synthesised report including foreign citations
## Auth flow

The token-refresh path is gated through `verifyToken()` in
[`src/auth/token.ts:42-58`](path:src/auth/token.ts#L42-L58)...

### Schema findings (data-analyzer)

* `users.refresh_token_hash` is the column the code reads
  [(connection: `primary`, table: `users`, column: `refresh_token_hash`)](data-cite:1).

### Deployment findings (deployment-analyzer)

* `JWT_SECRET` resolves to a `secretRef` named `auth-jwt` in dev/staging,
  but is unset in the prod overlay [(manifest: `k8s/prod/auth.yaml`,
  resource: `Deployment/auth`)](deploy-cite:1).

13.4 Graceful Fall-Through

If a cross-agent tool returns TOOL_UNAVAILABLE (target analyzer's tools aren't registered, e.g. user disabled it in insrc.analyzers.enabled):

  • The analyzer's run-task LLM sees the structured unavailable response and continues with whatever signal it can produce on its own.
  • The orchestrator's review step categorises the affected task as "external dependency missing" -- still acceptable, just with reduced confidence.
  • The synthesise step emits a single line at the bottom of the report: "Consider running /data-analyze for richer schema findings" (or the equivalent for deployment). No hard failure.

Same fall-through applies when the target analyzer's daemon-side handler errors or times out (5 s hard cap on cross-agent tool calls). The original analysis run never blocks on a sibling.

13.5 Flow 2 -- Plan-Level Delegation via code:analyze

Tool-call cross-agent (§13.1) is right when the calling agent needs a single targeted lookup -- "describe table X", "is this image vulnerable". When the calling agent has framed a multi-task investigation that's wholly inside this analyzer's domain, it dispatches via code:analyze: a single tool call that hands over a pre-built task list and gets back a synthesised report. 

// Tool surface registered by the Code Analyzer family
//
// Caller hands over an already-decomposed task list; the Code Analyzer
// skips its plan step (Flow 2 entry), runs the tasks, reviews each,
// synthesises a report on the local model, and returns the result inline.
{
  name: 'code:analyze',
  input: {
    tasks: AnalysisTask[];     // pre-decomposed, no plan step
    callerContext?: {
      agent: 'data-analyzer' | 'deployment-analyzer' | string;
      // optional, for citation labelling in the synthesised report
    };
  },
  output: {
    report:     string;        // Markdown, synthesised by the local LLM
    findings:   Finding[];     // accepted findings across all tasks
    citations:  CodeCitation[];
    confidence: 'high' | 'medium' | 'low';
    truncated?: boolean;       // if any cap was hit
  },
}
Decision: Flow 2 is a single tool call from the caller's perspective. The Code Analyzer's run-task / review / synthesise loop runs to completion before the call returns; there's no streaming partial findings back. This keeps the cross-agent contract symmetric with every other tool (one input, one output) and avoids interleaving two analyzers' progress in a single chat session.

Why a separate tool from the per-capability ones (code:locate, code:trace, ...):

  • Different cost shape. A code:analyze call can take 30 seconds and dozens of internal tool calls, where code:trace is a single graph traversal. Surfacing them as separate tools lets the caller's planner reason about cost.
  • Different return shape. Per-capability tools return raw entity / range data; code:analyze returns a synthesised Markdown report with citations. Both have their place; the caller picks based on what it needs.
  • Single-hop cap still applies. Flow 2's tasks themselves can call cross-agent tools (e.g. a Code Analyzer task calling data:describe-table), but recursion is capped at depth 1 regardless of which entry flow opened the chain.

Caps inside Flow 2: the caller-supplied task list is subject to the same 16/24 soft/hard cap as Flow 1. Lists > 16 don't fire the plan-size-approval gate (no user is in the loop) -- the Code Analyzer trims to 16 silently and sets truncated: true in the return value. The caller's review step sees the truncation and can decide whether to re-dispatch the dropped tasks in a follow-up call.

Flow 2 has no present gate -- the caller is responsible for what to do with the returned report. Typically the caller's synthesise step folds these foreign findings into its own report under a "Code findings (code-analyzer)" subsection, the same shape as §13.3's tool-call citations.

14. Caching & Resume

  • Per-task cache. Key = SHA256(task.question + normalized-scope + repo-rev). On a hit, the orchestrator skips the analyzer call and reuses the cached AnalyzerResult (updateItem(meta = cached) then markComplete). Cache lives under ~/.insrc/cache/code-analysis/, LRU-evicted at 200 entries.
  • Invalidation. Repo revision is taken from the indexer's last "repo snapshot id". On re-index, entries simply miss on the new rev — no active purge. A manual codeAnalysis.clearCache command is exposed.
  • Resume after daemon restart. The controller's TaskStateStore retains listId; on resume, the framework's LanceDB tables rehydrate the list and items. Any item marked in_progress at crash time is reset to pending and re-executed on resume. The Analysis Report Pane is ephemeral (§10.2) — if the run finished before crash, the user can reopen it from the todos-pane Open report action, which reads list.body.

15. Failure Modes

Failure Handling
Cloud provider unavailable (auth / network) plan + per-task review fall back to the local model with a warning banner in the todos pane and Analysis Report Pane. synthesise already runs local by default so it's unaffected. Final report is flagged provenance: 'local-only'.
Analyzer produces malformed JSON One retry with a strict-JSON reminder. On second failure, accept the answer as-is with confidence: 'low' and no structured findings; markComplete with a meta.warning string.
Analyzer cites a file that has since moved Daemon path-resolves against the current repo tree. Unresolved citations are kept in the report but annotated (file not found — possibly renamed).
Analyzer tool call returns empty Analyzer widens scope via graph.search before giving up; if still empty, the result reports confidence: 'low' with an explicit "no evidence found" answer.
User closes the todos pane or Analysis Report Pane mid-run Pipeline continues in the background. The inline chat widget still receives updates; a completion toast surfaces when synthesise finishes, with a Open report action to reopen the (ephemeral) report pane.
User closes VS Code mid-run Daemon keeps running; the controller's state (including listId) is persisted. On next open the todos pane auto-restores the list; if synthesise never completed, the orchestrator picks up from the last pending item.
Orchestrator reviewer keeps saying retry-with-hint Per-task retry cap = 2. Plan-level maxTasks cap = 20.
User starts a second analysis while one is running Rejected at plan step with a notification "an analysis is in progress — cancel or wait" (§10 single-pane invariant). The new request is NOT auto-queued.
User dismisses the fs-access gate by closing VS Code Gate times out after 5 min → deny. Analyzer receives a PermissionDenied error for that path and continues without it.

16. Phasing

  1. Phase 0 — Framework additions.
    • Extend TodosApi with updateItem(itemId, { meta }) and cancel(itemId, reason) (proposed in §5.2).
    • Extend todosListWidget to honour list.meta.suppressComments: true (suppresses the + Add comment affordance).
  2. Phase 1 — Core loop.
    • New CodeAnalysisOrchestratorController wired under the research family, variant code-analysis.
    • Analyzer tool loop using the existing tool registry (graph + vector + fs + grep + entity.summary).
    • Citations invariant + JSON schema for AnalyzerResult.
    • fs-access gate for out-of-repo paths (§7.3) with session-scoped approvals.
    • present gate for final save / copy / discard.
    • Todos pane + inline chat widget render the plan + progress (zero new pane code).
    • Classifier swaps code-analysis intent routing to the new controller; the legacy CodeAnalysisController is retained for rollback in this phase only.
  3. Phase 2 — Analysis Report Pane + feedback + legacy removal.
    • AnalysisReportPane (ephemeral, single per session) renders list.body via MarkdownWidget.
    • Annotate + batch Send all to chat flow (§10.3).
    • Quote to chat now single-shot path.
    • mid-flight-cancel gate via Stop analysis on the pane.
    • Per-task caching with rev-keyed invalidation.
    • Delete the legacy CodeAnalysisController and its prompt files; classifier routing has no fallback after this phase.
  4. Phase 3 — Cross-agent integration.
    • Register code:* tools in the daemon's tool registry so sibling analyzers can call them (§13).
    • Wire data:* / deploy:* tools into this analyzer's tool list (gated on insrc.analyzers.enabled).
    • TOOL_UNAVAILABLE sentinel + graceful fall-through path.
    • Single-hop depth cap enforcement via crossAgentDepth in run-task ctx.
    • Citation propagation: foreign citations rendered as separate blocks in synthesise output.
  5. Phase 4 — Polish.
    • Export to file-in-repo (docs/code-analysis/<slug>.md) via the existing artifact-save helper.
    • "Re-run with new repo rev" one-click action on a past analysis.
    • Diff-vs-previous-run mode (did audit findings change after the last commit?).
    • Optional @mention-driven cross-agent dispatch (let the user explicitly target a specific analyzer in a chat message: "@data-analyzer describe the users table").
