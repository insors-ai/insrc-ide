Data Analyzer Agent

Cloud-orchestrated, local-analyzed, read-only data understanding -- live schemas, lineage, drift, sample shapes -- with a live analysis surface. One of three standalone analyzers (alongside Code Analyzer and Deployment Analyzer).

1. Overview

The Data Analyzer is a read-only agent that produces a structured, cited Markdown report answering a user's question about a codebase's data -- live database schemas, sample-data shape, lineage between code and tables, schema drift between the code's expected shape and what the live DB actually carries, and ER topology. It handles everything from focused questions ("what columns does orders actually have right now?") to broad audits ("walk the data flow from API request to persistence and call out drift"). It never writes to a database.

Internally the agent is two LLMs cooperating:

  • An Orchestrator on the active cloud provider decomposes the request into a task list, reviews each analyzer response, decides the next task, and finally assembles the full report.
  • An Analyzer on the local Ollama model answers one unit task at a time by querying the registered DB connections (RDBMS + KV families), parsing optional Prisma / ORM schemas, and -- when present -- pulling lineage hints from the Code Knowledge Graph.

The agent rides on the session-scoped TODO framework (plans/todo-framework.md): the orchestrator's plan is a TodoList, each analyzer task is a TodoItem, and the existing todos editor pane + inline chat todos widget give the user live progress. A dedicated Analysis Report Pane renders the final synthesised Markdown and lets the user highlight a finding and send it back to the chat panel as a quoted follow-up.

The analyzer is standalone in every regard -- its plan, run loop, review loop, synthesise, present gate, findings store, artifacts dir (docs/data-analysis/<slug>.md), REPL entry (/data-analyze), prompt assets (~/.insrc/data-analyzer/), and tool registry are independent of the Code and Deployment analyzers. Removing one of the others does not affect this one. Cross-agent enrichment via registered tools is opt-in (see §13).

1.1 Two Entry Flows

The Data Analyzer accepts two entry shapes. Both share the same run-task / review / synthesise core; they differ only in whether the plan step is needed.

Decision: The synthesise step runs on the local LLM, not the cloud. The cloud is the heavy reasoner for plan + per-task review (where it sees minimal context per call); the local model writes the final Markdown report from accepted findings it already has in hand. Keeps cloud token cost focused on decisions, not prose generation.
Step Flow 1 -- direct user question Flow 2 -- tasks pre-decomposed (called from another agent)
Plan cloud LLM decomposes the user's request into DataAnalysisTask[] Skipped -- the caller hands over DataAnalysisTask[] directly
Run-task (per task) local LLM executes one task, calls read-only tools (data:* + cross-agent code:* / deploy:*), emits a structured DataAnalyzerResult
Review (per task) cloud LLM reviews the analyzer output; decides accept / retry-with-hint / add-follow-up / done
Synthesise local LLM composes the final Markdown report from accepted findings + citations
Output Final report rendered in the Analysis Report Pane; present gate fires for save / copy / send-to-chat Final report returned to the caller as a structured { report, findings, citations, confidence } object; no present gate (caller decides what to do with it)

Flow 1 is what the user reaches via /data-analyze or the classifier's data-analysis intent. Cloud LLM does the up-front decomposition because the user's prompt is unstructured.

Flow 2 is what another agent reaches when it wants this analyzer to handle a specific scope it has already framed. The caller dispatches via the cross-agent data:analyze tool (see §13.5) with a prepared task list. The analyzer skips plan, runs the tasks, reviews each, synthesises, and returns the result inline -- the caller's run-task LLM gets a tool result back, just like any other cross-agent call. Single-hop depth cap still applies. Connection-approval gates still fire on Flow 2's first use of any registered connection per session.

2. Goals & Non-Goals

Goals

  • Decomposed analysis. Break a broad request into focused sub-questions so the local model never has to carry the whole problem at once.
  • Cited answers. Every finding names a connection / table / column (or key pattern, for KV connections) that came from a real introspection or sample call, not free-text speculation.
  • Live truth over static schema. The default citation source is the live DB (information_schema / PRAGMA table_info / Mongo collection sampling / Redis SCAN). Optional ORM / Prisma fast-paths exist when the user opts in, but live introspection is the default to avoid silent drift.
  • Lineage when it's there. When the Code Analyzer family is enabled, the Data Analyzer cross-links findings with code paths (which functions read / write each table) via §13's cross-agent tools. When the Code Analyzer is absent, the Data Analyzer reports schema findings without lineage and notes the missing enrichment.
  • Local-heavy, cloud-thin. Analyzer work (which makes most of the DB round-trips and consumes most of the tokens describing schemas) runs locally. Cloud is used for planning and final synthesis only.
  • Progress-visible. User sees the plan, sees tasks complete one by one in the Analysis Pane, and can steer (add a task, edit the plan, ask a follow-up) mid-flight.
  • Resumable. Crash / VS Code restart / model switch mid-analysis preserves completed analyzer results.

Non-Goals

  • DB writes. The analyzer never executes INSERT / UPDATE / DELETE / DROP / Redis SET / Mongo writes / DynamoDB PutItem -- not at protocol level, not via parameters. If a finding implies a fix (e.g. a missing column), the user moves it to the coding agent separately.
  • Unbounded autonomy. The orchestrator runs a capped number of iterations; we do not let a cloud LLM chase its own findings indefinitely. (See §6.3 -- 16 / 24 caps, independent of the other analyzers.)
  • Prod-grade safety. The expected target is dev / staging / local DBs. Pointing at production is supported via per-connection PII masking + connection-approval gates, but the design assumes a developer-on-laptop threat model. (See §7.3.)
  • Cross-DB joins. The analyzer never invents a join between two connections. If a finding involves both a Postgres table and a Mongo collection, they're reported as two separate cited findings linked by prose -- not as a single synthesised join result.
  • Schema migration generation. The analyzer reports drift and gaps; it doesn't produce migration SQL. The user takes findings to a coding agent for that.

3. Family & Variant

Decision: The Data Analyzer is its own family (data-analyzer), not a variant of research and not a sub-mode of the Code Analyzer. The family owns its own registry row, slash command (/data-analyze), TODO ownership stamp (owner: 'data-analyzer'), prompt assets directory (~/.insrc/data-analyzer/), artifacts directory (docs/data-analysis/), and read-only tool surface. None of those depends on the Code or Deployment analyzer at runtime.

Why a sibling family rather than a variant of code analyzer or research:

  • Standalone in every regard. Removing the Code or Deployment analyzer leaves the Data Analyzer fully functional. The user can disable any of the three via insrc.analyzers.enabled without breaking the survivors.
  • Disjoint tool surfaces. Data wants the data:list-connections / data:describe-table / data:sample / data:scan family backed by per-kind drivers (pg, mysql2, better-sqlite3, ioredis, mongodb, ...). Hosting these under the Code Analyzer's family forces a lowest-common-denominator tool registry; a separate family lets the Data Analyzer carry the right closed set for its domain.
  • Disjoint citation shapes. Data citations are (connection, table, column [, queryResult]) and (connection, keyPattern, fieldPath); rendering them inline with code citations would muddle the Analysis Report Pane.
  • Independent plan budget. The 16/24 soft/hard task cap is owned per family, so cross-agent fan-out doesn't share a budget across analyzers (§6.3).
  • Different setup ceremony. Data Analyzer needs a registered DB connection before it can do anything useful (see §4.3). The Code Analyzer's setup is "have a repo open"; the Deployment Analyzer's is "have IaC files in the tree". Different launch / empty-state / first-run UX.

Prompt assets live in ~/.insrc/data-analyzer/: plan.md, review.md, analyzer.md, synthesise.md. The directory is mirrored in the bundled defaults; users who customise prompts edit their copy without affecting the other analyzers.

4.3 Relation to Data Driver

The data-driver is shipped infrastructure (plans/data-driver.md): a per-repo connection registry, secrets in the OS keychain, a closed set of registered drivers (Postgres, MySQL, SQLite, MSSQL, Oracle, Cassandra, Redis, Valkey, KeyDB, MongoDB, DynamoDB, etcd, Memcached, CSV / JSON / JSONL / TSV / Avro / Parquet / Arrow / Feather / BSON / xlsx file-family drivers), and the db:* tool family already registered in the daemon's tool registry.

Decision: The Data Analyzer is the agent layer on top of the data-driver. It does not re-implement connection management, driver registration, secrets, or tool-call enforcement -- those all live in daemon/db/. The Data Analyzer's contribution is the orchestrator + analyzer + synthesise + report pane that turns a free-form user prompt into a sequence of db:* tool calls and a final cited Markdown report.
Concern Lives in
Connection registry, secrets, per-connection PII masking config data-driver (daemon/db/registry.ts + daemon/db/secrets.ts)
Per-kind drivers (RDBMS / KV / file) data-driver (daemon/db/drivers/)
Driver-level write rejection + parameterised input contract data-driver (each driver module)
Connection-approval gate (first-time use of a connection in a session) data-driver -- the Data Analyzer hooks into the existing approval flow

What we do NOT build: a second connection registry, a second secrets vault, a second driver registry. The data-driver shipped first; the Data Analyzer is the orchestration layer that uses it. Anything mutating a registered connection (add / edit / remove / approve) goes through the data-driver's existing paths.

5. TODO Framework Integration

5.1 List & Item Shape

One TodoList per analysis run. The meta bag on each TodoItem carries the analyzer-specific payload without extending the framework schema: 

const list: TodoList = {
  id:          ulid(),
  sessionId,
  owner:       'data-analyzer',         // family stamp
  source:      'data-analyzer',
  status:      'active',
  title:       'Data Analysis: ',
  description: userRequest,
  body:        undefined,               // set by synthesise() to the final MD
  transfers:   [],
  items:       [ /* one per task */ ],
};

interface DataAnalysisItemMeta {
  kind:        'inspect-schema'   // describe a table / collection / key pattern
             | 'sample-data'      // pull rows / values for shape + content review
             | 'sample-shape'     // KV / document inferShape over many values
             | 'lineage'          // cross-link table to code that reads / writes it
             | 'schema-drift'     // compare expected (code / Prisma) vs. live shape
             | 'er'               // ER topology over a set of tables
             | 'free-form';       // fallback
  scope?:      {
    connections?: string[];      // connection ids to consider
    targets?:     string[];      // tables / collections / key patterns
  };
  origin:      'plan' | 'follow-up';
  retryCount:  number;
  hint?:       string;

  // populated on completion
  answer?:     string;
  findings?:   DataFinding[];
  citations?:  DataCitation[];
  confidence?: 'high' | 'medium' | 'low';
  toolCalls?:  ToolCallSummary[];
  truncated?:  boolean;
}

TodoItem.title is the short label shown on the todos pane row (e.g. "Sample orders from primary"); TodoItem.description is the full question the analyzer receives.

5.2 Item Lifecycle

Same five-state lifecycle as the Code Analyzer (§5.2): pending -> in_progress -> completed | blocked | cancelled. Transitions fire via deps.todos.markInProgress / updateItem / markComplete / markBlocked / cancel.

The one Data-Analyzer-specific lifecycle wrinkle: blocked can be reached not only via retry-cap exceeded, but also via connection-approval-denied (the user refused the connection-use gate -- see §7.3). The meta.blockedReason distinguishes the two so the synthesise step knows whether to suggest re-running the task with a different connection or with the connection approved.

5.3 Feedback Channel: Batched Annotations → Chat

Decision: Same as the Code Analyzer (§5.3): user feedback flows through the Analysis Report Pane's annotate-and-batch-send-to-chat path, not through framework per-item comments. Code-analysis lists are read-only on the todos pane (the kebab still offers copy-as-markdown and view-transfer-history); data-analysis lists adopt the same rule via list.meta.suppressComments: true.

5.4 Hierarchy & Follow-Ups

Two patterns:

  1. Flat follow-ups (default). A reviewer add-follow-up appends items to the same list with meta.origin = 'follow-up'.
  2. Scoped sub-list (when a follow-up explodes into ≥ 3 tasks). Common case: an audit on a single table reveals it's used by 5 services, each warranting its own drift check; the orchestrator spawns a child list. The pane renders root + child as sibling flat cards with ↑ parent: / ↓ children: cross-references.

6. Orchestrator

6.1 Step Flow

plan (cloud LLM, no tools) | -> deps.todos.createList(...) + addItem() per task | -> todos pane + inline chat widget auto-open showing the plan v plan-size check | +-- |plan| <= 16 --> auto-proceed (read-only, no gate) +-- |plan| > 16 --> [plan-size-approval] gate | approve -> proceed with full plan | trim-to-16 -> drop tail, keep first 16 | cancel -> abort run v run-task (one task at a time) | -> markInProgress(itemId) before analyzer.run() | | -> Analyzer picks connection -> may fire [connection-approval] gate | on first use of an unapproved connection in this session | v review-finding (cloud LLM, no tools) | +-- accept --> updateItem(meta); markComplete(itemId); advance +-- retry --> updateItem(meta.retryCount++, meta.hint); keep in_progress +-- add-follow-up --> addItem(..., meta.origin = 'follow-up'); advance +-- done --> cancel remaining pending items; jump to synthesise v (loop until list has no pending items OR caps hit; user may click "Stop analysis" on the pane to fire mid-flight-cancel gate) v synthesise (cloud LLM, no tools -- composes report) | -> updateList(body = markdown) v AnalysisReportPane opens with the rendered markdown v present gate (save / copy / send-to-chat / discard) | -> on save: artifact-save to docs/data-analysis/<slug>.md | -> on discard: list.transfer('system') for audit retention
Step Kind Description
plan llm Produces AnalysisTask[] from the user request + a connection summary (configured connection ids, kinds, last-known schemas if cached). No tool calls. Token budget ~1500.
plan-size-approval gate Conditional. Fires when the plan has > 16 tasks. Same actions as Code Analyzer (approve / trim-to-16 / cancel).
run-task[i] rpc Invokes the Analyzer sub-pipeline (§7). May fire a connection-approval gate (§7.3).
review-finding[i] llm Cloud LLM reads the analyzer output + accumulated context and decides accept / retry-with-hint / add-follow-up / done.
synthesise llm Composes the final Markdown on the local model: groups findings by table / collection / connection, preserves all citations, writes the top-level summary. Token budget ~4000. Writes to list.body on Flow 1; returns the structured result to the caller on Flow 2 (see §13.5). Local-only synthesis keeps cloud cost focused on per-task review decisions.
present gate Final gate. Actions: save (to docs/data-analysis/<slug>.md), copy, send-to-chat, discard.

6.2 Decision Loop

Same shape as the Code Analyzer (§6.2): the reviewer returns a JSON decision record with decision / rationale / retryHint? / followUps?; per-task retry cap = 2; on third failure accept-with-confidence: 'low'.

6.3 Termination

Caps are independent of the Code and Deployment analyzers: each family carries its own 16/24 soft/hard task cap. Cross-agent calls don't share a budget across families.

  1. Plan queue is empty and no pending follow-ups.
  2. Reviewer decides done.
  3. Soft cap at 16 tasks. Initial plans > 16 trigger the plan-size-approval gate; follow-ups beyond 16 are silently dropped with a follow-ups-skipped note.
  4. Hard caps: maxTasks = 24, maxFollowUps = 8.

6.4 Prompts

Three prompts in ~/.insrc/data-analyzer/ (overridable; bundled defaults shipped):

  • plan.md -- buildOrchestratorPlanPrompt(request, connSummary); emits AnalysisTask[] as strict JSON.
  • review.md -- buildOrchestratorReviewPrompt(task, result, accumulated); emits the decision record.
  • synthesise.md -- buildOrchestratorSynthesisPrompt(request, findings, plan); emits the final Markdown report.
  • analyzer.md -- analyzer system prompt; hands the local model the data:* tool list, citation contract, and per-task framing.

7. Analyzer

7.1 Task Contract

interface DataAnalysisTask {
  itemId: string;
  kind:
    | 'inspect-schema'
    | 'sample-data'
    | 'sample-shape'
    | 'lineage'
    | 'schema-drift'
    | 'er'
    | 'free-form';
  question: string;
  scope?: {
    connections?: string[];      // connection ids to consider
    targets?:     string[];      // tables / collections / key patterns
  };
  hint?: string;
  origin: 'plan' | 'follow-up';
  retryCount: number;
}

interface DataAnalyzerResult {
  itemId:      string;
  answer:      string;             // concise prose, 1-3 paragraphs
  findings:    DataFinding[];      // 0..N structured items
  citations:   DataCitation[];
  confidence:  'high' | 'medium' | 'low';
  toolCalls:   ToolCallSummary[];
  truncated?:  boolean;
}

// Citation shape for RDBMS-family findings
interface RdbmsCitation {
  agent:       'data';
  family:      'rdbms';
  connection:  string;             // connection id
  table:       string;
  column?:     string;
  row?:        Record<string, unknown>;   // serialised sample row, ≤ 1 KB
  confidence:  'high' | 'medium' | 'low';
}

// Citation shape for KV-family findings
interface KvCitation {
  agent:       'data';
  family:      'kv';
  connection:  string;
  keyPattern?: string;             // e.g. "session:*"
  fieldPath?:  string;             // dotted path inside a JSON value
  sampleValue?: unknown;           // serialised, ≤ 1 KB
  confidence:  'high' | 'medium' | 'low';
}

// Citation shape for file-family findings (CSV, Parquet, JSONL, ...)
interface FileCitation {
  agent:       'data';
  family:      'file';
  connection:  string;
  path?:       string;             // logical path within the connection's root
  column?:     string;
  confidence:  'high' | 'medium' | 'low';
}

type DataCitation = RdbmsCitation | KvCitation | FileCitation;

7.2 Read-Only Tools

The analyzer is given a closed tool set. The tool registry rejects anything outside this list even if the local model hallucinates a name. All data:* tools are thin agent-surface wrappers over the data-driver's underlying handlers (see §4.3).

Tool Purpose Notes
data:list-connections Enumerate registered DB connections for the active repo Returns { id, kind, family, label }[]. The analyzer always calls this first to discover what's available.
data:describe-table RDBMS schema: columns, types, PK, FK, indexes Backed by db.sql.describe. Honours per-connection schemaSource (introspect | prisma).
data:sample RDBMS row sample (SELECT * FROM <t> WHERE <...> LIMIT <n>) Limit clamped ≤ 50, wall-clock ≤ 5 s. where is a parametrised filter; raw SQL never flows from the LLM. Per-connection PII masking applied driver-side.
data:scan KV key listing under a pattern / prefix Limit ≤ 500 keys. Pattern restricted to the connection's namespace.allow if configured.
data:get KV single-value read Composite-key stores (DynamoDB partition+sort, Mongo collection+id) accept an object key.
data:sample-shape KV / document inferShape: field tree + types + nullability + frequency over N values Limit ≤ 50 values. Uses the data-driver's shape-common.ts inferShape helper.
data:lineage Cross-link table / collection / key pattern with code that reads or writes it Internally walks the Code Knowledge Graph for CALLS edges to known query-builder methods (db.query, prisma.user.findFirst, redis.set, ...). Returns { readers: Entity[]; writers: Entity[] }.
data:schema-drift Compare a code-side expected shape (Prisma / ORM model / static query analysis) vs. the live DB schema Returns { missingInDb: ColumnRef[]; missingInCode: ColumnRef[]; typeMismatches: ColumnDiff[] }. Per-RDBMS connection only -- KV stores don't carry a static schema to drift against.
data:explain (optional) RDBMS EXPLAIN on an AST-validated query Driver-specific output; useful for "is this query covered by an index?" follow-ups.
code:* / deploy:* Cross-agent read-only enrichment (see §13) Available only when the Code / Deployment analyzers are installed and enabled.

Explicitly excluded: raw SQL, raw Redis commands, write protocols on any driver, schema-mutation calls (CREATE, ALTER, DROP), FLUSHDB-shaped operations, shell exec, file writes, network fetch outside the registered connection.

7.3 Connection & Sample Gates

The Data Analyzer fires gates at three points where blocking on user input is worth more than the latency cost:

Gate id When Why
connection-approval First use of a registered connection in this session Even though the connection is already registered, we ask before the first introspection / sample / scan in a session. Prevents surprising the user with unprompted DB activity. Approval is session-scoped, not persistent. Approve cascades to any tool call against the same connection for the rest of the session.
sample-review Optional. Fires before returning sample rows that touch a connection flagged as prod in db-connections.json, and the sample crosses a threshold of unmasked columns matching common PII patterns (email, password, ssn, tax_id, ...) Belt-and-braces over the per-connection pii masking config. The user can review what's about to surface and choose mask-and-proceed / cancel-task.
schema-source-mismatch A drift task finds a Prisma schema referencing a connection that's not registered, or vice versa The user almost always wants to register / unregister rather than have the analyzer silently fall back. Actions: register-now, continue-without, cancel-task.
Connection-approval is the most common; the other two fire infrequently. The expectation is one connection-approval gate per connection per session, then no further blocking. Sample- review only fires on connections explicitly flagged prod -- developers pointing at local DBs never see it.

7.4 Tool Loop

Per-task tool loop on the local model:

  1. System prompt is prepended with /no_think (qwen3-coder structured tool-call requirement).
  2. User message contains the task JSON + hint (if retry) + a one-line summary of the connections returned by the most recent data:list-connections call.
  3. Model emits tool calls; daemon executes them; results fed back.
  4. Loop terminates on: model emits a final answer, hard cap of 8 tool calls, or 60 s wall clock.
  5. Final model turn produces the DataAnalyzerResult JSON.

7.5 Citations

Invariant: every claim in answer or every finding must resolve to at least one DataCitation. The analyzer's output JSON is rejected and retried (once) if any finding has citations.length === 0. After the retry, a missing-citation result is accepted but auto-downgraded to confidence: 'low'.

Citation rendering in the Analysis Report Pane: each citation kind has its own renderer. RDBMS citations link to a (connection, table, column) fingerprint; KV citations show the (connection, keyPattern, fieldPath); file citations show (connection, path, column). Sample rows / values are inlined verbatim (truncated at 1 KB) under a collapsed Sample disclosure to avoid PII surface in the primary view.

8. Controller State

interface DataAnalysisState {
  request:     string;
  connSummary: ConnSummary[];          // connections enumerated at plan time

  listId:      string;                 // primary TodoList id
  childListIds: string[];

  currentItemId?: string;
  truncated:    boolean;
  cancelled:    boolean;

  // Connection-approval state. Session-scoped, not persisted across sessions.
  approvedConnections: string[];       // connection ids approved this session

  // Final report -- mirrored to `list.body` for the framework's view.
  finalReport?: string;
  reportUri?:   string;
  presentedAt?: number;
}

Items, comments, follow-ups, transfer history, and inline chat rendering all live in the framework. The controller never keeps a parallel copy.

Resume on daemon restart rehydrates listId + loads the list from the framework's LanceDB tables; any in-flight item resets from in_progress to pending and re-executes. Connection approvals are session-scoped, so a fresh session re-prompts.

9. Gates

Gate id Phase Actions Trigger
plan-size-approval planning approve, trim-to-16, cancel Plan has > 16 tasks. Default after 5-min timeout = cancel.
connection-approval execution approve (cascades to all tool calls against this connection for the session), deny First use of a registered connection in this session.
sample-review execution mask-and-proceed, cancel-task Sample touches a prod-flagged connection with potential PII columns unmasked.
schema-source-mismatch execution register-now, continue-without, cancel-task Drift task finds a Prisma schema referencing an unregistered connection.

11. Intent Routing

Two entry points:

  • Explicit slash command: /data-analyze <prompt>. Bypasses the classifier; the request goes directly to the Data Analyzer family.
  • Classifier intent: a new data-analysis intent recognises free-form prompts about schemas / tables / columns / sample data / drift / lineage and routes to this controller. The classifier never disambiguates between code / data / deployment intents on a free-form prompt -- it picks the most likely fit by content; the user reaches for the explicit slash command when they want a specific analyzer.

Keyword hints for the classifier: schema, table, column, row, query, ER, drift, Prisma, ORM, DynamoDB, Redis, Mongo, sample, key pattern, partition. Falls back to research if the user's prompt is genuinely free-form.

13. Cross-Agent Integration

The Data Analyzer is fully functional on its own. When the Code Analyzer and Deployment Analyzer are installed and enabled, this analyzer can call their read-only tools mid-task to enrich findings -- e.g. resolve a users table to the functions that query it (code:callers), or resolve a connection's ${DB_HOST} env-var reference to its dev / staging / prod values (deploy:env-diff). When they're absent, the Data Analyzer falls back to schema-only findings and notes the missing enrichment.

Decision: Cross-agent enrichment uses the daemon's tool registry, not a new orchestration primitive. Each sibling analyzer registers its read-only capabilities as tools (code:locate, code:callers, deploy:env-diff, ...); this analyzer's run-task LLM sees them in the tool list and decides when to call them. No sub-pipeline, no shared in-memory state, single-hop only (cap depth at 1; tools detect crossAgentDepth >= 1 and return the TOOL_UNAVAILABLE sentinel).

13.1 Available Cross-Agent Tools

Tool Owner When this analyzer would call it
code:locate Code Analyzer A lineage task on a table -- locate the query-builder helper functions (e.g. userRepo.findById) before walking their callers.
code:callers Code Analyzer Once the lineage task has the query-helper entity, find every code path that calls it. Becomes the lineage finding's reader / writer list.
code:trace Code Analyzer A schema-drift task that finds a missing column -- trace which code paths actually access it so the report can call out which features are affected.
deploy:env-diff Deployment Analyzer A connection's URL references ${DB_HOST}; env-diff resolves it across dev / staging / prod overlays so the report can flag inconsistent values.
deploy:service-deps Deployment Analyzer An audit on a shared table reports which services depend on it -- combined with lineage, surfaces "service X reads orders but isn't in the deployment topology of orders-svc" findings.

13.2 Single-Hop Depth Cap

Same contract as the Code Analyzer (§13.2): cross-agent calls are single-hop. When this analyzer calls code:callers, the Code Analyzer's tool cannot in turn call deploy:* from within that call. Enforced via the crossAgentDepth counter in the run-task ctx.

13.3 Citation Propagation

Cross-agent results land in the report as a separate citation block tagged with the foreign agent. The synthesise step renders them in a Code findings (code-analyzer) or Deployment findings (deployment-analyzer) subsection, never inline with data citations. Reader can tell at a glance which findings came from which analyzer.

13.4 Graceful Fall-Through

If a cross-agent tool returns TOOL_UNAVAILABLE (target analyzer's tools aren't registered, e.g. user disabled it in insrc.analyzers.enabled):

  • The analyzer's run-task LLM sees the structured unavailable response and continues with schema-only / data-only findings.
  • The orchestrator's review step categorises affected lineage tasks as "external dependency missing" -- still acceptable, just with reduced confidence.
  • The synthesise step emits a single line at the bottom of the report: "Consider running /code-analyze for richer lineage findings" (or /deploy-analyze).

Same fall-through applies when the target analyzer's daemon-side handler errors or times out (5 s hard cap on cross-agent tool calls). The original analysis run never blocks on a sibling.

13.5 Flow 2 -- Plan-Level Delegation via data:analyze

Tool-call cross-agent (§13.1) is right when the calling agent needs a single targeted lookup -- "describe table X", "list connections". When the calling agent has framed a multi-task investigation that's wholly inside this analyzer's domain, it dispatches via data:analyze: a single tool call that hands over a pre-built task list and gets back a synthesised report. 

// Tool surface registered by the Data Analyzer family
//
// Caller hands over an already-decomposed task list; the Data Analyzer
// skips its plan step (Flow 2 entry), runs the tasks (firing
// connection-approval gates as needed), reviews each, synthesises a
// report on the local model, and returns the result inline.
{
  name: 'data:analyze',
  input: {
    tasks: DataAnalysisTask[];   // pre-decomposed, no plan step
    callerContext?: {
      agent: 'code-analyzer' | 'deployment-analyzer' | string;
    };
  },
  output: {
    report:     string;          // Markdown, synthesised by the local LLM
    findings:   DataFinding[];
    citations:  DataCitation[];
    confidence: 'high' | 'medium' | 'low';
    truncated?: boolean;
    blockedTasks?: { itemId: string; reason: 'connection-denied'
                                          | 'pii-gate-denied' }[];
  },
}
Decision: Flow 2 is a single tool call from the caller's perspective. The Data Analyzer's run-task / review / synthesise loop runs to completion before the call returns. Connection-approval and sample-review gates still fire -- the caller waits on them through the tool call, since the user is the right party to grant DB access in any case.

Why a separate tool from the per-capability ones (data:describe-table, data:lineage, ...):

  • Different cost shape. A data:analyze call with a multi-table audit can take 60+ seconds; data:describe-table is one introspection call.
  • Different return shape. Per-capability tools return raw schema / sample data; data:analyze returns a synthesised Markdown report with citations.
  • Connection-approval is gated once per session, not per call. A Flow 2 entry that touches three tables on the same connection fires the approval gate once and reuses the approval for the rest of the call. A caller that fired three separate data:describe-table calls would still hit the gate once (same session-scoped state); but the bookkeeping is cleaner with a single Flow 2 dispatch.
  • Single-hop cap still applies. Flow 2's tasks themselves can call cross-agent tools, but recursion is capped at depth 1 regardless of which entry flow opened the chain.

Caps inside Flow 2: the caller-supplied task list is subject to the same 16/24 soft/hard cap. Lists > 16 don't fire the plan-size-approval gate (no user is in the loop) -- the Data Analyzer trims to 16 silently and sets truncated: true in the return value. blockedTasks reports any tasks that hit a connection-approval-denied or PII-gate-denied path so the caller can decide whether to re-dispatch with a different scope.

Flow 2 has no present gate -- the caller folds the returned report into its own synthesise output as a "Schema findings (data-analyzer)" subsection.

14. Caching & Resume

  • Per-task cache. Key = SHA256(task.question + normalized-scope + connection-version), where connection-version is the data-driver's last-known schema fingerprint for the connections in scope (introspection result hash for RDBMS; SCAN cardinality + sample-shape hash for KV). On a hit, the orchestrator skips the analyzer call and reuses the cached DataAnalyzerResult. Cache lives under ~/.insrc/cache/data-analysis/, LRU-evicted at 200 entries.
  • Invalidation. connection-version is recomputed lazily on next use. A manual dataAnalysis.clearCache command is exposed.
  • Resume after daemon restart. The controller's TaskStateStore retains listId; on resume, the framework's LanceDB tables rehydrate the list and items. Any item marked in_progress at crash time is reset to pending and re-executed on resume. Connection approvals are not persisted across sessions; the resume re-prompts on the first connection use.

15. Failure Modes

Failure Handling
Cloud provider unavailable (auth / network) plan + per-task review fall back to the local model with a warning banner. synthesise already runs local by default so it's unaffected. Final report flagged provenance: 'local-only'.
Connection unreachable (DB host down, auth failed) Driver returns a structured error; analyzer reports findings: [], confidence: 'low', and a single connection unreachable note. Orchestrator marks task complete with meta.warning; subsequent tasks for the same connection are cancelled en bloc.
Connection-approval denied Analyzer marks the task blocked with meta.blockedReason: 'connection-denied'. Synthesise step emits the report without findings for that connection and notes which tasks were skipped.
Sample-review denied (PII gate) Same as connection-approval denied -- task blocked with meta.blockedReason: 'pii-gate-denied'.
Analyzer produces malformed JSON One retry with a strict-JSON reminder. On second failure, accept as-is with confidence: 'low'.
Schema drift detected on a connection the user no longer recognises Reported as a finding with confidence: 'high' and a connection: X (last touched 2024-08) hint -- doesn't fail the run.
Cross-agent tool times out 5 s cap; tool returns TOOL_UNAVAILABLE; analyzer continues with schema-only findings.
User starts a second data-analysis while one is running Rejected at plan with a notification. The new request is NOT auto-queued.
User dismisses VS Code mid-run Daemon keeps running; controller's state persists; on next open the todos pane restores the list. Connection-approval state does NOT persist; the resume re-prompts.

    • data:list-connections, data:describe-table, data:sample, data:scan, data:get, data:sample-shape tools wired into the analyzer.
    • connection-approval gate: first-use-of-a-connection-per-session prompt.

    • DataAnalysisReportPane ephemeral, single tab per session.
    • Annotate + batch Send all to chat flow.
    • Per-task caching keyed on connection-version.

  4. Phase 3 -- Lineage + drift.
    • data:lineage tool: cross-link table / collection / key pattern with Code Knowledge Graph CALLS edges.
    • data:schema-drift tool: compare static expected shape (Prisma schema / ORM model / static query analysis) against live introspection.

    • Register data:* tools so the Code and Deployment analyzers can call them.
    • Wire deploy:* tools into this analyzer's tool list (gated on insrc.analyzers.enabled).

    • Export to file-in-repo (docs/data-analysis/<slug>.md).

    • PII-pattern library extension (per-repo overrides).

17. Open Questions

Question Resolution
Per-session connection approval Required on first use. Even though the connection is already registered with the data-driver, the analyzer asks before its first introspection / sample / scan call in a session. Approval cascades to all subsequent calls against the same connection for the rest of the session; not persisted across sessions (§7.3).
PII-flagged sample handling Driver-side masking by default; sample-review gate for prod. Per-connection pii config triggers masking driver-side. Connections flagged prod additionally fire a sample-review gate when unmasked PII columns are about to surface (§7.3).
Drift detection scope Static expected shape vs. live. "Expected" comes from a Prisma schema (when present), an ORM model file (TypeORM / Sequelize / Mongoose), or static analysis of query-builder usage in the code. KV stores don't carry a static schema; drift on KV connections falls back to shape changed since last sample.
Cross-agent recursion Single-hop only in v1 (§13). Cap can be raised later with explicit token + latency budgets if real-world usage shows benefit from chains.
Lineage when Code Analyzer absent Schema-only findings + footer. The Data Analyzer reports schema / sample / drift findings without lineage and emits a "Consider running /code-analyze for richer lineage" footer line.
Concurrent analyses per session One at a time. Second request rejected with a notification.
Plan budget independence Per-family. The 16/24 soft/hard cap is independent of the Code and Deployment analyzers. Cross-agent fan-out doesn't share a budget across analyzers.
Caching cross-agent tool results Caller's cache only. The Data Analyzer caches its own cross-agent tool calls keyed on (tool, args, connection-version). The Code Analyzer's separate cache is independent. No shared cache.
