Memory + Context — consolidation & agent integration

Status: DRAFT · Scope: framework-level memory + context system across daemon, agent, chat, meta-task · Surfaced via: O4 of [/plan template design] · Tracks: plans/TODO.md item #1

This is a consolidation + integration design, not a from-scratch one. An audit of the codebase before drafting this doc surfaced an already-implemented memory substrate (src/insrc/daemon/substrate/, ~3,300 LOC, P0–P10 complete) plus four other partially-overlapping memory subsystems. The substrate covers ~90% of what we sketched for preferences in O4 — including a user-assertion classifier that's exactly the "preferences from corrective turns" mechanism. The real work isn't building new memory machinery; it's wiring the substrate into the agent / chat / meta-task surfaces and deciding the fate of the legacy config/ system.

1. Overview

1.1 The problem (user-reported)

Real-world reliability: the framework's memory slot (chat turn ANN) + the auto-memory file lose durable user preferences over time. Examples the user has been bitten by: "always include unit tests in implementation plans for this repo" gets stated, used for a session, then drifts out of recall when the next /plan invocation happens. Even when forced to write the preference to memory, it gets diluted, paraphrased, or lost.

1.2 The shape of the answer

Three things need to be true for durable preferences to actually work:

  1. Categorized, owner-scoped storage — not undifferentiated blob memory. A "prefer unit tests" rule belongs in a specific bucket (template /plan, category implementation, repo X) so retrieval is deterministic, not ANN-pray.
  2. Capture from observed user behavior — not just explicit "/remember" commands. The user shouldn't have to manually curate every preference. When they say "always include unit tests" in chat, the system should notice and offer to save it.
  3. Always-include retrieval at the right moments — not opt-in via semantic search. When /plan is producing an implementation plan, the preferences for (template: plan, category: implementation, repo: this) must be in the prompt. No "if cloud LLM happens to ask for memory" gating.

2.1 Substrate (daemon/substrate/)

The most comprehensive prior work and the foundation everything else should compose around. Designed in detail in plans/memory-context-substrate.md (1,342 lines, 15 locked decisions D1–D15). Implementation tracked in plans/skills/substrate-implementation-status.md (P0–P10 all done).

What it provides:

  • Owner-scoped typed memory store — namespaces per owner ('skill:code.class.extract-fields', 'agent:pair', 'classifier:intent', …). File-backed; atomic temp+rename writes; directory-tree sharded.
  • Trichotomy: every entry is fact / hint / constraint. constraint = external authority (usually user); wins conflict resolution; ages only on explicit recontradiction. This is the right kind for user preferences.
  • Four query modes: byKey, prefix, byEmbedding (Lance ANN), filter. Single-source slots; no cross-source mixing.
  • Working state ledger + distillation on successful return. Pinned ledger entries become memory entries.
  • Feedback bus (D8) — fire-and-forget fan-out by target owner.
  • User-assertion classifier (D6) at daemon/substrate/classifier/user-assertion.ts. Three-layer pipeline: heuristic detect → heuristic classify → LLM classify → user confirm. Accepted assertions land as kind: 'constraint' with source: { kind: 'user-asserted', turnId } in the targeted owner's user-assertions namespace.
  • AssertionIndex — routes accepted assertions to owners that declared assertionInterests at registration time. This is the routing layer that makes "save preference for /plan implementation category" work without each consumer hand-rolling the routing.
Critical gap that fully explains the user's problem. The substrate has the machinery. No agent, no chat-handler, no meta-task currently calls runtime.classifyAssertion(turn). Chat turns flow through the L1-L5 context budget (which doesn't classify) and the intent resolver (which only does intent + relationship classification, not assertion classification). The user-assertion classifier exists but is never invoked on a user turn. That's why "always include unit tests" gets stated and forgotten.

2.2 L1-L5 context budget (agent/context/)

Per-turn chat-side context assembler. ContextManager builds:

  • L1 system — static project instructions (built once per session)
  • L2 summary — rolling summary; updated on eviction
  • L3a recent — recency-weighted recent turns
  • L3b semantic — ANN-similarity prior turns
  • L4 task — code entities from the graph
  • L5 response — output budget

Used by chat-handler.ts, session.ts, task.ts, intent/resolver.ts. Strictly per-turn; no notion of cross-session storage or ownership scoping. Doesn't manage preferences — it manages tokens. Stays unchanged in the new design except for the addition of a "preferences" layer drawn from the substrate (§5).

2.3 Conversation store

db/conversations.ts + db/lance/turn-vec.ts. Multi-tier retention (hot/warm/cold/archive); per-session turns; per-repo ANN via searchTurnsByRepo. The chat memory backbone — durable, indexed, but free-form. Nothing distinguishes a preference assertion from chat noise in storage; that's the classifier's job at capture time (§5).

2.4 Classifier memory bundle

agent/intent/classifier-memory.ts + IPC handler internal-ipc/handlers/memory.ts + MCP tool mcp/tools/memory.ts. Bundles top-K turns + top-K response segments via dual-ANN for the intent classifier (§2.5 of CLAUDE.md). Reusable wrapper around turn_vec + response_segment_vec. Doesn't grow new responsibilities under this design; the substrate's preferences slot composes with it but doesn't replace it.

2.5 Config store (legacy)

config/ — pre-substrate system. ConfigStore + searchConfig + recordFeedback. LLM-driven generalization (a raw user correction becomes an imperative-form rule), scope classification (global vs project), namespaces under ~/.insrc/conventions/, ~/.insrc/feedback/, ~/.insrc/templates/.

Used by the legacy planner, Delegate, brainstorm, designer. Pre-dates the substrate; overlaps heavily in concept (typed scoped storage with LLM-curated entries) but uses a different storage format and a different API. This is the system to migrate / absorb / retire — we don't want two parallel preferences storages.

3. The user's problem, decomposed

Mapping the user-reported failure to the existing systems:

SymptomWhat goes wrongWhy existing systems don't fix it
"I told the agent X; the agent didn't remember X in the next session" X was never classified at capture time. Lives as a free-form chat turn. L1-L5 doesn't classify. Intent resolver classifies intent, not assertions. Substrate's classifier exists but is never invoked on chat turns.
"Auto-memory forced to write X eventually loses X" Auto-memory is unstructured; ANN retrieval over many turns dilutes the signal. L3b semantic recall is similarity-based; high-recency or high-similarity wins, not high-authority. A constraint should win, but the constraint kind only exists in the substrate, which the chat doesn't touch.
"I want this preference to apply to /plan specifically" No mechanism for the user to scope a preference to a template / category. Substrate has assertionInterests + AssertionIndex that would do this routing — but it's not exposed to chat-side capture.
"My preferences should auto-load into /plan, not require asking" No always-include retrieval at template execution time. Meta-task framework's memory slot is opt-in via the cloud LLM's phase-1 ask. Substrate has a preferences-shaped equivalent (the typed slot system) but isn't accessible to meta-task templates yet.

4. Strategy: consolidate around the substrate

The substrate is the canonical memory layer. Everything else either composes with it, delegates to it, or migrates into it.

Operating principles:

  1. One memory primitive. Substrate is it. The config/ system becomes a transitional surface, then deletes.
  2. One classifier. Substrate's UserAssertionClassifier is the only path for "convert a free-form statement into a durable rule." Used by chat capture, explicit slash commands, and meta-task gate handlers alike.
  3. One retrieval contract. Substrate's typed-slot ContextAssembler is the API every consumer composes against. The meta-task framework's memory slot becomes a thin delegate. The L1-L5 chat assembler adds preferences as a new layer drawn from the substrate.
  4. Owner identity scales from skills (already done) to agents ('agent:pair', 'agent:meta-task:plan', 'agent:meta-task:plan:implementation') without new primitives. The existing owner-naming convention handles the scope axes our O4 conversation needed.

What this preserves: the substrate's locked design (D1–D15), the implementation already shipped, all skill consumers, all backward-compatible test surfaces. What this changes: chat turns get classified; meta-task templates declare owners + assertion-interests; config/ deprecates.

5. Integration points (the real questions)

Three concrete decisions the design has to make. Each one is a wiring exercise + a small framework extension, not a from-scratch subsystem.

5.1 Chat ↔ substrate

Wire chat turns through runtime.classifyAssertion(). Three sub-questions:

5.1.1 When does classification run?

Two candidate triggers:

  • Per-turn passive scan — every user turn flows through classifyAssertion before the intent resolver. Captures everything; risk of noise.
  • Targeted at correction moments — only when the user is rejecting / revising / correcting (M5 plan-revision gates, abort feedback, explicit /remember slash). Cleaner signal; misses standalone preference statements ("by the way, this codebase requires JS not TS").

My read: both. Passive scan with a heuristic gate (only enqueue classification when the turn matches assertion-shape regexes — D6's Layer 1 already does this cheaply). Targeted invocation guaranteed at gate moments. The classifier itself deduplicates against already-stored assertions per D7's last-wins rule, so noise is bounded.

5.1.2 What does user-confirm look like?

D6's Layer 3 is "user-confirm" — when the classifier's confidence is below threshold, ask the user explicitly. The default substrate implementation returns "defer" (no confirm surface). We need to wire this to a chat-side affordance.

Candidate UX: inline confirmation bubble in chat ("Save 'always include unit tests' as a preference for /plan implementation? [Save] [No thanks] [Customize…]"). Same gate framework already used for handoff Mode A and M5 plan-revision — no new component.

5.1.3 Default acceptance threshold

D6 spec: Layer 1 heuristic accept-only for the obviously-shaped patterns ("always X", "never Y", "remember Z", "use A for B", "do not C"). Layer 2 LLM-classify for ambiguous shapes. Layer 3 user-confirm when LLM confidence is below threshold.

Open: what's the threshold? Substrate code currently leaves this injectable. Picking a default is a UX call — high threshold = many confirms (annoying) but high precision; low threshold = few confirms but risk of false-positive preferences locked in.

5.2 Meta-task ↔ substrate

Make meta-task templates first-class substrate owners. Three pieces:

5.2.1 Template-as-owner registration

Each meta-task template declares an owner id + assertion-interests + memory schema: 

// In templates/plan.ts:
export const planTemplate: MetaTaskTemplate = {
  id: 'plan',
  // ... existing fields ...
  ownerId: 'agent:meta-task:plan',
  assertionInterests: [
    'plan-policy',
    'naming-conventions',
    'test-strategy',
    'commit-strategy',
    // ...
  ],
  memorySchema: [
    { namespace: 'user-assertions', kind: 'constraint' },
  ],
};

Owners can be sub-scoped: 'agent:meta-task:plan:implementation' for category-specific preferences. The AssertionIndex routes accepted assertions to all owners whose interests match the classified subject.

5.2.2 New preferences context slot

Add to meta-task framework's ContextRequest: 

type ContextRequestPreferences = {
  readonly kind: 'preferences';
  readonly scope?: {
    readonly templateId?: string | undefined;
    readonly category?:   string | undefined;
    readonly repoPath?:   string | undefined;
  } | undefined;
};

Fulfillment translates to a substrate query: open the owner namespace matching the scope, scan user-assertions with the trichotomy ranking (constraint > fact > hint), return as a chunk. Local LLM doesn't synthesize — the substrate already manages ranking + freshness.

5.2.3 Always-include policy

For the user's "preferences should auto-load" requirement: meta-task templates declare preferences as a required phase-1 slot. The framework injects a preferences request into every step's phase-1 ask automatically, before the cloud LLM sees the ask. The cloud LLM can additionally request preferences via its own phase-1 ask, but the framework guarantees they're already in the chunk set.

This violates the meta-tasks framework's "cloud LLM decides what to ask for" principle slightly — preferences are framework-mandatory. Worth the violation because the user's problem is exactly that preferences should NOT be cloud-LLM-discretionary.

5.3 Config-store fate

Three options for the legacy config/ system:

  • A. Migrate fully. config/ deletes; everything moves to substrate. Legacy planner / Delegate / brainstorm / designer call substrate APIs. ~1170 LOC removed; ~5 consumers migrate.
  • B. Keep as a thin facade. config/ survives as a thin wrapper that delegates to substrate. config.searchConfig() becomes a substrate query; config.recordFeedback() becomes a substrate classifier invocation. No consumer migration; substrate is the source of truth.
  • C. Retire when callers retire. Legacy planner gets retired in /plan M4.b (per /plan template design); Delegate retires when Pair migrates; brainstorm / designer follow. config/ deletes when no callers remain.

My read: C. Lowest risk (no API change to callers in flight); preserves substrate as the new path without forcing a coordinated migration; aligns with the existing per-meta-task retire schedule. Marks config/ as deprecated in code comments + adds to plans/TODO.md for tracking.

6. Worked example end-to-end

Trace of the "always include unit tests" preference, from utterance to next-run retrieval.

  1. User says in chat: "For this repo, always include unit tests in implementation plans."
  2. Chat-handler enqueues a classification. Layer 1 regex matches "always X in implementation plans" — high-confidence assertion shape. No LLM needed.
  3. Substrate classifies + routes. Subject: test-strategy:include-unit-tests. AssertionIndex lookup finds owners that declared assertionInterests matching test-strategy: 'agent:meta-task:plan' + 'agent:meta-task:plan:implementation' + 'agent:meta-task:implement' (when /implement lands).
  4. Substrate persists. Writes kind: 'constraint' entry to each routed owner's user-assertions namespace with source: { kind: 'user-asserted', turnId }. Scope refinement (repo path) lands in the entry's value, not the namespace, so retrieval can filter.
  5. Substrate fires feedback event. Each routed owner's applyFeedback handler (if any) sees the new constraint. /plan's handler is a no-op for now — existing constraints get included in next run via the slot, no cache invalidation needed.
  6. Chat shows confirmation (or doesn't, per §5.1.2). Layer 1 high confidence: silent acceptance, optional toast. Layer 2 ambiguous: inline confirmation bubble.
  7. Days later, user invokes /plan implement: add a new auth provider.
  8. P1 analyze runs. Framework injects { kind: 'preferences', scope: { templateId: 'plan', repoPath: '/Users/.../repo' } } into the phase-1 fulfillment automatically. Substrate-backed fetcher scans agent:meta-task:plan/user-assertions, filters by scope, returns the matching constraints.
  9. Phase-2 prompt includes: "Active user preferences for this scope: test-strategy: include-unit-tests (constraint, source: user-asserted 2026-06-10)."
  10. P1 emits category: implementation/new-feature. P3 draft sees the same preferences. P5 detail's enrichment for the implementation category bakes the unit-test requirement into each step's data.
  11. Resulting plan includes unit-test steps. No need for the user to re-state the preference.

7. Open questions (gaps to iterate)

These are the gaps to resolve before implementation. Numbered for the iteration loop.

  1. G1: Chat-turn classification trigger. — RESOLVED

    Both passive (every user turn) and targeted (gate moments), with split UX semantics. Every user turn runs Layer 2 LLM classification — not regex-gated. Regex remains only as a fast-skip for clearly-non-assertion turns (single-token slash commands like /plan alone). When in doubt → LLM-classify. Decision pivots on the project principle accuracy primary, cost least priority (CLAUDE.md / AGENTS.md): the regex gate is a cost optimization that loses real preferences phrased outside its patterns.

    Passive flow (per user turn, after intent resolution):

    • Layer 2 classifier runs fire-and-forget — user turn proceeds without blocking on LLM.
    • Layer 2 accept: persist + small toast in chat ("✓ Saved preference: 'X'"). Non-intrusive but visible.
    • Layer 2 low confidence: Layer 3 confirm fires via a non-blocking chat surface (inline toast with [Save] / [No thanks] / [Customize…] buttons). Earlier "defer in passive" framing was cost-of-attention reasoning; under accuracy-first, missing a real preference is the worse failure mode.
    • Layer 2 reject: log + discard.

    Targeted flow (M5 plan-revision gates, abort feedback, /remember slash):

    • Layer 2 runs synchronously — user already in gate wait; adding 1-3s is fine.
    • Layer 3 confirm runs inline in the same gate modal when confidence is low.

    Same-turn application: when a passive-flow preference is captured, its substrate write completes before the same turn's action invocation dispatches. The user's /plan: add auth and always include unit tests sees the unit-tests preference applied to the same plan. ~2s synchronous wait is the price; degrades to fire-and-forget silently if the LLM is unavailable.

    Provider routing: classifier:user-assertion defaults to the local LLM (Ollama). Sub-second on assertion-shaped prompts; keeps the per-turn cost low without sacrificing accuracy (the classifier task is well within local-tier capability).

    Assistant turns are not classified — D6 designed for user input only.

  2. G2: User-confirm UX threshold. — RESOLVED

    Verdict-driven, not numeric-driven. Layer 2 classifier emits structured output { verdict: 'accept' | 'reject' | 'defer', confidence: 0..1, rationale }. The framework routes based on the verdict; the numeric confidence is a tiebreaker within the accept band.

    Layer 2 outputActionUX
    accept + confidence ≥ 0.85 Auto-persist as kind: 'constraint' Toast confirmation in chat
    accept + confidence < 0.85 Layer 3 confirm Inline toast with Save / Customize… / Discard
    defer Layer 3 confirm Same
    reject Silent discard None
    Subject already stored (dedup hit) Refresh timestamp/confidence per G7 None

    The 0.85 threshold (auto-accept boundary) is broad on purpose — fewer auto-accepts, more confirms. Under accuracy-first we'd rather pull the user in once than silently capture a wrong rule. Tracked as an externalizable setting at insrc.memory.assertionClassifier.autoAcceptThreshold in plans/TODO.md for landing in the user-settings framework (insrcConfiguration.ts) when the chat-wiring milestone ships.

    Layer 3 UX shape

    ─── Capture preference? ───
"For this repo, always include unit tests in implementation plans."

Scope: meta-task:plan + category=implementation + repo=insrc-ide

[ Save ]    [ Customize… ]    [ Discard ]
    • Save → persist as constraint.
    • Customize… → inline editor: edit the canonical text; widen the scope (dropdown: this repo / all repos; this template / all meta-tasks; this category / all categories). Then Save.
    • Discard → silent discard.

    Same component, two mount points: chat toast (passive flow) + gate modal inline (targeted flow per G1).

    No dismissal timeout, no silent loss.

    If the user ignores a toast, the substrate persists the candidate as kind: 'hint' with a pendingConfirm: true flag in the source metadata. The preference isn't lost; it's downgraded to advisory until the user reviews it. Future retrieval includes hints ranked below constraints (substrate's existing trichotomy ranking handles this for free). This re-uses the existing kind primitives — no new "pending" enum value needed.

    Review surface for pending preferences

    M1: /prefs slash command — lists pending + confirmed preferences in chat; actions (confirm / edit / discard) flow through gates. ~few hundred LOC; ships in the same milestone as the chat-side classifier wiring.

    Follow-up: dedicated preferences pane (workbench editor, like the meta-task report pane) lands later if the slash UX gets cumbersome.

  3. G3: Assertion-interest taxonomy. — RESOLVED

    Closed-enum taxonomy of 12 categories in TypeScript code. Classifier emits one of them, JSON-schema-constrained. No config-side extension — new categories land via code change.

    The substrate's existing routing layer (AssertionIndex.lookup) already does exact-string match on subjectPattern per D14 step 1. G3 just decides that we document and constrain the canonical set rather than leaving the subject space open. Free-form would force fuzzy matching at routing time, trading determinism for flexibility — the wrong tradeoff under accuracy-first. 

    // src/insrc/daemon/substrate/taxonomy/preference-subjects.ts
export type PreferenceSubject =
  | 'code-style'             // naming, formatting, structural conventions
  | 'test-policy'            // coverage, test types, fixtures, mocking
  | 'documentation-policy'   // docstrings, comments, design docs, READMEs
  | 'commit-policy'          // granularity, messages, signing, branches
  | 'dependency-policy'      // libraries, versions, vendoring
  | 'architecture-policy'    // patterns, layering, dep direction
  | 'tooling-policy'         // build, linter / formatter, CI choices
  | 'security-policy'        // auth, secrets, validation, audit
  | 'data-policy'            // schema, migrations, retention
  | 'workflow-policy'        // PR review, deployment, hotfix procedure
  | 'communication-policy'   // chat tone, verbosity, format
  | 'escalation-policy';     // when to ask user vs proceed

    Owners declare typed interest: 

    // In templates/plan.ts (or any owner):
assertionInterests: [
  { subjectPattern: 'test-policy',
    description: 'Test coverage + style preferences for plans' },
  { subjectPattern: 'documentation-policy',
    description: 'Doc requirements for plan steps' },
  { subjectPattern: 'code-style',
    description: 'Code conventions to reflect in plan steps' },
] satisfies readonly AssertionInterest[],

    Classifier's Layer 2 structured output schema constrains the subject field to the PreferenceSubject enum. The LLM must pick one; can't emit free-form. The failure mode is misclassification (LLM picks wrong category), mitigated by G2's wide auto-accept band — confidence < 0.85 triggers Layer 3 confirm and the user can re-classify via the Customize… editor.

    Adding a new category:

    • PR to add the enum value to preference-subjects.ts.
    • PR to update each interested owner's declared interests.
    • Re-registration on daemon restart.
    • Deliberate, surfaced as an explicit code change — not LLM-discretionary expansion.

    Sub-categorization happens via scope axes (G4), not via sub-subjects. A preference like "always include unit tests in implementation plans" is:

    • subject: 'test-policy' — routing.
    • scope: { templateId: 'plan', category: 'implementation', repoPath: '…' } — filtering at retrieval, defined in G4.
    • payload: { canonicalText: "always include unit tests" }

    Taxonomy stays flat. We don't introduce test-policy/unit-tests/coverage/lines/80%-style hierarchical subjects.

    Cost: ~50 LOC for the enum + taxonomy file, ~20 LOC for the JSON schema constraint on the classifier's structured output. Negligible.

    Follow-up doc task: short user-facing description of each category (for the /prefs UX to show "what subjects mean"). Lives at design/preference-taxonomy.html when needed; not a blocker for code.

  4. G4: Preference scope axes serialization. — RESOLVED

    Owner-local isolation as a first-class principle. Substrate's existing on-disk layout (<rootDir>/<workspaceId>/<owner>/<namespace>/…) already enforces per-owner subtrees. When the AssertionIndex routes an accepted assertion to N owners, N entries get written, one per owner. After capture, each owner is sovereign — updates / edits / deletes don't cascade.

    This is a feature, not a bug: owners may legitimately want different phrasings of "the same" preference (agent:meta-task:plan vs agent:pair may want subtly different framings of "always include unit tests"). Isolation lets them diverge.

    Scope serialization

    interface PreferenceValue {
  readonly canonicalText: string;
  readonly subject:       PreferenceSubject;   // routing (G3)
  readonly scope: {
    // Coarse scope = owner identity (storage-enforced); not in this struct.
    // Fine scope axes filter within an owner's namespace at retrieval.
    readonly categories?: readonly string[];   // e.g., ['implementation'] within /plan owner
    readonly repoPaths?:  readonly string[];   // which repos; omit = all repos
  };
  readonly source:        EntrySource;          // substrate's existing turnId/classifier refs
  readonly confidence:    number;
  readonly createdAt:     string;
}

    scope.templates is not a field — owner identity already encodes template (agent:meta-task:plan is plan-only). Sub-owners narrow further: agent:meta-task:plan:implementation exists when an owner wants category-bound preferences distinct from its parent.

    Retrieval flow

    1. Open the owner's user-assertions namespace (substrate primitive).
    2. Scan all entries (filter mode supported; scale is microseconds for any realistic count).
    3. For each entry: skip if scope.categories is set and query's category isn't in it. Same for repoPaths.
    4. Return matches ranked per substrate's trichotomy (constraint > fact > hint).

    Storage stays at substrate's existing path.

    ~/.insrc/substrate/<workspace>/<owner>/user-assertions/<key>.json. JSON file format unchanged from substrate convention. Raw file editing supported but not the primary UX; /prefs slash command (M1) + future dedicated pane handle user-facing curation.

    Future scope-axis extensions

    Same policy as G3's taxonomy extension — code change adds a new field, owner re-registration. Likely future candidates: filePatterns, languages, branches. Start with categories + repoPaths; extend as evidence demands.

    "Same preference across many owners"

    User re-states the rule in chat with broader phrasing; classifier captures with wider routing. No /prefs copy-to <owner> command — adds complexity for a niche flow without enough payoff.

  5. G5: Framework-mandatory preference injection. — RESOLVED

    Framework auto-injects a kind: 'preferences' request into every meta-task step's phase-1 fulfillment — preferences are always considered. The local LLM curates relevance against the step's intent and returns only applicable preferences. Cloud LLM sees a focused, filtered set in phase 2.

    This is the meta-tasks framework's local-as-librarian / cloud-as-reasoner pattern applied to preferences specifically. The framework guarantees consideration; the local LLM ensures relevance.

    Two-stage filter

    1. Hard scope filter (G4): categories / repoPaths must match the query scope. Pure JS predicate; microseconds.
    2. Soft relevance filter (G5): local LLM gets the scope-passed preferences + the step's intent and picks which ones apply to the step's subject matter. ~sub-second on Ollama. 
    // Framework injects automatically per step's phase 1:
const preferenceRequest: ContextRequestPreferences = {
  kind: 'preferences',
  scope: { templateId, category, repoPath },
  stepIntent: stepDescriptor.intent,        // for local LLM curation
};

// Local LLM fetcher:
async function fetchPreferences(req, inputs) {
  const owner  = `agent:meta-task:${req.scope.templateId}`;
  const all    = await memory.scope(owner, 'user-assertions').scan();
  const scoped = all.filter(matchesScope(req.scope));       // G4 hard filter
  if (scoped.length === 0) {
    return { request: req, status: 'empty', payload: [] };  // short-circuit
  }
  const relevant = await localLLM.curatePreferences({
    preferences: scoped,
    stepIntent:  req.stepIntent,
    bias:        'inclusion',                                // high recall
  });
  return { request: req, status: 'ok', payload: relevant };
}

    Worked example

    /plan generating an implementation plan for "add user auth." Owner agent:meta-task:plan has two stored preferences:

    • "always include unit tests" — subject: test-policy, scope: categories: ['implementation']
    • "deploys happen Friday only" — subject: workflow-policy, scope: any

    Stage 1 (scope filter): both pass — test-policy matches category: implementation; workflow-policy has no category restriction.

    Stage 2 (relevance curation): local LLM sees stepIntent: "draft an implementation plan for adding user auth". Includes test-policy (clearly relevant to implementation drafting); excludes workflow-policy (deploy timing isn't a planning concern at draft time).

    Phase-2 prompt sees one focused preference, not two with one irrelevant.

    Bias toward inclusion

    The curation prompt is "include if there's any chance this preference might apply" — high recall over high precision. Cloud LLM can ignore irrelevant chunks in phase 2; recovering from "preference was filtered out" is impossible. Under accuracy-first this is the right asymmetry.

    Framework principle dilution (documented)

    The meta-tasks framework's "cloud LLM declares its own sufficiency" principle is slightly diluted here: when cloud emits kind: 'sufficient', the framework still runs the local LLM for preferences. Documented exception — preferences are the one always-on slot. Cloud LLM CAN additionally request preferences via its own phase-1 (e.g., a different subject filter or wider scope); the auto-injection is a baseline, not a cap.

    Diagnostics

    The curation call optionally returns a short "why" per preference picked. Logged to ~/.insrc/meta/<id>/step-N-…phase1.jsonl for debugging; not surfaced in the phase-2 prompt.

  6. G6: Cross-session conversation store tagging. — RESOLVED

    Tag the turn with the memory-entry refs it produced. Cheap reverse lookup, natural UI affordances, simple audit query path. No retroactive edits when the underlying preference is later revised or discarded — history stays immutable, the renderer resolves current state at read time.

    Schema addition

    // db/conversations.ts -- TurnRecord (only the new field shown)
export interface TurnRecord {
  // ... existing fields ...
  /**
   * Memory-entry refs produced by the user-assertion classifier (D6) when this
   * turn was processed. Empty / undefined for turns that didn't produce
   * assertions (the common case). The substrate's source.turnId back-reference
   * provides the substrate -> turn link; this field provides the turn -> substrate
   * link for cheap reverse lookup.
   */
  readonly assertionRefs?: readonly string[] | undefined;
}

    What "tag the turn" enables

    • Reverse lookup is one field access. Loading a chat turn from history and immediately knowing "this captured X preferences" doesn't require scanning a substrate index.
    • Chat scrollback UI can render a small badge ("📌 captured as test-policy preference") next to turns that produced preferences. Without the tag, computing that requires a substrate scan per turn render.
    • Audit / curation queries. "Show me every turn that contributed preferences" becomes a turn-side filter.

    Immutable turn history; lazy resolution at read

    When a preference is revised (user edits canonical text via /prefs) or discarded (G7 confidence-aging or explicit user discard), the turn keeps its assertionRefs pointing at the now-stale entry. The renderer follows the ref at read time:

    • Ref resolves to active constraint → "📌 captured as preference: X (active)".
    • Ref resolves to superseded entry → "📌 captured as preference; superseded by [later turn]".
    • Ref resolves to discarded entry → "📌 previously captured as preference (discarded)".
    • Ref dangling (entry deleted entirely) → "📌 captured a preference; no longer tracked".

    Turn record never gets mutated retroactively. History stays a faithful record of what happened; current state lives in the substrate.

    Cost: one optional readonly string[] field on TurnRecord. Most turns have none (undefined / empty). Negligible.

  8. G8: Implicit-capture-during-retrieval (from O4). The original O4 conversation proposed the local LLM inline-flagging candidate preferences during retrieval. Substrate's classifier is already the right mechanism — do we also run a "scan recent unclassified turns at retrieval time" pass, or rely purely on capture-time classification? Implicit-at-retrieval recovers preferences the capture-time classifier missed (e.g., LLM was down at the time); but it's a re-classification pass that costs tokens.

8. Non-goals

  • Not redesigning the substrate. Its design is locked (D1–D15) and implementation is done. We compose with it; we don't rework it.
  • Not replacing the L1-L5 chat budget. It does per-turn token budgeting, a different concern. We may add preferences as a new layer; we don't subsume it.
  • Not a sync-across-machines or cloud-backed memory. Substrate is workspace-local by D5; user preferences stored under the same constraint.
  • Not exporting preferences to external systems (Jira, GitHub). Those are deliverable-side routing; preferences are inputs.
  • Not in-memory caching of preferences at the framework level. Substrate's existing caching (LRU per-workspace) suffices; we don't add another tier.
