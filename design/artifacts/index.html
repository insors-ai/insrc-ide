Artifact Tasks

Pre-defined tasks that produce embeddable HTML snippets for software-development artifacts (ER, sequence, flow, deployment, wireframes).

1. Overview

A small, fixed menu of pre-defined tasks that each generate one kind of software-development artifact and return an embeddable HTML snippet. Each task is a deterministic tool — given the same inputs it produces the same snippet — wrapped around a prompt specific to its artifact kind and a standard HTML template specific to its rendering.

Phase-1 menu:

  • ER diagram — entities + relationships, sourced from live DB / Prisma schema / Kuzu graph / free-text.
  • Sequence diagram — call / message sequence, sourced from Kuzu CALLS traversal or free-text.
  • Flow diagram — code-flow (graph-sourced) or business / process flow (free-text).
  • Deployment diagram — nodes / services / connections, sourced from docker-compose.yml, k8s manifests, Terraform, or free-text.
  • UI wireframe — low-fi layout from a free-text description.

Snippets are portable HTML (self-contained or host-rendered; see §8). Callers choose where to embed them — chat transcript, analysis / brainstorm / designer panes, a dedicated artifacts pane, or exported markdown.

2. Goals & Non-Goals

Goals

  • Deterministic, pre-defined tasks — fixed menu, known inputs, known outputs. Not "ask an agent to draw something."
  • Embeddable HTML snippets — the output of every task is a string of valid, self-contained-or-host-rendered HTML that drops into any markdown / HTML host without rework.
  • Standard templates shipped with the tool — one bundled HTML template per artifact kind. Users can override per-repo or per-user without forking the daemon.
  • Data-source-first, free-text fallback — when the kind has a natural source (graph, DB, config files), the task uses it. Free-text is always available as a fallback or greenfield path.
  • Iterable — every generated artifact stores its source (Mermaid text, wireframe spec) so a follow-up "regenerate with these changes" call is cheap and produces a coherent diff.
  • Callable by user and agents alike — slash commands for direct user invocation; the same tools registered in the analyzer tool registry so designer / brainstorm / planner / code-analyzer agents can embed artifacts in their output.

Non-Goals

  • Free-form "draw whatever" agent. No generic "artifact generator" that plans its own decomposition. Each task has a fixed output shape.
  • High-fidelity UI mockups. Wireframes are low-fi structure — boxes, labels, rough layout. Pixel-accurate mockups belong in a design tool.
  • Round-trip editing of generated HTML. The source (Mermaid text / wireframe spec) is editable; the rendered HTML is output, not source of truth.
  • Third-party diagram hosting. Snippets render inline; we don't upload anything to mermaid.live, kroki.io, or similar.
  • New agent family. This is a tool plugin (§3) — no registry additions.

3. Fit: Tool Plugin, Not Agent

Decision: Artifact tasks are a tool plugin registered in the analyzer tool registry, not a new agent family. Each kind is a tool under the artifact.* namespace. Callers: user slash commands dispatch directly to the tools; agents (designer, brainstorm, planner, code-analyzer) call them via their normal tool-calling loop.

Why tool plugin and not agent:

  • Deterministic shape. Each task has a fixed output kind and a known set of inputs. There is no planning, no decomposition, no multi-step review loop — the analyzer controller pattern would be overhead for no gain.
  • Natural for composition. Designer wants to embed an ER diagram in its output? It calls artifact.er. Code-analyzer wants a sequence diagram in a finding? Same thing. No new controller wiring per caller.
  • No new registry entry. AGENT_REGISTRY stays as-is; AgentFamily stays as-is. One less migration to do.

The tool plugin still participates in the same infrastructure the analyzer tool registry provides: closed tool list, schema validation, result caps, and (for artifacts that pull from the graph / DB) the same read-only guarantees.

4. Artifact Kinds

Each kind has a primary source (preferred) and a free-text fallback (always available). Tasks pick the source based on the input: if the user passes code references / entity ids, the kind's primary source fires; pure prose inputs route to free-text.

4.1 ER Diagram

Sources (priority order) live DB (phase-3 driver) → schema.prisma parse → Kuzu entity graph (entities + REFERENCES) → free-text
Inputs Optional connection id (artifact.er({ connection: 'primary', tables: ['users', 'orders'] })), or a list of entity ids from the graph, or a free-text description.
OutputMermaid erDiagram + standard ER template.
Typical use"Show me the ER for the orders schema", or embedded in a designer-authored data-model section.

4.2 Sequence Diagram

Sources (priority order) Kuzu CALLS traversal starting at a named entry point → free-text
Inputs Entry-point entity id + traversal depth (artifact.sequence({ entry: 'auth.login', depth: 3 })), or a free-text scenario description.
OutputMermaid sequenceDiagram + standard sequence template.
Typical use"Draw the call flow for login", or embedded in a code-analyzer finding.

4.3 Flow Diagram

Two sub-kinds under one tool — resolved by whether inputs reference code:

Code-flow sub-kind Kuzu-backed. Sources: function-level CFG approximation from the graph's CONTROLS / BRANCHES relations (when parser emits them) or a light tool-loop that reads the function body and emits a flowchart.
Process / business flow sub-kindFree-text only.
Inputs artifact.flow({ entity: 'payment.process', kind: 'code' }) or artifact.flow({ description: '...', kind: 'process' }).
OutputMermaid flowchart + standard flow template.

4.4 Deployment Diagram

Sources (priority order) docker-compose.yml parse → k8s manifests (kind: Deployment / Service / Ingress) → Terraform plan dump (phase 4+) → free-text
Inputs artifact.deployment({ fromFile: 'docker-compose.yml' }) or artifact.deployment({ description: '...' }).
OutputMermaid flowchart with deployment-styled nodes (see mermaid architecture/C4 beta, or a hand-styled flowchart) + standard deployment template.
Typical use"Draw the deployment for this repo's docker-compose", or embedded in a brainstorm/design doc.

4.5 UI Wireframe

SourcesFree-text description (phase 1). React component introspection via Kuzu (phase 4+).
Inputs artifact.wireframe({ description: '...', layout: 'desktop' | 'mobile' }).
OutputHand-generated SVG in a grid-based wireframe style + standard wireframe template. No Mermaid (Mermaid has no wireframe mode that fits).
Typical useGreenfield "sketch me a dashboard with these sections". Not for pixel-accurate mockups.

4.6 Extensibility

Kinds are registered in a single in-daemon registry. Adding a kind means: (a) a task module in src/insrc/agent/tasks/artifacts/<kind>.ts that produces the renderer source, (b) a template in templates/<kind>.html, (c) a slash-command binding, and (d) one registry entry. No framework changes.

5. Tool Surface

Registered under the artifact.* namespace on the analyzer tool registry (sibling of graph.*, db.*, fs.*). Each kind is one tool + a shared helper:

  • artifact.er(opts) → ArtifactResult
  • artifact.sequence(opts) → ArtifactResult
  • artifact.flow(opts) → ArtifactResult
  • artifact.deployment(opts) → ArtifactResult
  • artifact.wireframe(opts) → ArtifactResult
  • artifact.regenerate(artifactId, edits) → ArtifactResult — shared helper, §10.
  • artifact.list_templates() → TemplateInfo[] — introspection, used by the setup/customisation UI (§7).
interface ArtifactResult {
  id:         string;                   // ULID; stored as TodoItem meta (§10)
  kind:       ArtifactKind;             // 'er' | 'sequence' | 'flow' | 'deployment' | 'wireframe'
  source:     string;                   // Mermaid text / wireframe spec -- the editable source
  renderedHtml: {
    embedded:   string;                 // snippet relying on host renderer
    standalone: string;                 // self-contained with CDN script tags
  };
  title?:     string;
  metadata:   Record<string, string>; // generatedAt, provenance, sourceConnection, etc.
  warnings:   string[];                 // missing data, fallback to free-text, etc.
}

6. Generation Pipeline

Each artifact tool runs the same three-stage pipeline, with kind-specific modules at each stage:

invoke(kind, opts) | v [1. source-fetch] kind-specific | pulls from live DB / Prisma / Kuzu / config files / free-text | returns a structured model (tables, entities, nodes, steps, ...) v [2. source-render] kind-specific | emits Mermaid text (diagrams) or wireframe spec (SVG) | uses a small LLM pass (local model by default) for free-text inputs | or for tidying graph/DB-sourced models v [3. template-bind] shared | loads kind's template, substitutes slots, produces | { embedded, standalone } HTML v ArtifactResult --> returned to caller; persisted as a TodoItem (§10)

Stage details

  • Source-fetch is deterministic when a data source is available and LLM-backed only for free-text inputs. For an ER diagram against a live DB, this is a db.sql.describe call per table — no LLM.
  • Source-render is where Mermaid text / wireframe spec is produced. For structured inputs this is mostly a mechanical translation; for free-text it's a local LLM call with a strict-output prompt. Cloud models are available via the usual @mention override.
  • Template-bind is pure string substitution against the kind's template (§7). No LLM.
The LLM is only in stage 2 and only when the input is free-text or when the structured model needs a pass to pick labels / layout hints. An ER diagram driven from Prisma is fully deterministic — no LLM anywhere.

7. Templates

7.1 Template Shape

A template is a small HTML file with named slots. Substitution is plain string replacement — no templating DSL, no Handlebars. Slots are uppercase tokens wrapped in @@…@@ to keep them rare in real HTML: 

<!-- templates/er.html (bundled default) -->
<div class="insrc-artifact insrc-artifact-er" data-artifact-id="@@ID@@">
  <header>
    <h3>@@TITLE@@</h3>
    <span class="insrc-artifact-meta">@@META_LINE@@</span>
  </header>
  <pre class="mermaid">@@SOURCE@@</pre>
  @@LEGEND@@
  <footer class="insrc-artifact-footer">
    Generated by insrc · @@GENERATED_AT@@ · source: @@PROVENANCE@@
  </footer>
</div>
@@RENDERER_SCRIPT@@

Standard slots every template supports:

SlotRequired?Populated from
@@ID@@yesArtifactResult.id
@@TITLE@@yesArtifactResult.title, falls back to a kind-specific default
@@SOURCE@@yesArtifactResult.source (Mermaid text / SVG spec)
@@META_LINE@@noCompact one-line summary from ArtifactResult.metadata
@@LEGEND@@noOptional kind-specific legend; empty string when omitted
@@GENERATED_AT@@yesmetadata.generatedAt
@@PROVENANCE@@yesmetadata.provenance ("live DB: primary", "prisma/schema.prisma", "free-text", etc.)
@@RENDERER_SCRIPT@@yesFilled with renderer <script> tags in standalone mode; empty in embedded mode (§7.3)

Kinds may define additional kind-specific slots (e.g. @@NODE_STYLE_OVERRIDES@@ on deployment). Unknown slots in a user-supplied template are left in place; templates with missing required slots reject at load time with a clear error.

7.2 Override Layers

Templates resolve in this order (first match wins):

  1. <repo>/.insrc/artifacts/templates/<kind>.html — per-repo override (checked into the repo if the team wants a shared style).
  2. ~/.insrc/artifacts/templates/<kind>.html — per-user override.
  3. Bundled default — ships with the daemon at src/insrc/assets/artifacts/templates/<kind>.html.

Commands to manage user overrides:

  • insrc.editArtifactTemplate <kind> — opens the resolved template in the editor; if no override exists, copies the bundled default to the user-override path first.
  • insrc.resetArtifactTemplate <kind> — deletes the user-override, restoring the bundled default.
  • insrc.listArtifactTemplates — shows which layer each kind is resolving from.

7.3 Embedded vs Standalone Modes

Every render produces two HTML strings:

Embedded Standalone
Purpose Insrc-internal surfaces (chat, panes) where the host supplies the renderer once per session Export surfaces (copy-snippet, markdown export, paste into Confluence / README / email) that need to work with no external context
@@RENDERER_SCRIPT@@ Empty string Renderer loader (Mermaid via cdn.jsdelivr.net, or an offline-bundled inline script if artifacts.offline: true)
Size (typical ER diagram) ~0.5 KB ~1–2 KB + the renderer fetch on first load
Works offline? Yes (host supplies renderer) Only if artifacts.offline: true bundles the renderer inline at ~200 KB

Callers pick the mode at invocation:

  • The chat inline renderer and every insrc pane use embedded; they load Mermaid once on first artifact and cache it.
  • The "Copy snippet" action in the Artifacts Pane, markdown export (docs/analysis/<slug>.md in code-analyzer phase 4), and any agent that emits an artifact into a user-external surface use standalone.

7.4 Bundled Template Set

Phase 1 ships these bundled templates: 

src/insrc/assets/artifacts/templates/
├── er.html
├── sequence.html
├── flow.html
├── deployment.html
├── wireframe.html
└── _renderer.html        # shared standalone-mode <script> snippet, inlined by the binder

Each bundled template is short (~30 lines), VS-Code-dark-theme-aware via CSS custom properties inherited from the host when embedded, and prints as a self-contained card when standalone (fixed palette, no external stylesheet).

8. Rendering Stack

Decision: Mermaid for diagrams, hand-authored SVG for wireframes. Mermaid covers ER / sequence / flow / deployment cleanly and renders client-side from a <pre class="mermaid"> block. Wireframes don't fit Mermaid's model, so the wireframe task emits a grid-based SVG directly.

8.1 Mermaid

  • Runtime: mermaid (ESM bundle). Host surfaces load it once per pane / chat session and call mermaid.run() when new artifact nodes appear.
  • Version pinned in package.json; standalone-mode CDN reference points at the exact same pinned version.
  • Offline mode (artifacts.offline: true) inlines the Mermaid bundle into the standalone template instead of using CDN — bigger snippets but no network dependency. Default off; users on restricted networks opt in.

8.2 Wireframe SVG generator

  • A small module src/insrc/agent/tasks/artifacts/wireframe/render.ts takes a wireframe spec (JSON: rows, columns, sections, labels) and emits SVG with a consistent low-fi style (mono font, light-grey fills, dashed borders).
  • The spec is produced by the stage-2 LLM pass; the renderer itself is deterministic.
  • Example spec shape:
interface WireframeSpec {
  layout: 'desktop' | 'mobile' | 'tablet';
  rows: WireframeRow[];
}

interface WireframeRow {
  height: number | 'auto';
  cells: WireframeCell[];      // flex-distributed horizontally
}

interface WireframeCell {
  kind: 'header' | 'nav' | 'content' | 'sidebar' | 'footer' | 'placeholder';
  label?: string;
  widthRatio?: number;         // relative to siblings in the row
  children?: WireframeRow[];   // nesting allowed for composite regions
}

9. Iteration & Persistence

Every generated artifact is persisted as a TodoItem on an auto-created Artifacts list in the current session (owner: the calling agent's family, or 'chat' when fired by a user slash command). Reusing the TODO framework gives us free persistence, live-update events, and the existing todos pane surface as a listing of the session's artifacts. 

// TodoItem.meta for an artifact item
interface ArtifactItemMeta {
  kind:         ArtifactKind;
  source:       string;                 // Mermaid / wireframe spec -- editable
  renderedHtml: { embedded: string; standalone: string };
  title?:       string;
  metadata:     Record<string, string>;
  warnings:     string[];
  // iteration history
  revisions: {
    at:    string;                      // ISO
    edits: string;                      // user's natural-language edit request
    source: string;                     // full source at that revision
  }[];
}

Regenerate flow

  1. User / agent calls artifact.regenerate(artifactId, { edits: 'make the orders box green' }).
  2. Tool loads the item, re-runs stage 2 (source-render) with the prior source + edit request as prompt context, produces a new source.
  3. Stage 3 re-binds the template.
  4. Item's meta.source / meta.renderedHtml are updated; meta.revisions appends the old source + edit text.
  5. Framework emits itemUpdated; any surface showing the artifact re-renders in place.

Revision retention: last 5 revisions kept on the item; older ones evicted. The user can jump back to any kept revision via the item's kebab menu on the todos pane.

10. User Surface

Slash commands map one-to-one to the artifact tools:

Slash commandDispatch
/erd <args>artifact.er(...)
/seq <args>artifact.sequence(...)
/flow <args>artifact.flow(...)
/deploy-diagram <args>artifact.deployment(...)
/wireframe <args>artifact.wireframe(...)
/artifact-edit <id> <edits>artifact.regenerate(...)

Argument parsing is light: positional tokens become the primary input; key=value pairs populate the typed opts. Free-text after -- becomes the description field. Example: 

/erd users orders --
Include the many-to-many through table, but skip the audit fields.

The chat panel also surfaces a classifier-detected path — natural-language "draw the sequence for login" gets routed via the classifier to artifact.sequence when confidence is high. Low-confidence requests fall back to asking the user which task they meant (disambiguation prompt with the five kinds).

11. Agent Integration

Because artifact tasks are tools in the analyzer tool registry, any agent with tool-calling capability can produce an artifact in its own output. Phase 1 wires up only two callers — the other agents (designer, planner) are scheduled for a rewrite and will pick this up then.

Phase 1 callers

  • Code analyzer. Analyzer's tool registry includes artifact.*; a finding that benefits from a diagram (e.g. a trace result) can include one. The snippet is embedded in the analyzer's markdown report (embedded mode), or in the exported markdown (standalone mode).
  • Brainstorm. Theme-spec sections can embed a flow / ER / sequence / deployment diagram when the spec discusses one; Mermaid text is small enough to live inside the spec without bloating context. The presentation step's assembled document uses standalone-mode snippets so the saved artifact is portable.

Deferred callers

  • Designer and planner are not wired in phase 1. Both are slated for rewrites (tracked separately). When each rewrite lands, the integration is a single registry wire-up — the tools themselves don't need changes.

Agents call the tool exactly like any other: the tool contract (§5) is the integration surface, and the ArtifactResult.renderedHtml.embedded string is what the agent splices into its markdown output.

13. Security & Sanitisation

Artifact outputs are HTML and pass through surfaces that also render model output — the sanitisation posture has to be consistent with the rest of insrc.

  • Template text is trusted. Bundled and user-override templates are read from local disk and not sanitised — the user / maintainer wrote them.
  • Slot values are sanitised at bind time. @@SOURCE@@, @@TITLE@@, @@META_LINE@@, etc. come from LLM output or structured data and go through the same sanitiser the chat markdown renderer uses (strip <script>, on* attributes, javascript: URLs). The exception is @@SOURCE@@ for Mermaid: we escape < / > / & so the Mermaid runtime sees the raw text. For the wireframe SVG spec, the renderer emits SVG directly — no raw LLM text lands in the DOM attribute space.
  • Standalone mode uses a pinned CDN hash. The CDN <script> tag includes integrity="sha384-…" so a modified bundle on the CDN side is rejected by the browser.
  • No inline event handlers. Templates are reviewed to forbid onclick / onload / etc.; a linter in the test suite enforces this on both bundled and user templates at load time.
  • User-override trust model. User-supplied templates at ~/.insrc/… are trusted to the same extent as any other file in the user's home directory — we do not sanitise them but we do refuse to load a template containing inline event handlers (lint pass above).

14. Phasing

  1. Phase 1 — Core tool plugin + five bundled kinds.
    • artifact.* tools registered in the analyzer tool registry.
    • Bundled templates for er / sequence / flow / deployment / wireframe.
    • Mermaid integration (embedded + standalone modes, CDN with SRI hash).
    • Wireframe SVG generator.
    • Slash commands /erd, /seq, /flow, /deploy-diagram, /wireframe.
    • Persistence as TodoItems on an auto-created Artifacts list.
    • Data sources: Kuzu graph, schema.prisma parse, docker-compose.yml, k8s manifests, free-text.
    • Embed targets: chat inline + all existing insrc panes that render markdown.
  2. Phase 2 — Iteration surfaces.
    • artifact.regenerate tool + /artifact-edit slash command.
    • Revision history on artifact items (last 5 kept).
    • Dedicated ArtifactsPane — session-scoped list of artifacts with preview + source editor + regenerate button.
    • User-override template commands (insrc.editArtifactTemplate / resetArtifactTemplate / listArtifactTemplates).
  3. Phase 3 — Deeper data sources.
    • Live DB ER via the phase-3 db.sql.* driver.
    • Terraform plan parser for deployment.
    • Classifier-detected natural-language routing (§10).
    • Offline mode (artifacts.offline: true) with inlined Mermaid bundle.
  4. Phase 4 — Advanced sources + extensibility.
    • React component introspection for wireframes (Kuzu-backed).
    • CFG-based flow diagrams from the graph's BRANCHES relation.
    • Community-contributed template kinds + driver kinds via a small plugin contract.

15. Open Questions

Resolved decisions:

Question Resolution
Mermaid version policy Pinned. Exact version locked in package.json for the embedded bundle and echoed in the standalone-mode CDN <script> tag (with integrity="sha384-…"). Phase 1 pins at a v10 release — stable API, covers ER / sequence / flow / deployment / class / state cleanly. A version bump is an explicit PR with a diff review of any renderer-behaviour shift; not an auto-updated dependency. Re-evaluate the pin before phase 3 if the deployment kind wants architecture-beta (v11+). (§8.1)
Chat-transcript rendering of artifacts Custom chatArtifactWidget. A dedicated chat-side widget — mirroring the chatTodosWidget pattern from the todo-framework — intercepts artifact events on the chat event stream and renders each artifact into its own DOM node keyed by artifactId. The widget owns its Mermaid bootstrap (load once per session, call mermaid.run({ nodes: [el] }) per new artifact) and handles wireframe SVG inline. This keeps Mermaid out of the generic markdown path and lets the widget carry artifact-specific affordances (kebab menu: "Copy snippet / standalone", "Open in Artifacts Pane", "Regenerate with edits"). (§12)
Phase-1 agent auto-embedding Code analyzer + brainstorm only. Designer and planner are scheduled for rewrites; they pick up artifact integration then. No wiring effort on those two in phase 1. (§11)
Wireframe LLM layout constraints Unconstrained — let the model propose. No fixed layout vocabulary forced into the prompt; the model picks what fits the user's description. If the output misses the mark, the user iterates via the regenerate flow (§9) — "move the sidebar to the right", "drop the hero section", etc. Edit-and-regenerate is cheaper than guessing the right constraint set up front. (§8.2)

No remaining open questions.
