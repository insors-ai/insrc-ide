Chat RPC Design

Streaming agent communication over daemon IPC for VS Code extension

1. Problem Statement

The insrc agent currently runs in-process inside the CLI REPL (src/agent/index.ts). The REPL directly calls LLM providers for streaming, renders to stdout, handles gates via readline, and records turns via fire-and-forget RPC. This architecture does not support external clients like the VS Code extension because:

  • No chat RPC exists — the daemon has no method to accept a user message and run the agent
  • No streaming over IPC — the current protocol is single request → single response (newline-delimited JSON)
  • Gates are blocking — agent steps pause for user input via readline; no way to relay this to an external client
  • Session lifecycle is in-process — Session, ContextManager, LLM providers are all instantiated inside the REPL
Goal: Enable any client (VS Code extension, web UI, future mobile app) to run agent sessions via daemon RPC, with token-level streaming, gate relay, and full session lifecycle management.

2. Architecture Options

Option A: Agent in Daemon (Streaming IPC)

Move the agent loop into the daemon process. Upgrade the IPC protocol to support persistent connections with multi-message streaming.

  • Pro: Single process, single source of truth, clean architecture
  • Pro: Daemon already has DB access, indexer, config store
  • Con: Requires IPC protocol upgrade (breaking change)
  • Con: Long-running agent occupies daemon — concurrent sessions need careful management

Option B: Agent in Client (Extension Process)

Keep the agent running in the client process (extension host). Client calls daemon only for search/context/persistence (same pattern as CLI REPL).

  • Pro: No IPC protocol changes needed
  • Pro: Streaming is client-local (direct provider calls)
  • Con: Extension must bundle all agent code (~50+ files)
  • Con: Two processes running LLM calls (daemon embedder + client agent)
  • Con: Can't share agent state across multiple VS Code windows

Option C: Agent in Daemon (Message Queue Polling)

Agent runs in daemon. Client sends message, daemon enqueues response chunks into a per-session message queue. Client polls the queue for new messages.

  • Pro: No IPC protocol change — uses existing request/response
  • Pro: Multiple clients can poll the same session
  • Con: Polling latency (100-500ms between checks)
  • Con: Complex state management (queue lifecycle, cleanup)
Decision: Option A — Agent in Daemon with Streaming IPC. The daemon is the right home for the agent because it owns DB access, config, and session state. The IPC upgrade is a one-time investment that enables all future clients. Option B duplicates too much logic. Option C adds latency that degrades the streaming experience.

3. IPC Protocol Upgrade

3.1 Current Protocol

Client → Server: {"id":1,"method":"search.query","params":{"text":"foo"}}\n
Server → Client: {"id":1,"result":[...]}\n
[socket closes]

Single request, single response, socket closes after response. No streaming, no multi-message.

3.2 Upgraded Protocol: Persistent Streaming

Add a stream mode for methods that need multi-message responses. Standard RPC methods continue to work unchanged (backward compatible).

// Standard RPC (unchanged)
Client → Server: {"id":1,"method":"repo.list","params":{}}\n
Server → Client: {"id":1,"result":[...]}\n

// Streaming RPC (new)
Client → Server: {"id":2,"method":"chat.send","params":{"sessionId":"...","message":"..."},"stream":true}\n
Server → Client: {"id":2,"stream":"delta","data":{"text":"Hello"}}\n
Server → Client: {"id":2,"stream":"delta","data":{"text":" world"}}\n
Server → Client: {"id":2,"stream":"gate","data":{"gateId":"g1","title":"Apply changes?","actions":["approve","reject"]}}\n
// Client sends gate reply as a NEW request:
Client → Server: {"id":3,"method":"chat.reply","params":{"sessionId":"...","gateId":"g1","action":"approve"}}\n
Server → Client: {"id":3,"result":{"ok":true}}\n
// Streaming continues on original request id:
Server → Client: {"id":2,"stream":"delta","data":{"text":"Changes applied."}}\n
Server → Client: {"id":2,"stream":"done","data":{"summary":"..."}}\n
[socket stays open for duration of streaming request]

3.4 Wire Format

// Standard response (unchanged)
interface IpcResponse {
  id: number;
  result?: unknown;
  error?: string;
}

// Stream message (new)
interface IpcStreamMessage {
  id: number;                                    // matches original request id
  stream: 'delta' | 'progress' | 'gate' | 'checkpoint' | 'done' | 'error';
  data: unknown;                                 // payload varies by stream type
}

3.5 Server Changes (src/daemon/server.ts)

The IpcServer needs a new handler type for streaming methods:

// Current handler type (unchanged)
type RpcHandler = (params: unknown) => Promise<unknown>;

// New streaming handler type
type StreamHandler = (
  params: unknown,
  send: (msg: IpcStreamMessage) => void,   // push messages to client
  signal: AbortSignal,                      // cancellation
) => Promise<void>;                        // resolves when stream ends

// Handler registry
interface RpcHandlers {
  [method: string]: RpcHandler | StreamHandler;
}

// Differentiation: if request has `"stream": true`, use StreamHandler
// Server keeps socket open until handler resolves or signal aborts

4. Chat Session Lifecycle

4.1 Session Management in Daemon

The daemon manages a pool of active chat sessions. Each session holds the agent's Session object (context manager, providers, turn history).

// In-memory session pool (daemon/chat-sessions.ts)
interface ActiveSession {
  id: string;
  session: Session;                    // from src/agent/session.ts
  channel: DaemonChannel;             // new Channel implementation
  abortController: AbortController;
  createdAt: number;
  lastActivityAt: number;
  agentRunning: boolean;              // true while runAgent() is in progress
}

const sessions = new Map<string, ActiveSession>();

4.2 RPC Methods

MethodTypeDescription
chat.start Standard Create a new session. Returns { sessionId, repo }. Initializes Session object, context manager, providers.
chat.send Streaming Send a user message. Runs classify → route → agent. Streams back deltas, progress, gates, done/error.
chat.reply Standard Reply to a gate. Unblocks the waiting agent step.
chat.cancel Standard Cancel a running agent. Triggers AbortSignal.
chat.resume Streaming Resume an agent from checkpoint. Streams like chat.send.
chat.close Standard Close a session. Persists L2 summary, cleans up resources.
chat.list Standard List active sessions with their status.

4.3 DaemonChannel — New Channel Implementation

A new Channel implementation that bridges the agent framework to the IPC stream. Replaces ReplChannel (terminal) for daemon-hosted agents.

// daemon/channel.ts
class DaemonChannel implements Channel {
  private sendFn: (msg: IpcStreamMessage) => void;
  private gateResolvers = new Map<string, (reply: ReplyPayload) => void>();
  private signal: AbortSignal;

  constructor(requestId: number, sendFn: (msg: IpcStreamMessage) => void, signal: AbortSignal) {
    this.sendFn = sendFn;
    this.signal = signal;
  }

  // Called by agent steps via ctx.emit()
  send(msg: AgentMessage): void {
    switch (msg.kind) {
      case 'emit':
        this.sendFn({ id: this.requestId, stream: 'delta', data: msg.payload });
        break;
      case 'progress':
        this.sendFn({ id: this.requestId, stream: 'progress', data: msg.payload });
        break;
      case 'checkpoint':
        this.sendFn({ id: this.requestId, stream: 'checkpoint', data: msg.payload });
        break;
      case 'done':
        this.sendFn({ id: this.requestId, stream: 'done', data: msg.payload });
        break;
      case 'error':
        this.sendFn({ id: this.requestId, stream: 'error', data: msg.payload });
        break;
    }
  }

  // Called by agent steps via ctx.gate() — blocks until client sends chat.reply
  async gate(msg: AgentMessage<GatePayload>): Promise<ReplyPayload> {
    const gateId = msg.payload.gateId;
    this.sendFn({ id: this.requestId, stream: 'gate', data: msg.payload });

    // Block until resolveGate() is called (from chat.reply handler)
    return new Promise<ReplyPayload>((resolve, reject) => {
      this.gateResolvers.set(gateId, resolve);
      this.signal.addEventListener('abort', () => reject(new Error('cancelled')), { once: true });
    });
  }

  // Called by chat.reply RPC handler
  resolveGate(gateId: string, reply: ReplyPayload): boolean {
    const resolver = this.gateResolvers.get(gateId);
    if (!resolver) return false;
    this.gateResolvers.delete(gateId);
    resolver(reply);
    return true;
  }

  onMessage(handler: (msg: AgentMessage) => void): void {
    // Cancel messages handled via AbortSignal, not onMessage
  }
}

6. Streaming LLM Integration

6.1 Provider Streaming Through DaemonChannel

The agent steps call provider.stream() which yields tokens. These must be relayed through the DaemonChannel to the client. Two approaches:

Approach A: Step-level streaming (simpler)

Each step that calls a provider emits the tokens via ctx.emit():

// Inside a step's run() method:
const stream = provider.stream(messages, opts);
let fullText = '';
for await (const delta of stream) {
  fullText += delta;
  ctx.emit(delta, true);  // stream: true → relayed as stream:delta
}
// Step uses fullText for further processing

This is the current pattern used in the REPL (writing to stdout). The change is minimal — ctx.emit() routes through DaemonChannel instead of stdout.

Approach B: Provider-level streaming hook (transparent)

Wrap the provider to automatically relay tokens:

function streamingProvider(provider: LLMProvider, channel: DaemonChannel): LLMProvider {
  return {
    ...provider,
    async *stream(messages, opts) {
      for await (const delta of provider.stream(messages, opts)) {
        channel.send(createMessage(agentId, runId, 'emit', { text: delta, stream: true }));
        yield delta;
      }
    },
    // complete() remains non-streaming
  };
}
Decision: Approach A (step-level). Each step already controls when to stream vs batch. Some steps intentionally don't stream (e.g., tool calls, internal reasoning). Approach B would leak internal LLM calls to the UI. Steps should explicitly choose what to emit.

7. Concurrency Model

7.1 One Agent Per Session

Only one chat.send can be active per session at a time. If a second chat.send arrives while the agent is running, return an error:

{ "error": "agent already running on this session" }

7.2 Multiple Sessions

The daemon can host multiple active sessions concurrently (different repos or contexts). Each session has its own Session object, providers, and DaemonChannel. LLM calls are naturally concurrent (Ollama handles its own queuing, Claude API is async).

7.3 Session Timeout

Sessions idle for >30 minutes are automatically closed (persist L2 summary, release resources). The chat.send on a closed session returns an error suggesting chat.start.

8. Implementation Plan

Phase 1: IPC Protocol Upgrade

Modify src/daemon/server.ts to support streaming handlers.

  • Add StreamHandler type alongside existing RpcHandler
  • Detect "stream": true in request to select handler type
  • Keep socket open during streaming, write multiple newline-delimited messages
  • Add AbortController per streaming request
  • All existing handlers unchanged — backward compatible

Phase 2: DaemonChannel

Create src/daemon/channel.ts — new Channel implementation.

  • Implements send() → maps AgentMessage kinds to IpcStreamMessage
  • Implements gate() → sends gate message, returns Promise that blocks until resolveGate()
  • Gate resolution via chat.reply RPC → looks up session → calls channel.resolveGate()

Phase 3: Session Pool

Create src/daemon/chat-sessions.ts — manages active sessions.

  • createSession(repo) → initializes Session, providers, returns sessionId
  • getSession(id) → returns ActiveSession or null
  • closeSession(id) → persists, cleans up
  • Idle timeout (30min) with automatic cleanup

Phase 4: Chat RPC Handlers

Add handlers in src/daemon/index.ts:

  • chat.start — standard handler, creates session
  • chat.send — streaming handler, runs classify → route → agent
  • chat.reply — standard handler, resolves gate
  • chat.cancel — standard handler, aborts agent
  • chat.close — standard handler, closes session
  • chat.list — standard handler, lists active sessions

Phase 5: Extension RPC Client Upgrade

Update vscode-insrc/src/daemon/rpc.ts:

  • Add callStream(method, params, onMessage) — keeps socket open, fires callback per message
  • Returns when stream:done or stream:error received
  • Supports AbortSignal for client-side cancellation

Phase 6: Refactor REPL to Use Chat RPC

Update src/agent/index.ts to optionally use daemon-hosted sessions:

  • CLI REPL can either run in-process (current) or connect to daemon via chat RPC
  • --daemon flag to use daemon-hosted session (same IPC as extension)
  • Default: in-process (no change for existing CLI users)

9. VS Code Extension Integration

The chat panel (Segment 5) uses the streaming RPC client:

// Extension sends message
const sessionId = await rpc.call<string>('chat.start', { repo: currentRepo });

// Streaming send
await rpc.callStream('chat.send', { sessionId, message: userText }, (msg) => {
  switch (msg.stream) {
    case 'delta':
      chatPanel.appendText(msg.data.text);        // Token-by-token render
      break;
    case 'progress':
      chatPanel.showProgress(msg.data.message);    // Step indicator
      break;
    case 'gate':
      chatPanel.showGate(msg.data);                // Render approve/reject UI
      break;
    case 'done':
      chatPanel.finishMessage(msg.data.summary);   // Complete
      break;
    case 'error':
      chatPanel.showError(msg.data.error);         // Error display
      break;
  }
});

// Gate reply (from user clicking approve/reject in chat panel)
await rpc.call('chat.reply', { sessionId, gateId, action: 'approve' });

// Cancel (from user clicking stop button)
await rpc.call('chat.cancel', { sessionId });
