/plan meta-task — template design

Status: DRAFT · Scope: design only — no code · Implements: M4 of meta-tasks framework · Replaces: src/insrc/agent/planner/

First per-template design doc. Sets the pattern for /design, /implement, /migrate: each one's doc lives at design/meta-task-<name>.html and covers (a) what the existing path does today, (b) what we keep / reshape / drop, (c) the new step list with phase-1 fetcher needs + phase-2 prompts + acceptance, (d) the deliverable contract, (e) consumer interop, (f) open questions.

1. Overview

/plan takes a free-form planning request and produces a structured implementation plan: an ordered list of steps with dependencies, complexity hints, file references, and (optionally) domain-specific data for implementation / test / migration variants. It's the "structured approach instead of free-form prompt" layer the user asked for at the design level (meta-tasks §1).

The existing plannerAgent (in src/insrc/agent/planner/, 1860 LOC across ten files) already does this work. Its 8-step pipeline produces a typed Plan<T> object, validates dependencies, enriches with domain data, and serializes to a round-trippable markdown format. The legacy planner's prompts, validators, and markdown serializer are reusable assets that this design preserves.

What this design changes is the orchestration shape: the 8 step-machine steps with inline user gates become a 6-step meta-task with phase-1 demand-pull context + phase-2 cloud-LLM execution per step. User gates fold into the meta-task framework's plan-revision flow (§7), not as inline per-step pauses.

2. Scope & non-goals

Scope (M4)

  • Ship /plan as a usable meta-task template via the chat slash command and the sub-meta-task primitive.
  • Reuse legacy markdown.toMarkdown + fromMarkdown for round-trippable deliverables — the meta-task deliverable string IS the canonical plan markdown.
  • Reuse legacy engine.detectCycles + detectBlockedSteps as deterministic validators inside the validate step's phase-2.
  • Port the legacy prompts (ANALYZE_SYSTEM, DRAFT_SYSTEM, ENHANCE_SYSTEM, DETAIL_SYSTEM, SEARCH_PLAN_SYSTEM) verbatim into the new template's phase-2 prompts.
  • Wire the new /plan meta-task to the chat surface (already routed via meta-tasks M2.8 — /plan is in the slash-command regex).

Non-goals (M4)

  • Do not edit the legacy src/insrc/agent/planner/ module. The new /plan template lives entirely under src/insrc/meta-task/templates/plan.ts and reuses what it can via imports, not edits. Per user direction at design time: "don't try to edit the current planner, extract the design from it and create a new planner module."
  • Do not migrate Delegate, CLI, or chat-handler dispatch. Those consumers stay on plannerAgent until they're individually migrated. Both paths coexist briefly during the migration window. See §7 for migration sequencing.
  • Per-step interactive user gates (the legacy validate-plan / validate-details gates). Folded into meta-task §7 plan-revision (M5).
  • Domain-data variants beyond what the legacy planner emits (ImplementationStepData, TestStepData, MigrationStepData). Same shapes; no schema additions.

4. Step list

Six steps, each one phase-1 + phase-2 cycle. Where the legacy planner had 8 steps + 3 gates, the new template has 6 steps + 0 gates — the framework's plan-revision (§7 below) handles user input post-completion. Phase-1 contracts and phase-2 prompts are spelled out per step so the implementation is mechanical.

#StepPhase 1 typical requestPhase 2 prompt sourcePhase 2 output expectations
P1analyze { kind: 'sufficient' } — the intent is in the step's prompt body; no corpus needed ANALYZE_SYSTEM (legacy) JSON wrapped in { kind: 'deliverable', body } where body is the legacy schema: { planType, goals, constraints, scope }
P2gather semantic + entities + memory. Cloud picks terms based on P1's analysis SEARCH_PLAN_SYSTEM as phase-1 ask helper; phase-2 prompt synthesizes findings into a "codebase context summary" Markdown body summarizing the matched entities + memory snippets + config context. Used as input to P3.
P3draft deliverable (P1 analysis) + deliverable (P2 gather) DRAFT_SYSTEM — or CONDENSED_SYSTEM when P2's gather yielded little (the template's helper picks based on chunk byte-count) JSON array of raw steps (legacy RawStep[] shape: { title, description, checkpoint?, complexity?, dependsOnIdx?, fileHint? }), then refined via a second phase-2 call using ENHANCE_SYSTEM
P4validate { kind: 'sufficient' } None — this is a deterministic check, no LLM call Calls engine.detectCycles + detectBlockedSteps. Emits a deliverable with: pass/fail, cycle path if any, blocked-step list if any. On cycle/block issues, emits { kind: 'abort', resolution: 'plan-revisable' } — M5's revision flow re-invokes the planner
P5detail deliverable (P3 draft) + semantic (per step description, when scope is medium/large — cloud decides) DETAIL_SYSTEM (legacy) JSON array of { stepIndex, data } enrichments. For generic plans this step skips (emits { kind: 'deliverable', body: '(skipped)' })
P6synth deliverable (P3 draft) + deliverable (P5 detail) None — deterministic. Helper assembles a Plan object from P1-P5, calls markdown.toMarkdown(plan), returns the markdown as the deliverable body { kind: 'deliverable', body } where body is the canonical toMarkdown output. This IS the template's deliverable contract

4.1 P1 analyze

Maps the legacy analyzeRequestStep. Phase 2 calls the cloud with ANALYZE_SYSTEM as the system prelude and the user's intent as the user message. The cloud emits a JSON object the helper validates against the { planType, goals, constraints, scope } shape; on malformed JSON the meta-task framework's retry-with-feedback path kicks in automatically.

Phase 1 is { kind: 'sufficient' } because the entire planning intent is in the user's message; no corpus lookup is needed at this stage. Templates can override on a per-step basis if they want classification to consider memory; in M4 we keep it stateless.

4.2 P2 gather

Maps the legacy gatherContextStep. This is where the meta-task framework's demand-pull context model earns its keep: the cloud LLM (now informed by P1's analysis) picks its own search terms instead of the legacy planner's hard-coded 2-stage search pipeline.

Phase 1: the cloud emits { kind: 'context-needed', requests: [...] }, typically with 2-4 slot requests: 

{
  "kind": "context-needed",
  "requests": [
    { "kind": "semantic",
      "query": "user registration endpoint validation",
      "topK": 10,
      "over": ["entities"] },
    { "kind": "entities",
      "names": ["UserService", "AuthMiddleware"],
      "repos": ["/Users/.../repo"] },
    { "kind": "memory",
      "query": "prior auth refactor decisions" }
  ],
  "intent": "find existing entry points + relevant entity definitions"
}

Phase 2 then synthesises a free-form "codebase context summary" markdown. This block becomes one of the deliverable inputs P3 pulls via the deliverable slot.

Config context (conventions/feedback/templates) is loaded by the template's helper code and injected as additional input to phase 2. Same flow as the legacy planner's loadConfigContext.

4.3 P3 draft

Maps the legacy draftPlanStep's two-stage pattern (sketch → refine). Phase 2 makes two cloud calls:

  1. Sketch with DRAFT_SYSTEM (or CONDENSED_SYSTEM when phase-1 chunks total < 1 KB of useful context).
  2. Refine the sketch with ENHANCE_SYSTEM, passing the sketch back as user-message input.

Both stages emit a JSON step array. The framework's per-step phase-2 contract gets one terminal deliverable; the sketch → refine pattern lives inside the template's helper which makes both calls before returning. This is template-internal detail; from the orchestrator's perspective P3 is one step.

4.4 P4 validate

Deterministic. The template's helper takes the P3 step array, builds a Plan object via the legacy buildPlan helper (which we copy in), runs detectCycles + detectBlockedSteps, and emits one of:

  • Pass: { kind: 'deliverable', body: '' } with the plan summary + "no dependency issues found". Orchestrator advances to P5.
  • Fail: { kind: 'abort', resolution: 'plan-revisable', reason: 'cycle detected: ...', hint: 'consider re-ordering steps so X precedes Y' }. The framework's M5 revision flow surfaces this to the user; their feedback drives the re-draft.

Phase 1 is { kind: 'sufficient' }. No cloud LLM call in phase 2 either — this is the place the framework lets a "pure helper" step shine. The orchestrator's per-step contract doesn't require an LLM call; phase 2 can be a synchronous function.

Implementation note: the meta-task framework's current orchestrator assumes every phase-2 is a cloud-LLM call. P4 will require adding a "no-LLM step" escape where the template's plan-builder can supply a synchronous phase-2 implementation. Tracked as open question O1.

4.5 P5 detail

Maps the legacy detailStepsStep. Phase 1 typically pulls the P3 draft deliverable plus optional per-step semantic searches. Phase 2 uses DETAIL_SYSTEM with the plan type (implementation / test / migration / generic) folded into the prompt. Generic plans skip this step entirely (the template's helper checks planType === 'generic' and emits a sentinel deliverable so P6 knows to skip the detail-merge).

4.6 P6 synth

Deterministic, no LLM call (same caveat as P4). The helper:

  1. Pulls P3 draft & P5 detail deliverables.
  2. Merges P5 enrichments into the Plan<T> object.
  3. Calls markdown.toMarkdown(plan) (legacy import).
  4. Emits { kind: 'deliverable', body: markdown }.

The framework writes the deliverable to ~/.insrc/meta/<id>/step-06-synth.deliverable.md automatically. Because P6 is the last step the same body is mirrored into synthesis.md and into the TodoList body so the report pane auto-opens with the rendered plan.

5. Deliverable contract

The /plan template's deliverable is round-trippable markdown. Specifically: the synthesis body is produced by markdown.toMarkdown(plan) and can be parsed back into a typed Plan<T> via markdown.fromMarkdown(body). This is the load-bearing design choice that lets consumers (Delegate, future others) reuse the structured shape without the meta-task framework needing a new "structured deliverable" contract.

Why markdown-only (vs. a new structured-deliverable framework feature)

  • The legacy planner already uses markdown as its serialized shape (toMarkdown + fromMarkdown). Adding a parallel structured-JSON path would duplicate the contract.
  • Meta-task framework changes stay zero. The framework's Phase2Out.deliverable is already { body: string }; no new structured? field is required.
  • The report pane renders markdown well. The user sees the plan as a properly-formatted document, not a JSON dump.
  • Consumers do one round-trip. Delegate's migration becomes const plan = fromMarkdown(result.deliverables.get(6)!); that's it.

7. Plan revision + user feedback

The legacy planner has three inline user gates with edit-round counters (max 3) and a recordFeedback sink wired into local-LLM-driven memory. The new template drops these in favor of the meta-task framework's M5 revision flow:

  • No per-step pause-for-user. Steps run end-to-end without interactive gates. The user sees the final deliverable in the report pane.
  • Revision via M5 abort gate. When P4 detects a cycle, or when the user wants changes post-completion, the framework's "Adjust plan" / "New plan" actions fire. Those re-invoke /plan with the user's feedback injected into the scope.
  • Edit-round counter retained, semantically. The framework's maxPlanRevisions: 2 cap (meta-tasks §7.2) plays the same role as the legacy MAX_EDIT_ROUNDS = 3.
  • Feedback capture deferred. The legacy recordFeedback hook (writes user gate text into a config-store namespace for future search) has no analog in the meta-task framework yet. Open question O4 — lands as a framework extension if feedback capture proves load-bearing for plan quality.
The legacy planner had a "re-draft with rejection feedback" loop. When the user rejected a plan at validate-plan, the next iteration's draft prompt got the user's feedback appended. The meta-task framework's M5 flow achieves the same outcome through its plan-revision sub-task invocation (the user's feedback feeds into P1 analyze's prompt). Same semantics, different mechanism.

8. Post-approval routing

Once the user approves a plan, the structured deliverable needs to land in places the user and the team can act on: a canonical plan document (always), and external task trackers like Jira / GitHub Issues (opt-in per invocation, only if configured). The framework provides the integration plumbing; the /plan template supplies the per-system mapping.

8.1 Approval action

M5's user-driven gate (meta-tasks §7.1) is extended with an Approve action alongside Adjust plan / New plan / Retry / Abort. On approve:

  1. The meta-task closes with outcome: 'completed'.
  2. The framework writes the plan document to disk per user settings (§8.2).
  3. The report pane re-renders with a new "Export to…" section listing every configured external integration. External pushes are not bundled into the approve modal — they're a follow-up action.

Why post-approval rather than part-of-approval: the approve modal already carries the revision options; adding integration target selection in the same surface creates decision overload. Separation lets the user review the canonical plan first, then decide whether to push outward.

8.2 Plan document output

Always produced on approve. Two settings drive output: 

# ~/.insrc/settings.yaml (sketch)
output:
  format:           markdown          # markdown | html
  defaultLocation:  project           # project | ~/Documents/insrc-plans/ | <abs path>
  filenamePattern:  plan-{intent-slug}-{date}.md

Default behavior: writes the plan document next to the project root (configurable). Format picks between the existing markdown.toMarkdown output and an HTML renderer (the template adds renderHtml alongside renderMarkdown — same shape, different output).

The plan document is canonical — even if external pushes are skipped, the file is the record. External targets are downstream replications, not replacements.

    <h3 id="layering">8.4 Framework / template layering</h3>
    <p>
      The framework provides the registry + adapter contract; templates declare per-integration
      mappings. Adding a new integration (e.g., Linear) requires a framework-side adapter; using
      that integration with /plan requires the template to provide a mapping function.
    </p>

<pre><code>// Framework
interface ExternalIntegration {
  readonly id:           'jira' | 'github' | 'linear' | string;
  readonly displayName:  string;
  readonly isConfigured: () => boolean;
  readonly listTargets:  () => Promise<TargetOption[]>;
  readonly emit:         (payload: unknown, target: string) => Promise<EmissionReceipt>;
}

interface MetaTaskTemplate {
  // ...
  exportAdapters?: {
    readonly file?:    (data: unknown, format: 'markdown' | 'html') => string;
    readonly jira?:    (data: unknown) => JiraPayload;
    readonly github?:  (data: unknown) => GithubPayload;
    // ... one entry per integration the template supports
  };
}</code></pre>

    <p>
      Integration auth + per-instance defaults live in
      <code>~/.insrc/integrations/<id>.yaml</code>. Tokens / secrets land in the OS
      keychain via the same mechanism cloud-provider API keys use (Model Providers pane).
    </p>

    <h3 id="jira-github-mapping">8.5 Jira / GitHub mapping</h3>

    <p><strong>Jira</strong> — <code>plan.steps[i]</code> → Jira issue:</p>
    <ul>
      <li>Issue type from <code>(category, subCategory)</code>: <code>implementation/bugfix</code>
        → Bug; <code>implementation/new-feature</code> → Story;
        <code>migration/*</code> → Task; <code>test/*</code> → Test.</li>
      <li>Step dependencies → <code>blocks</code> / <code>blocked-by</code> links.</li>
      <li>Step metadata (<code>fileHint</code>, <code>complexity</code>) → custom fields
        when present.</li>
      <li>Sub-steps (<code>step.subSteps</code>) → Jira sub-tasks under their parent.</li>
      <li>Plan title → optional epic (user setting:
        <code>jira.createEpic: true | false</code>).</li>
    </ul>

    <p><strong>GitHub Issues</strong> — <code>plan.steps[i]</code> → GitHub issue:</p>
    <ul>
      <li>Labels from <code>(category, subCategory)</code>: e.g., <code>category:implementation</code>,
        <code>type:bugfix</code>, <code>complexity:high</code>.</li>
      <li>Milestone scoped to the Plan: <code>milestone: <plan title></code>.</li>
      <li>Cross-issue dependencies via task list / mentions
        (GitHub's native blocking is project-level).</li>
      <li>Sub-steps → nested task list within parent's issue body.</li>
    </ul>

    <p class="muted">
      Mapping shapes are template-internal; integrations themselves are reusable. /design would
      have different adapters mapping design sections to Confluence pages or wiki entries; the
      framework's ExternalIntegration contract stays unchanged.
    </p>

    <h3 id="receipts">8.6 Receipts + idempotency</h3>
    <p>
      Each external emission returns an <code>EmissionReceipt</code> that the framework appends
      to <code>~/.insrc/meta/<id>/exports.json</code>:
    </p>

<pre><code>{
  "exports": [
    {
      "integration": "jira",
      "target":      "ENG",
      "emittedAt":   "2026-06-17T19:42:11Z",
      "items": [
        { "stepId": "step-001", "externalId": "ENG-1247", "url": "https://insors.atlassian.net/browse/ENG-1247" },
        { "stepId": "step-002", "externalId": "ENG-1248", "url": "..." },
        // ...
      ]
    }
  ]
}</code></pre>

    <p>
      Three uses for the receipts:
    </p>
    <ul>
      <li><strong>Report pane re-rendering</strong>: shows links back to created tickets
        alongside the plan steps after export.</li>
      <li><strong>Idempotency</strong>: re-running export for an already-exported plan is a no-op
        for steps that already have a receipt; new steps (if the plan was revised after first
        export) get pushed; existing items get reconciled (state-sync, not re-create).</li>
      <li><strong>Cleanup</strong>: a future "abandon this plan" flow can revoke / close the
        created tickets via the receipt list.</li>
    </ul>
