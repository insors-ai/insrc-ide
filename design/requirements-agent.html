Requirements Agent

Iterative scope decomposition + story authoring, persisted as HTML/MD under <project>/requirements/, optionally pushed to GitHub Issues + Projects v2.

1. Overview

The Requirements agent is a new, standalone insrc agent dedicated to producing business-facing requirements documentation. It differs from the Designer agent (which produces architectural design output from extracted requirements) in both audience and output shape:

AgentAudienceOutputFlow
Designer Engineering Architecture / component sketches Single-pass: extract → sketch → detail → assemble
Requirements (new) Business + engineering Epic + Story documents in HTML/MD Iterative: scope → breakdown → main doc → per-sub-section stories
Planner Engineering Implementation plan (how to build) Unchanged; runs after requirements are set

Core responsibilities:

  1. Scope sizing. Classify a prompt as standalone-feature vs. too-broad (needs breakdown). For the broad case, propose an Epic → Sub-epic breakdown iterated with the user.
  2. Existing-workspace awareness. On a prompt like "Build new matching module for shipping invoices against contracts," the agent queries the knowledge graph to understand already-indexed repos and surfaces structural context to the user before breaking down scope.
  3. Main-document authoring. Iterate with the user to produce the top-level Epic doc (overall scope, sub-section index, personas, system NFRs, serves as the TODO tracker).
  4. Per-sub-section story authoring. One sub-section at a time (user's call to handle in new chats), generate the story list, iterate to finalize, then produce full story documents one by one.
  5. Optional push. When a sub-section finishes, offer to push stories to GitHub Issues + Projects v2 (Jira mapping designed but delegated-tool not yet implemented).

3. Intent Routing

Today requirements intent is routed to the Designer agent in src/insrc/agent/index.ts:540-560 via runDesignerAgent(). That path is removed; requirements now flows to the new requirementsAgent.

Breaking change for users who were relying on requirements routing to Designer. The user-visible difference is meaningful: the old path produced architecture sketches; the new path produces Epic / Story docs. Note in release notes. 4.1 Resolution

  • requirements.dir — relative to the active repo's root. Default: requirements. Resolves to <repoPath>/requirements/. Absolute paths allowed (discouraged; breaks repo-portability).
  • requirements.format — "html" | "md". Default: "html". Applies to all document kinds (main, sub-section, story).
  • Project-level override: <repoPath>/.insrc/config.json can set both fields. Merge order: project > global > defaults. Follows the config-hierarchy design (config-management.html).

5. ID Scheme & File Naming

5.1 Hashing function

function reqId(title: string): string {
  const norm = title
    .toLowerCase()
    .replace(/[^a-z0-9]+/g, '-')
    .replace(/^-|-$/g, '');
  return sha256(norm).slice(0, 6);          // 6 hex chars
}

function storyId(title: string, parentId: string): string {
  const norm = (parentId + '|' + title.toLowerCase())
    .replace(/[^a-z0-9|-]+/g, '-');
  return sha256(norm).slice(0, 12);         // 12 hex chars
}

Hashing on normalized title gives determinism (same title → same ID across re-runs) and collision-free enough at 6/12 hex (166 = 16.7M; 1612 = 2.8e14). Title changes produce a new ID; the agent maintains a rename table (see §8) so references survive renames.

5.2 File naming

Spec: REQ-[id]-[name-32 chars max].[ext].

  • [id] — 6-hex hash above.
  • [name-32] — lowercase-kebab of the title, trimmed to 32 chars. No trailing hyphen.
  • [ext] — html or md per requirements.format.

Examples:

REQ-ab12cd-accounts-payable-platform.html
REQ-def345-ingestion.html
REQ-ghi678-classification.html
REQ-jkl901-document-type-detection.html
REQ-mno234-extraction.html

Stories live inline in their sub-section's HTML/MD file, NOT as separate files on disk (each story is a section within the parent sub-section doc). Story IDs are referenced by other stories (dependencies) and by the GitHub push step.

7. Agent Steps

The agent follows the insrc step-based framework (agent-framework.html). Nine steps, most with gates. The runner checkpoints state after every step so long sessions are resumable.

(brainstorm handoff OR user prompt) │ ▼ ┌───────────────────┐ │ scope-analyze │ local LLM + knowledge-graph query └────────┬──────────┘ ▼ ┌───────────────────┐ │ breakdown-draft │ local LLM proposes sub-epic list └────────┬──────────┘ ▼ ┌───────────────────┐ │ breakdown-review │ cloud provider validates + enhances └────────┬──────────┘ ▼ ┌───────────────────┐ │ breakdown-gate │ EditorPane accordion review └────────┬──────────┘ │ approved ▼ ┌───────────────────┐ │ scaffold │ create folder + placeholder HTML/MD files └────────┬──────────┘ ▼ ┌───────────────────┐ │ main-doc-author │ draft + cloud review + chat gate └────────┬──────────┘ ▼ ┌───────────────────┐ │ sub-section-plan │ list sub-sections with deep-link buttons └────────┬──────────┘ │ (each sub-section handled in a new chat) ▼ (new chat) │ ▼ ┌───────────────────┐ │ story-list-author │ EditorPane accordion review of story titles └────────┬──────────┘ ▼ ┌───────────────────┐ │ story-detail-loop │ per-story detail + chat gate + NFR harvest └────────┬──────────┘ ▼ ┌───────────────────┐ │ nfr-consolidate │ module-level NFR consolidation └────────┬──────────┘ ▼ ┌───────────────────┐ │ offer-push │ "Push to GitHub?" gate └────────┬──────────┘ ▼ accepted ┌───────────────────┐ │ delegate-push │ delegate agent runs the GitHub push sequence └───────────────────┘

7.1 scope-analyze

Input: user prompt (or input.brainstormSpec from handoff).

  1. Query the knowledge graph for semantically-related entities across all registered repos (top-20 entities via vector search).
  2. Compute a rough scope-size heuristic from the prompt (word count, keyword density for broad-scope signals like "platform", "system", "suite").
  3. Classify into one of: standalone-feature (single module, no breakdown), extension (extends existing code; surface the relevant entities), broad (needs breakdown).
  4. Emit a progress message summarizing the classification and any relevant existing-code context.

7.2 breakdown-draft + breakdown-review + breakdown-gate

For broad scopes:

  • breakdown-draft (local LLM): produce sub-epic list with title, one-line description, and estimated dependency order.
  • breakdown-review (cloud provider): validate the list for completeness, overlap, missing domains, and dependency correctness. Output: same list structure, enhanced.
  • breakdown-gate (EditorPane accordion): user approves/rejects/edits each sub-epic, bulk approve-all, bulk reject-all. Rejections with feedback loop back to breakdown-draft.

For standalone-feature: skip breakdown. Agent proceeds directly to main-doc-author with a single-section scope.

For extension: breakdown-draft receives the existing-code context in its prompt so sub-epics align with the existing module boundaries (e.g., a new "Matching" sub-epic that uses the existing "Contracts" module).

7.3 scaffold + main-doc-author

scaffold: creates the requirements/ folder (if missing), generates placeholder REQ files for each approved sub-epic (title + skeleton + empty stories section), seeds _index.json with all parent/child links. Placeholders are committed to disk before the user starts detailing anything so they're stable reference points.

main-doc-author: draft → cloud review → user gate for the Epic document. Content defined in §8.1.

7.4 sub-section-plan

After the main doc lands, the agent emits a sub-section list with one "Start chat for this sub-section" action per row. The action pre-fills a new chat session with:

@requirements continue REQ-def345 (parent: REQ-ab12cd, kind: sub-epic)

When that new chat starts, the agent skips scope-analyze and breakdown (already done), loads the sub-epic doc + parent context, and proceeds to story-list-author.

7.5 story-list-author + story-detail-loop + nfr-consolidate

  • story-list-author: local LLM generates story titles + one-line narrative (functional capabilities only, not implementation). Cloud review enhances. EditorPane accordion review.
  • story-detail-loop: for each approved story title:
    • local LLM produces full 12-section story doc
    • cloud provider reviews
    • chat gate with approve/reject/feedback (single-story view uses the standard chat response UX)
    • any module-NFR impacts are collected into a running list on the agent state
  • nfr-consolidate: once all stories settle, cloud provider reads the collected NFR impacts + existing module NFRs and proposes a deduplicated, merged set. User gates the consolidated list.

8. Document Formats

Three shapes. Each emitted in HTML by default (business audience) or MD (opt-in via config). HTML templates include inline styles so the rendered doc is self-contained; MD templates are CommonMark.

8.1 Main (Epic) doc

Filename: REQ-[6-hex]-[kebab-title-32].{html,md}. Content sections (order preserved):

  1. Metadata (front-matter in MD; <head> meta in HTML) — id, title, kind: "epic", parent: null, created, updated, status.
  2. Overall Scope — 2-4 paragraph narrative.
  3. Sub-sections — table with columns: REQ ID, Title, Description, Status, Link. Status is one of draft / ready / in-progress / done and doubles as the TODO tracker (when a sub-section is fully detailed, status flips to done).
  4. Personas — per-persona block: name, goals, context, success criteria.
  5. System NFRs — platform-level NFRs that span sub-epics (security, compliance, performance, scale, accessibility, availability, observability, data-retention). Consolidated from sub-epic NFRs post-hoc.
  6. Open Items — explicit questions/unknowns for stakeholder review.

8.2 Sub-section (Sub-epic) doc

  1. Metadata — id, title, kind: "sub-epic", parent: REQ-XXX, children: [REQ-YYY, ...] (only if further nested).
  2. Title.
  3. Scope narrative — 1-3 paragraphs.
  4. Stories — one section per story, content as in §8.3.
  5. Module NFRs — NFRs specific to this sub-epic (after consolidation).
  6. Open Items.
  7. Dependencies — list of other sub-epic REQ IDs this sub-epic depends on (references into the sibling sub-epics).

8.3 Story doc (embedded in sub-section)

Each story is a self-contained unit. MD template (HTML mirrors structure):

9. Requirements EditorPane

New pane under src/vs/workbench/contrib/insrc/browser/requirements/ following the Brainstorm EditorPane pattern. Three modes:

  1. List-review mode: accordion of items (sub-epics, stories, features). Each row:
    • Collapsed: title, one-line description, per-row actions [Approve] [Reject] [Feedback...]
    • Expanded: full description, edit inline, Save / Cancel
    • Header bar: [Approve All] [Reject All] [Add Item] [Regenerate]
    Gate payload includes items: [{ id, title, description, status }]. User decisions flow back via the gate reply.
  2. Tree-browse mode: persistent sidebar showing _index.json as a tree. Each node shows title, status chip, last-updated time. Clicking a node opens that doc in the main editor; the pane highlights the active node.
  3. Sub-section-handoff mode: list of sub-sections with "Start chat for this sub-section" buttons per row (command: insrc.requirements.continueInNewChat with payload { parentId, subEpicId }).

Opens on first list-review gate fired by the agent and persists across steps (mode changes). Closes when the agent finishes or the user explicitly dismisses.

10. Brainstorm Handoff

Existing brainstorm finalize step terminates with next: null. Add a new gate action "Hand off to Requirements" alongside the existing save/download/exit actions.

When chosen:

  1. Brainstorm finalizes its spec as normal (writes to brainstorms/).
  2. A new chat session is opened with the requirements agent as the target.
  3. The finalized brainstorm spec is passed as input.brainstormSpec (a string, the finalized HTML/MD content).
  4. Requirements scope-analyze checks for input.brainstormSpec first; if present, it seeds its classification from the spec's structure (spec-defined features count, domain keywords) instead of a cold user prompt.

Implementation: add a new ReplyAction name ('handoff-requirements') recognized by the brainstorm agent's finalize step; its handler invokes chatService.startSession with a pre-filled initial message and a structured brainstormSpec field.

11. GitHub Projects v2 Mapping

GitHub Projects v2 supports issues, labels, milestones, and rich custom fields, but doesn't natively model Epic / Story hierarchy or backlog grooming / sprint-planning workflows. We mimic those with explicit conventions: labels for type, task-lists in issue bodies for parent/child, custom fields for status / priority / size / iteration, and saved views for Epic roadmap, Story backlog, and sprint board.

11.5 Parent / child relationships

Three mechanisms, all maintained in lockstep by the push handler:

  1. Custom Parent field on the child issue — stores the parent issue number. Used by Story-Backlog view's "group by parent".
  2. Task-list in parent body — the Main Epic issue body ends with: 
    ## Sub-epics
- [ ] #101 Ingestion
- [ ] #102 Classification
- [ ] #104 Extraction
- [ ] #105 Matching
    Sub-epic bodies similarly task-list their children. GitHub auto-flips the checkbox when the linked issue closes, and shows a completion progress bar on the parent.
  3. Body back-links — each child issue body begins with Parent: #101 for discoverability when viewing the child in isolation.

11.6 Gaps vs Epic/Story natively

Things GH Projects v2 doesn't do well, and how we work around them:

ConceptNative supportOur workaround
Multi-level Epic hierarchy (Epic → Sub-epic → Sub-sub-epic) None (GitHub only has sub-issues 1-level deep, still in preview) Every level is an Issue with Kind field + task-list in body. Views group by Parent field.
Backlog grooming workflow None formal Status = Draft gating + "Needs Grooming" view surfacing ungroomed stories.
Sprint planning with capacity Iteration field exists; capacity math does not Sprint Board view + Size field. Sum-of-size per iteration shown in a project insights chart (built-in).
Story dependency visualization (DAG) None (GitHub dependency graph is for code deps, not issues) Dependencies view grouped by Parent; dependency refs live in issue body under # Dependencies as Blocked by #NNN — GitHub auto-linkifies and cross-references.
Roll-up rollup of Epic progress (% stories done) Partial (task-list completion) Task-list based. Not a rollup percentage on custom views, but sufficient for a glance at the parent issue.
Personas, NFRs, Acceptance Criteria as structured fields None Live in issue body as structured sections; not filterable but human-readable.
Acknowledged limits. GitHub Projects v2 is a solid tracker but not a specialized Epic/Story tool. Teams that want hierarchical burndown, sprint capacity math, or Kanban swim lanes at scale typically graduate to Jira, Linear, or Shortcut. This mapping gets the team to "functional" without a separate tracker subscription; the deeper feature set is a future optimization.

11.7 Push sequence (implemented via Delegate agent)

The requirements agent hands off to the Delegate agent with a plan derived from the finalized requirements tree. Delegate runs each step as a tool call, checkpointing between issues so a crash mid-push can resume.

The push is split into two phases:

  • Phase A — Schema reconciliation: inspect the target project's current schema (existing fields, views, labels, milestones), compute the delta against what the requirements push needs, present the delta to the user, apply only the approved additions. Runs once per project per push; no-ops if the schema already matches.
  • Phase B — Issue creation + project population: create / edit issues and add them to the project against the now-reconciled schema.

This design preserves any custom fields, views, labels, or workflow states the user has already set up in their project. We never overwrite or delete existing configuration — we only propose additions for missing pieces.

Default disposition. In the reconciliation UI, adds default to approved; extends-an-existing-field defaults to pending (unapproved) so users consciously confirm any change to existing schema. This respects the "never overwrite" principle while making fresh-project push one-click.

Phase B — Issue creation + project population

step B1: create Main Epic issue
  gh:issue:create
    title:    [Epic] <Main title>
    body:     <Main Epic body + task-list placeholder for sub-epics>
    labels:   [type:epic, source:insrc]      (only include labels that exist)
    milestone: <id from Phase A>             (only if created)
  → capture issue #

step B2: create Sub-epic issues (and sub-sub-epics)
  for each sub-epic / sub-sub-epic in dependency order:
    gh:issue:create
      title:    [Sub-epic] <title>
      body:     <sub-epic body + task-list for children>
      labels:   [type:sub-epic, source:insrc, domain:xxx]
      milestone: <main epic milestone>
    → capture issue #

step B3: create Story issues
  for each story in each sub-epic:
    gh:issue:create
      title:    [Story] <title>
      body:     <full story body + "Parent: #NNN">
      labels:   [type:story, source:insrc, domain:xxx]
      milestone: <main epic milestone>
    → capture issue #

step B4: patch parent bodies with real issue numbers
  for each parent issue:
    gh:issue:edit with final task-list body

step B5: add issues to project
  for each issue:
    gh:project:item-add
    gh:project:item-update × N fields
      (skip fields that the user declined during reconciliation —
       degraded view; still functional, just less filterable)

step B6: write mapping back to _index.json
  gh field per doc: { issueNumber, projectItemId, projectId, repoOwner, repoName }

step B7: report
  Summary: N Epics, M Sub-epics, K Stories, project URL,
           + any deferred schema items the user can approve later
Tool inventory for reconciliation. Several of these already exist (per the exploration audit): gh:project:list, gh:project:field-list, gh:label:list, gh:milestone:list, gh:project:item-add, gh:project:item-update. New tools this agent needs: gh:label:create, gh:milestone:create, gh:project:create, gh:project:field-create, gh:project:field-update (to add options to an existing single-select), gh:project:view-list, gh:project:view-create. All are thin wrappers over the GitHub REST / GraphQL API.
Partial approval mode. If the user declines some schema additions in Phase A, Phase B still runs but with reduced capability:
  • Missing labels → label simply omitted on created issues (no hard error).
  • Missing fields → corresponding item-update call skipped; issue still added to the project.
  • Missing views → no user-facing impact beyond the missing saved view.
  • Missing milestone → issues created without milestone; existing milestone reused if one already matches the Epic title.
The final report lists every deferred item so the user can re-run reconciliation later.
