Meta-tasks: structured multi-step task orchestration

Status: DRAFT · Owner: insrc · Depends on: handoff ▸ section-flow ▸ planner

1. Overview

Today the agent exposes two surfaces. One end is the chat REPL with free-form prompts (Pair / Delegate / Brainstorm / Designer / Planner, each its own step-machine). The other end is /handoff <intent>: a single-shot worktree-isolated sub-agent that produces one deliverable and gates on acceptance. Neither shape covers the case the user actually wants for design / plan / implement / review workflows: a structured task that decomposes itself into ordered work, runs each piece with its own tightly-scoped context, accumulates results, and can revise its own plan when reality diverges.

Meta-tasks are that middle layer. A meta-task is a named recipe (e.g. design, plan, implement, migrate, review) that the user invokes once with a high-level intent. The orchestrator scopes it, plans it, executes each step, and synthesizes the result — with every step's output persisted to disk so later steps can pull whatever they need.

The two load-bearing design choices, both already vetted by the user:

  1. Demand-pull context, not push-predict. Step N-1 doesn't try to guess what step N will need. Step N asks — specifically — via a typed ContextRequest, and a local LLM builds the answer from persisted outputs + tools.
  2. No orchestrator heuristics. The orchestrator never decides "this step doesn't need context" or "this step needs the prior deliverable". The cloud LLM declares sufficient explicitly when it has what it needs; the orchestrator only honors what the LLM says.

Concretely:

  • Handoff stays the leaf primitive — one spec, one worktree, one agent, one deliverable. Reused as-is; no changes required for v1.
  • Section-flow (the Q8 todo-orchestrator work) already runs an ordered step list with per-step status + artifact accumulation. Meta-tasks plug into this as a new family of recipes. Each leaf step is a handoff (or a non-handoff primitive like "ask local LLM to summarize").
  • Planner agent is invoked as the meta-task's first heavy step — it produces the plan that section-flow then executes.

In short: meta-task is not a new step-machine; it's a section-flow recipe + the two-phase execution model this doc introduces. The novelty is the context contract, not the orchestrator.

3. Meta-task lifecycle

Every meta-task instance goes through the same outer loop. The recipe (template) decides what each named step does; the orchestrator just runs the loop.

  1. Scope. A scope-analysis step reads the user's intent, walks the relevant slice of the repo (entities, files, prior deliverables, memory), and produces a scope manifest: in-scope artifacts, size estimate, risk hints, open ambiguities the user should resolve.
  2. Plan. The planner agent consumes the scope manifest and produces an ordered list of step descriptors. Each descriptor names a primitive (typically a handoff template), its intent, and its acceptance criteria. The plan is written to a TodoList.
  3. Approve. User gate: review the scope + plan, edit, accept. Same gate framework already used by handoff Mode A.
  4. Execute. Each step in the TodoList runs via the two-phase model (§4). The step's deliverable lands in the meta-task's persistRoot. The step's "did the plan still hold?" verdict feeds the revise hook.
  5. Revise (optional). If a step emits kind: 'plan-divergence' or its audit returns revise-major, the orchestrator re-invokes the planner with the failure context. The remaining steps may be rewritten; completed steps are not redone.
  6. Synthesize. A final step composes all step deliverables into the meta-task's primary artifact (e.g. a design doc, a single PR diff, a migration runbook).

4. Two-phase step execution

4.1 Phase 1 — context

The orchestrator hands the cloud LLM the step definition (template + intent + acceptance criteria) and the names + headings of every deliverable persisted by prior steps — not bodies, just a catalog. The cloud LLM responds with one of two things:

  • sufficient — "I have what I need from my caller; skip the local LLM and run me."
  • context-needed — a typed list of ContextRequest items the local LLM fulfills against persisted outputs + tools.

Phase 1 itself is mandatory — the cloud LLM is the only entity allowed to declare sufficiency. The orchestrator never short-circuits.

4.2 Phase 2 — task

The cloud LLM receives the assembled context (when phase 1 returned context-needed) and runs the step with full tool access. It terminates in one of three ways:

  • deliverable — success; body is persisted.
  • context-needed — "this context was insufficient because X; here's a refined request". Loops back to phase 1 with the reason attached (§6).
  • abort — hard fail with reason; step ends, orchestrator decides whether to revise the plan or surface to the user.

5. Wire shapes

5.1 ContextRequest

A small set of typed slots covering what we already have query primitives for in the daemon.

type ContextRequest =
  // Find specific code entities (LMDB graph + name-index).
  | { kind: 'entities';    names?:  string[];
                           kinds?:  EntityKind[];
                           repos?:  string[] }

  // Read files by glob pattern (bounded by maxBytes).
  | { kind: 'files';       globs:   string[];
                           maxBytes?: number }

  // Pull a prior step's output (or a section of it).
  | { kind: 'deliverable'; specId:  string;
                           heading?: string }

  // ANN over entity_vec + deliverable_vec (Lance).
  | { kind: 'semantic';    query:   string;
                           topK?:   number;
                           over?:   ('entities' | 'deliverables')[] }

  // Graph traversal: callers / callees / imports / closure.
  | { kind: 'graph';       op:      'callers' | 'callees' | 'imports' |
                                    'importers' | 'closure';
                           targets: string[];
                           depth?:  number }

  // Recent git activity for the scope.
  | { kind: 'git';         paths?:  string[];
                           since?:  string;
                           maxCommits?: number }

  // Step trace replay (audit / debug context).
  | { kind: 'trace';       specId:  string }

  // User memory bundle (top-k entries by ANN).
  | { kind: 'memory';      query?:  string };

Every slot maps to a query primitive that already exists in db/search.ts, the graph layer, Lance ANN, or the memory store — the local LLM's job is selection / packaging, not novel retrieval.

5.2 Phase1Ask

type Phase1Ask =
  | { kind: 'sufficient' }                              // skip local LLM
  | { kind: 'context-needed';
      requests: ContextRequest[];
      intent?: string };                                // free-text tiebreaker

Empty requests is not the same as sufficient. The schema rejects an empty-array context-needed — the cloud LLM has to actively pick a shape.

5.3 Phase1Result

type ContextChunk = {
  request: ContextRequest;        // echoed for traceability
  status:  'ok'              // fulfilled cleanly within cap
         | 'empty'           // no matches
         | 'partial'         // truncated under cloud-set topK or explicit cap acceptance
         | 'needs-narrowing' // too broad to pick blindly; local LLM declined
         | 'error';
  payload: unknown;               // shape depends on request.kind
  note?:   string;                // local LLM's rationale ("picked top 5 by ANN")

  // Populated when status === 'needs-narrowing'. Structured push-back
  // the cloud LLM uses to refine the next phase-1 ask.
  narrowingHint?: {
    matched:                    number;                          // e.g. 500 files / 5 MB
    suggestedFilters?:          string[];                        // "narrow by dir: src/a, src/b, src/c"
    suggestedAlternativeKinds?: ContextRequest['kind'][];        // "try 'semantic' or 'entities'"
    note?:                      string;                          // free-text guidance
  };
};

type Phase1Result = {
  chunks: ContextChunk[];
  meta:   { totalBytes:      number;
            elapsedMs:       number;
            droppedRequests: number };  // requests local couldn't fulfill (status === 'error')
};

Each chunk carries its originating request verbatim so the cloud LLM can see exactly what it asked for vs. what it got back. Two failure modes surface explicitly:

  • partial — truncation under a cloud-acknowledged cap (e.g. topK: 5 capped at 50 KB). Cloud asked for "at most N"; local LLM gave what fit.
  • needs-narrowing — the request was too broad to pick blindly. Local LLM declines to truncate silently and instead emits a structured narrowingHint — match count, suggested filters, alternative slot kinds, free-text guidance. The cloud LLM uses this to refine its next ask. See §6 for the resulting mini-loop.

No silent fan-out, ever — if local LLM can't fulfill cleanly, that's a visible signal not a hidden compromise.

5.4 Phase2Out

type Phase2Out =
  | { kind: 'deliverable';    body:     string }
  | { kind: 'context-needed'; requests: ContextRequest[];
                              reason:   string;            // REQUIRED
                              intent?:  string }
  | { kind: 'abort';          reason:     string;
                              resolution: 'user-required' | 'plan-revisable';
                              hint?:      string };

reason is required when phase 2 escalates back to phase 1. Schema rejects a missing reason. This is the load-bearing detail for retry contextualization (§6).

On abort, the cloud LLM recommends a resolution kind — but the orchestrator does not auto-route on it. Every abort escalates to the user (§7); the resolution + hint are surfaced in the abort gate as the cloud's guidance, not as a directive. This preserves the "user is the final authority on plan changes" rule while still giving the user the cloud LLM's read of the situation.

6. Contextualized retries

Two retry loops, separate cap counters, never paraphrased by the orchestrator.

6.1 Phase 1 ↔ Phase 1 (narrowing loop)

Triggered when any ContextChunk comes back with status: 'needs-narrowing'. The orchestrator returns to phase 1 with the cloud LLM's prior ask + the local LLM's narrowingHint(s) attached. Cloud refines just the offending requests; ok chunks are kept in the cumulative catalog so they aren't re-fetched. 

─── Narrowing required ───
You requested:
  <serialized prior ContextRequest[]>

Local LLM returned:
  <chunk summary; needs-narrowing chunks expanded with narrowingHint>

Refine the marked requests. Narrowing retries remaining: 1 / 2.

─── Updated request ───

Cap: maxNarrowingRetries: 2. On the third attempt, the prompt becomes "Narrowing cap reached. Either accept a partial result with an explicit cap, or abort with reason." — forcing a decision instead of looping.

6.2 Phase 2 ↔ Phase 1 (context-needed loop)

Triggered when phase 2's terminal output is kind: 'context-needed' — the cloud LLM ran the task with the assembled context and decided it was insufficient. Loops back to phase 1 with the reason attached. 

─── Previous attempt ───
You requested:
  <serialized prior ContextRequest[]>

Local LLM returned (full payloads on disk, refer to chunk-ids):
  <chunk summary: kind, status, byte-count, droppedRequests>

You then said this was insufficient because:
  <reason from Phase2Out>

Context retries remaining: 2 / 3.

─── Refine your request ───

6.3 Shared rules

  • Reason required. Schema rejects a phase-2 context-needed with no reason; phase-1 needs-narrowing chunks must carry a narrowingHint. No retry without an articulated why.
  • Caps, not silent loops. Narrowing 2, context 3. After a cap the prompt forces either a partial accept or an explicit abort. Steps always end with a deliverable, partial result, or abort — never hang.
  • Catalog grows monotonically across both loops. The cloud LLM's catalog of fetched chunks persists across narrowing AND context retries within a single step. Earlier successful fetches stay; refinements only affect the requests that failed.
  • Counters are independent. Burning through narrowing retries doesn't eat into the context-retry budget, and vice versa. They're different failure modes (request shape vs content sufficiency); their caps reflect that.

7. Plan revision (user-driven)

The plan is not immutable, but revisions are always user-gated. The orchestrator never auto-revises; the cloud LLM's resolution recommendation is information for the user, not a routing signal.

7.1 Abort gate

Any Phase2Out: { kind: 'abort' } surfaces an inline gate in chat (standard gate framework, no new UI). The gate carries:

  • The failed step's name + lifecycle position
  • The cloud LLM's reason verbatim
  • The cloud LLM's recommended resolution (user-required or plan-revisable) and hint — as the cloud's read of the situation, not as a forced action
  • Four action buttons + a free-text feedback input
─── Meta-task: design / Step "M3 plan" aborted ───
Reason:        <abort.reason>
Cloud says:    <abort.resolution> — <abort.hint>

[ Adjust plan ]  [ New plan ]  [ Retry step ]  [ Abort meta-task ]

Your feedback (optional): ______________________________________

7.2 User-driven revision paths

  • Adjust plan. Light-touch re-planner invocation scoped to the failed step + downstream. User's feedback feeds in as additional scope context. Surgical, cheap.
  • New plan. Full re-invoke of /plan as a sub-meta-task with the original scope + user feedback + completed-steps deliverables as context. Rewrites all remaining steps.
  • Retry step. Reruns the failed step's phase 1+2 with the user's feedback injected into its context (similar to a context-needed retry, but seeded by human guidance instead of the cloud LLM's self-articulated reason).
  • Abort meta-task. Ends the run. Partial state persists in ~/.insrc/meta/<id>/ for inspection or future resume.

Whether the user picks "Adjust plan" or "New plan", the orchestrator invokes /plan as a sub-meta-task — the difference is the scope of what the sub-task is allowed to change. Adjust passes only the failed step + downstream as the rewrite target; New passes the whole remaining tail.

Termination on revision loops. maxPlanRevisions: 2 user-driven revisions per meta-task. After the cap, the abort gate's "Adjust plan" and "New plan" options grey out; only "Retry step" and "Abort meta-task" remain. Prevents walking the user into infinite revision cycles.

7.3 Step heartbeats

Long-running steps need keepalive emissions or the IPC channel goes quiet and the user can't tell the difference between a working step and a hung daemon. The orchestrator runs a 30-second timer per active step that fires a progress event whenever nothing else has emitted within the window. Reuses the always-visible top progress widget — no new UI.

Status content is contextual — whatever substate the orchestrator knows about gets surfaced verbatim:

  • phase-1 ctx: fetching <slot.kind> (Ns) — local LLM is mid-fetch
  • phase-2 task: thinking (Ns) — silent cloud LLM time (no streaming, no tool active)
  • phase-2 task: tool/<name> (Ns) — cloud LLM is blocked on a tool call
  • phase-2 task: retry 2/3 — building context (Ns) — during a context-needed retry's phase 1

Two further rules:

  • Honest, never filler. If nothing meaningful is known, emit elapsed time alone (phase-2 task (Ns)). Avoid "still working…" placeholder strings.
  • Soft long-step threshold. At 10 min elapsed without activity, the heartbeat status string gains a — consider /abort suffix. Purely informational; nothing automatic happens. The user decides. 
const STEP_HEARTBEAT_INTERVAL_MS = 30_000;
const STEP_LONG_THRESHOLD_MS    = 10 * 60_000;

8. Persistence + state

Mirroring handoff's layout. Each meta-task instance gets a directory under ~/.insrc/meta/: 

~/.insrc/meta/<metaTaskId>/
  meta.json                       # template, intent, scope, status
  plan.json                       # canonical plan (latest revision)
  plan.history.jsonl              # one record per plan revision
  scope.md                        # scope-step deliverable
  step-<n>-<slug>.deliverable.md  # each step's primary output
  step-<n>-<slug>.phase1.jsonl    # phase-1 ask + result + retries
  step-<n>-<slug>.phase2.jsonl    # phase-2 output (+ abort reasons if any)
  step-<n>-<slug>.audit.json
  synthesis.md                    # final composed artifact

Phase-1 / phase-2 logs are append-only JSONL so retries leave a complete record without rewriting earlier attempts. The orchestrator never reads its own state from memory — on resume it rebuilds from these files. (Same approach as handoff trace.)

9. Worktree shape: mutate vs analyze

Open design tension. A meta-task whose steps make code edits (e.g. implement) wants each step to build on the prior step's edits — one shared worktree. A meta-task that's purely analytical (design, plan, review) wants each step in an isolated worktree so they can't accidentally clobber state.

Proposal: meta-task templates declare a worktreeMode:

ModeBehaviorUse for
shared One worktree allocated at scope; every step runs in it; diffs accumulate across steps. implement, migrate
isolated Each step gets its own fresh worktree (handoff default). Steps communicate only via persisted deliverables. design, plan, review
none No worktree. Step runs against the source repo read-only. For meta-tasks that produce only docs. brainstorm, doc-only design

10. User-facing surface

Meta-task reuses the code-analyzer flow's emission pattern verbatim. Zero new chat widgets, gate UIs, or report panes. The orchestrator emits the same IPC stream events the chat panel and workbench already consume; the user sees the same shape they're used to.

SignalChannelWhat it surfaces
liveStep({agent, step, text, done?}) IPC stream Per-step activity-console bubble in chat (chatView._handleLiveStep). Token-streamed text accumulates; done:true removes the bubble. One bubble per (agent, step) pair.
progress({step, status}) IPC stream Always-visible top progress bar (chatView._showProgress). Carries the contextual heartbeat content described in §7.3.
todos mutations IInsrcTodosService Plan rendered in the TodoList workbench pane (already shared by section-flow + handoff). Items advance as steps complete; final body via updateListBody.
gate events Inline chat gate framework Plan-approval, abort-resolution, plan-revision-confirm. Same gate UI as handoff Mode A.
updateListBody + flow contribution Workbench editor Final synthesis auto-opens in the report pane via a MetaTaskFlowContribution modelled on HandoffFlowContribution / DataAnalyzerFlowContribution.

10.1 Per-step emission pattern

For each step in the executing plan:

1. todos.markInProgress(stepItem)
2. liveStep({ agent: 'meta-task:design',
              step:  'M3 plan: phase-1 ctx' })           // bubble appears
3. ... local-LLM fetches stream as token chunks ...      // bubble body grows
4. liveStep({ ..., done: true })                          // bubble removed

5. liveStep({ agent: 'meta-task:design',
              step:  'M3 plan: phase-2 task' })          // new bubble
6. ... cloud-LLM tokens stream into the bubble ...
   ... or progress() heartbeats fire every 30s if no stream ...
7. liveStep({ ..., done: true })

8. Persist deliverable to ~/.insrc/meta/<id>/step-N-*.md
9. todos.markComplete(stepItem)

During retries (narrowing or context-needed) the bubble label naturally encodes state: M3 plan: phase-1 ctx (narrowing 1/2), M3 plan: phase-2 task (retry 2/3).

10.2 Synthesis bubble

Following code-analyzer's synthBubble pattern, the meta-task's final synthesis step uses one long-lived liveStep bubble that accumulates multiple chunks (executing N leaves, composing report, …) rather than creating a new bubble per chunk. The final text becomes the report-pane content via updateListBody.

10.3 Chat card

One small chat-card per meta-task instance (modelled on chatHandoffWidget) sits in the transcript as a launch point + at-a-glance status: meta-task name, current lifecycle stage, step N of M, "open dashboard" link to the TodoList pane. No actions on the card itself — all interaction is via gates and the dashboard.

11. Open questions

The five questions originally listed here (local-LLM selection contract, planner placement, user surface, step granularity, abort surface) have been resolved into §5–§10. New questions will be added here as they surface during the build.

  1. Sub-meta-task gate semantics in detail. When /plan runs as a sub-meta-task of /design, the rough rule is "only the outermost surfaces gates". But the sub-meta-task might want to surface its OWN plan-approval gate (the user is approving the planner's output, not the parent's). Open: does the parent's approve-plan gate just include the sub-task's plan inline, or does the sub-task get its own gate? Decide concretely when M3 lands.
  2. Deliverable catalog format for phase 1. Phase 1 hands the cloud LLM a "catalog" of prior step deliverables (names + headings, not bodies). What's the exact shape — a flat list of (stepName, headings[])? Indexed by step number? Searchable via the same deliverable slot? Trivial to nail down at M2 but worth surfacing now.
  3. Where does scope analysis live? The lifecycle has a scope step before the plan step. Is scope its own primitive, or is it the first thing the planner sub-meta-task does? My instinct: a separate primitive, because scope is meant to be cheap and consultative ("does this make sense?") while the planner is heavier. Confirm when M2 / M3 land.
